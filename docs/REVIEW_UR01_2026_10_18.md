# Review UR-01 (static update writer), 2026-10-18

Scope: 8ec1fa460 (code) and 30f496ea8 (docs/allowlist) on origin/dev. Static review, no board.

Counts: HIGH 0, MED 1, LOW 3, INFO 4.

## UW-01 MED: static TCB/stack reuse is time-based, not proven
`wr_task` WR_EXIT gives `wr_done` and calls `vTaskDelete(NULL)`. A self-deleting task stays on
`xTasksWaitingTermination` until an idle task runs `prvCheckTasksWaitingTermination` -> `prvDeleteTCB`
(which also runs the TLS-pointer deletion callbacks and `vPortCleanUpTCB`). With static allocation nothing is freed,
but if `xTaskCreateStaticPinnedToCore` re-initialises `s_wr_tcb` while its list item is still linked on the
termination list, the kernel lists are corrupted silently (no assert), and the later `prvDeleteTCB` would act on the
new task. `wr_start` only waits until 100 ms after `s_wr_exit_tick`. In practice the gap between jobs (new HTTP
request, TLS handshake, plus the delay itself, during which the caller blocks) lets IDLE1 run, so this is unlikely,
but it is not guaranteed: IDLE1 is starved by any busy prio>=1 task on core 1. Also note `eTaskGetState()==eDeleted`
is NOT a fix: it is exactly the "still on the termination list" state.
Fix (recommended): make update_fetch_wr persistent. Create it once (static) on first use, never delete it; WR_EXIT
becomes "go idle" (record stack margin, give `wr_done`, loop back to `xSemaphoreTake(wr_req)`), and keep the two
semaphores for the life of the module. This removes the grace delay, the `s_wr_used/s_wr_exit_tick` state and the
reuse question entirely. The wedge rule is unchanged (a wedged writer still blocks the next job).

## UW-02 LOW: no test reaches the reuse path ordering
The host stub counts static creates but nothing checks that a second job waits for (or does not need) reclaim. With
the UW-01 persistent-task fix, add a test that two consecutive download jobs create the writer once.

## UW-03 LOW: stack_margin exit record per job
`stack_margin_retain_exit` + `stack_margin_task_exit` run before `wr_done` is given, which is the right order (UB-01).
With a persistent writer (UW-01) the slot should stay registered and only the retained high-water updated; do not
call `stack_margin_task_exit` on "go idle".

## UW-04 LOW: draw model leaves the 1024 B scratch inside MEASURED_DRAW
`FETCH_HEAP_WRITER_SHARE_BYTES` (4096 + 400 = 4496 B) is correct for the rows (measured with the 4096 B heap stack;
GP-01's +1024 B never entered the table). The former heap scratch (1024 B) is now static but stays in
MEASURED_DRAW: conservative by 1024 B, documented as margin. Fold it out at the BENCH-PENDING re-measure.

## INFO
- UW-05: double start: `busy` is an atomic exchange and only `fetch_task` calls `wr_start`; `s_wr_exit_tick` is
  written before `xSemaphoreGive(wr_done)`, so the reader sees it. No race.
- UW-06: shared static scratch: one job at a time (`busy`), checks take no scratch, and a wedged writer that may still
  own `s_scratch` blocks every later download in `wr_start` before WR_BEGIN. No sharing hazard.
- UW-07: dropping the 7168 B largest-block gate is sound: the biggest remaining internal allocation of either kind is
  the TLS 2 KB client buffer pair, still gated by FETCH_CHECK_BLOCK_MIN 3072 B.
- UW-08: the updated tests can fail: the 4096 B-block download now must not report `low_heap_block`, and
  FETCH_CHECK_BLOCK_MIN-1 must; the internal-malloc count must be 0 for a download (would be >=1 if the heap scratch
  returned). Pinned numbers (17908 B DMA hop need, 25696 B hop need) follow from 21488 - 4496.
