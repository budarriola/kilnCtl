# Review: OH-04 install confirm tracking (2026-10-20)

This is a static review of `02e31fca9` (the OH-04 fix) and `932aaff3f` (its test tweak) on origin/dev. No code was changed and the board was not touched.
It covers `update_install_record.c/.h`, `update_install_http.c`, `main_network_http.c`, `recovery_install.c` (the rollback rewrite), `ota_page.html`, `mcp_server_update.py` and `update_http_client.py`.

Counts: HIGH 0, MED 1, LOW 5, INFO 3.

## Findings

| ID | Sev | Where | Problem | Fix |
|----|-----|-------|---------|-----|
| OC-01 | MED | `App/drivers/update/update_install_http.c:262-278`, `App/main_network_http.c:305` | `update_install_http_mark_confirmed()` makes one `ota_http_update_try_begin` attempt. When the claim is busy it returns 1, and the confirm task then deletes itself. Nothing retries in this boot, so `last_install.state` stays `pending_confirm` until the next reboot. That can take weeks on a kiln. Meanwhile the MCP install call keeps answering UNKNOWN and the web page says "Not final yet". The busy case is likely, not rare. `pico_auto_update_boot.c:128` takes the same cross-processor claim at boot, so an ESP install that brings a newer Pico image is likely to have a Pico auto-update running at the 30 s confirm. A stage upload or update fetch during the soak hits the same window. | Retry the mark until rc != 1. Either loop in the confirm task with a bounded backoff (for example every 5 s for 10 min, then every minute), or have whoever holds the claim run the mark from `ota_http_update_end()`. Another option: derive the state at status time from `esp_ota_get_state_partition(running) == ESP_OTA_IMG_VALID` plus a running-image match (see OC-03), so the record write only caches it. |
| OC-02 | LOW | `App/main_network_http.c:298-305`, `App/drivers/update/update_install_record.c:141-161` | The window between the confirm and the record write. `boot_confirm_step` marks otadata VALID and clears boot_guard before `mark_confirmed` writes the record. Power loss in between, or an NVS write failure (rc -1, never retried), leaves an image that is VALID while the record still reads `pending_confirm`. The page and the MCP then say "a reset now rolls it back", which is false at that point. The next OTA-slot boot heals it, because the mark runs on every boot and the recovery rewrite skips a VALID app. So the record is never wrong in the dangerous direction. | Retry rc -1 along with OC-01. In the status handler, report the result as confirmed whenever the running partition is VALID and matches the record. |
| OC-03 | LOW | `App/drivers/update/update_install_record.c:126-133,141-161` | `update_install_confirm_result` marks any OK unconfirmed record confirmed without checking that the record names the running image (`semver`/`id`). Here is how the wrong record gets confirmed. Install X records ok. A reset in the soak rolls X back. Recovery's rewrite to `rolled_back` is best effort (`recovery_install.c:229-230`, the `kv_write` result is ignored), so the write can fail. Image Y is then flashed over JTAG (`flash_firmware`) or another path that does not touch the record. Y confirms and stamps the X record "installed and confirmed". The web page then shows a rolled-back X as confirmed. The MCP is protected only because `_ok_is_new` also requires `running_version == want`. | In `update_install_res_mark_confirmed`, require the record's semver (and its id, when the app can compute it) to equal the running app's descriptor. Otherwise leave the record alone, or rewrite it as superseded. |
| OC-04 | LOW | `App/drivers/update/update_install_http.c:131-140` (install_prepare) | A second install before the first one confirms is not refused. While the running image is still PENDING_VERIFY, a new POST `/api/update/install` erases the pending OK result (`app_res_erase`) and reboots into recovery. The first image's soak outcome is lost. If recovery then fails without modifying the app and boots back into the unconfirmed slot, the bootloader can mark it ABORTED, and the board lands in recovery with a FAIL reason for the second install, not `rolled_back`. This depends on the order in which recovery and otadata are handled; it has not been bench-verified. | Refuse the install with 409 while the running partition is PENDING_VERIFY, or while the last result is `pending_confirm` (the "confirming boot, retry in N s" pattern). |
| OC-05 | LOW | `tools/PcTools/src/kilnctrl/mcp_server_update.py:692,797,840` | `_SETTLED_STATES` treats `recorded` as final. A target image built before OH-04 (a downgrade, or reinstalling pre.3) reports `recorded` for an OK result that has not been confirmed. `_ok_is_new` then returns "ok - installed" up to 30 s before the soak ends, and a later rollback goes unreported. The rollback lands in recovery, so the next call reports UNKNOWN or 404, never FAILED. The mapping itself never reports ok for `rolled_back`, because that is code FAIL and `_failure_is_this` returns FAILED. | When `state == "recorded"`, `code == "ok"` and `detail != "confirmed"`, add a note to the ok line: "board predates OH-04: boot confirm not proven". Alternatively, require one more `/api/status` read with uptime > 35 s. |
| OC-06 | LOW | `KilnFW_recovery/main/recovery_install.c:227`, `App/drivers/update/update_install_record.c:116-121,208` | The `CONFIRMED` guard in `update_install_res_apply_rollback` and the `confirmed` detail name exist only in recovery images built from this commit or later. Recovery is flashed separately, so a bench or field board on an older recovery image shows detail 36 as an unknown name. Such a board would also rewrite a confirmed result to `rolled_back` if `app` were ever the last invalid partition. That is unlikely, because any new install rewrites the record first. | Note in KNOWN_ISSUES/BENCH docs that the recovery image must be rebuilt and reflashed to get OH-04 end to end. Optionally show unknown detail codes numerically. |
| OC-07 | INFO | `App/drivers/net/ota_page.html:1124-1141` | `loadLastInstall()` runs once, on page load. A page opened during the soak keeps the "waiting ... Not final yet" text until it is reloaded. | Re-poll every 5 s while the state is `pending_confirm`, and stop once it is final. |
| OC-08 | INFO | `App/drivers/update/update_install_record.c:156-160` | Flash and NVS wear. The mark writes only on a real change: an OK record not yet confirmed. Every later boot does a read only. That adds 1 blob write (32 B) to kiln_nvs per install, which is negligible next to FW-01. | None. |
| OC-09 | INFO | `App/main_network_http.c:298-306`, `KilnFW_recovery/main/recovery_install.c:224-231` | boot_guard, otadata and Pico ordering are correct. The mark runs only after `BOOT_CONFIRM_STEP_DONE` (mark-valid done and boot_guard counter cleared) and is skipped on factory. It cannot fail the boot. Recovery rewrites only when `esp_ota_get_last_invalid_partition()` is `app`. A reset during the soak gives PENDING_VERIFY, then ABORTED, then recovery, then `rolled_back`, which is the intended path. The Pico link does not take part in the confirm (`link_up` is informational), so `confirmed` is an ESP-only statement. A Pico update triggered by the new image is tracked separately (see OC-01 for its claim collision). | Say "ESP image" in the page text if Pico confusion arises. |

## Cases checked

- Reset during the soak: correct (OC-09). The stale-record variant is OC-03.
- Power loss between the confirm and the record write: safe direction, self-heals on the next boot (OC-02).
- Pico or ESP update ordering: the Pico auto-update claim blocks the mark (OC-01).
- Second install before the first one confirms: not refused (OC-04).
- Busy claim left pending forever: yes, until the next reboot (OC-01).
- NVS or flash wear: negligible (OC-08).
- boot_guard and otadata: correct (OC-09).
- MCP success for a rolled-back image: not for an OH-04 image. A pre-OH-04 target can report ok before its soak (OC-05).
