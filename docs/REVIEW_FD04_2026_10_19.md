# Review: FD-04 SNTP TIME_SYNC event (ee4cc5ab9), 2026-10-19

Scope: `time_sync.c/.h` (`s_event_pending`, `time_sync_take_event`), `event_log.h` (`EVENT_CODE_SYS_TIME_SYNC=32`),
`telemetry_log.c` (emit into both stores), `event_log_decoder.py` (`annotate_utc`), `main_page.html` (UTC footer),
and the tests. Review only, no code changed.

Counts: **HIGH 0, MED 1, LOW 4, INFO 6**

## MED
- **FQ-01 `annotate_utc` misses reboots where uptime does not go down.** A boot segment ends only when `uptime_s`
  decreases. If boot A's last record is at uptime 30 s and boot B's first record is at 40 s or later (short boot,
  crash loop, or a quiet boot B), B's records join A's segment and get A's anchor, so their UTC is wrong with no
  warning. The record has no boot id, and no boot event is logged into these stores. Fix: emit a SYSTEM boot record
  (for example an FD-03 boot counter) as the first event in each store, segment on it, and keep the
  uptime-decrease rule as a fallback. Display only, no safety effect.

## LOW
- **FQ-02 Takes the flag even if the write fails.** `time_sync_take_event()` clears the flag before
  `event_log_emit()` runs, and both return values are ignored. A failed write (store not mounted, flash worker busy)
  loses that anchor until the next resync, about 1 h later. Fix: re-arm on failure, or log the error.
- **FQ-03 Hourly resync fills the autotune store.** No `CONFIG_LWIP_SNTP_UPDATE_DELAY` override, so IDF uses the
  1 h default, and `sntp_sync_cb` fires on every resync. That is 2 records/h (one per store, 64 B/h): little flash
  wear. But the autotune store is capped at 256 KiB (8192 records) and rarely gets real events. Within about
  341 days on an idle board, TIME_SYNC records evict all real autotune history. Fix: log only the first sync per
  boot plus any step larger than N s, or write into the firing store only.
- **FQ-04 The anchor's uptime is the write time, not the sync time.** `arg` is `last_sync_epoch`, taken in the
  callback. `uptime_s` is stamped later in `event_log_emit` (telemetry tick 1000 ms, plus flash-worker dispatch,
  plus truncation to whole seconds). The header comment says they are "the same instant", but they can differ by
  1-2 s. If several syncs come before one take, they merge into one event with the newest epoch and an even later
  uptime. Fix: record the uptime inside the callback with the epoch, or emit `time(NULL)` at write time; and fix
  the comment.
- **FQ-05 The wiring is untested.** Neither the emit in `telemetry_log.c` nor the footer JS has a test, and no
  negtest is recorded for the new host or pytest tests. `test_ts_fd04_sync_event_once_per_sync` is not vacuous (it
  checks false before, true after, and false again), but it depends on running first in the section, because no
  earlier test may call `sntp_sync_cb`. Fix: reset `s_event_pending` in a test hook, and negtest the new tests with
  `tools/negtest.ps1`.

## INFO
- **FQ-06 The flag has no race.** It is set and cleared under `s_status_mux` (`portENTER_CRITICAL`), and the epoch is
  read under the same lock, so it needs neither volatile nor atomic. Coalescing is fine apart from FQ-04.
- **FQ-07 Epoch range is correct until 2106.** `(int32_t)(uint32_t)time_t` plus the decoder's `& 0xFFFFFFFF` is right
  for 1970-2106, and there is a test past 2038. The 64-bit `time_t` truncates in Feb 2106, and no firmware code
  reads `arg` back as a signed value. Not a concern.
- **FQ-08 No safety code reads wall time.** FD-04 adds no wall-time readers. The existing `time(NULL)` uses
  (`profile_executor_run.c` run_started, `safety_link.c` fault-edge `unix_time_s`, CT verify `taken_unix`,
  adaptive-tune `last_applied_unix_s`) are timestamps that are stored or displayed only. None of them branches on
  wall time.
- **FQ-09 The footer leaks nothing new.** `time_synced` and `time_now_epoch` were already in `/api/status` before
  FD-04, and the dashboard tier is public by owner decision. The current time is not sensitive.
- **FQ-10 The footer shows UTC only.** It ignores the configured TZ that `/api/status` already exposes. This is a UX
  choice.
- **FQ-11 Old data loses anchors.** When a store trims its oldest segments, it can drop a boot's only anchor. The
  hourly resync (FQ-03) re-anchors later records, so only records from the gap before the next resync get None.
