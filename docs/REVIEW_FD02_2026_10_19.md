# Review: FD-02 durable firing trace (3fba7f2bd), 2026-10-19

Scope: `drivers/persist/firing_trace.{c,h}`, `firing_trace_glue.{c,h}`, `drivers/http/firing_trace_http.c`,
hooks in `profile_executor.c`, `profile_executor_status.c`, `main_control_bringup.c`, `dashboard_http.c`,
`test/test_firing_trace.c`. Static review only, no bench run.

**Counts: HIGH 1, MED 2, LOW 4, INFO 4.**

## HIGH

**FY-01: second poster on the one-poster flash-worker slot.** `firing_trace_glue.c` `ft_post()` calls
`uart_bridge_ext_post_on_flash_worker()`. That slot enforces the ONE-POSTER INVARIANT
(`uart_bridge_ext.c:327`, `:776`): it latches the fn of the first accepted post in `s_bx_post_owner_fn`
and refuses every other fn for the rest of the boot. The existing poster is safety_link_poll's
Pico-half divergence recapture. So whichever fn posts first wins for the whole boot:
- if the trace posts first (first sample of a firing before any recapture post), the safety divergence
  recapture is refused for the rest of the boot. That breaks a safety-side divergence check;
- if the recapture posts first, every trace post is refused. No periodic flush runs, so a power cut loses
  the whole firing, not "at most 10 samples" as `firing_trace.h` claims, and the slot logs an `ESP_LOGE`
  on every executor tick (see FY-03).
Fix: do not share the slot. Either give the trace its own slot or queue on the worker, or follow the
invariant comment's rules for a real second poster. Only the end-of-firing flush (`flash_hop_run`) works.

## MED

**FY-02: the tests cannot see FY-01.** `test_firing_trace.c` uses its own `t_post` stub, which always
accepts. `test_post_busy` checks only firing_trace's own double-post guard. No test runs the real
slot semantics, or a refused post (any `ESP_ERR_INVALID_STATE` that never clears). The power-cut bound
test (`25 - durable <= FT_FLUSH_EVERY`) holds only because the stub accepts every post. Add a case for a
post that is refused forever. The bound should then fail, or degrade in a documented way.

**FY-03: the flush retries every tick with no backoff when a post is refused.** When `post` fails,
`firing_trace_service()` sets `s_flush_due` again, so the next control tick tries again. That is a lock
take on the post slot, plus a log line from the slot, on every executor tick. The executor itself does
not block (the take uses a 0 timeout), but it puts per-tick logging work on the control path. Rate-limit
the retry, for example to the next sample, and log only once.

## LOW

**FY-04: the CSV of an in-progress firing is stale and does not say so.** `GET /api/firing_trace?id=N`
reads the slot file, so it shows only flushed samples: up to 10 min stale, and nothing at all under FY-01.
The JSON shows `closed:false`, but the CSV has no marker. Document this, or add the RAM tail for the
active seq.

**FY-05: an ESP reboot mid-firing leaves a file that never closes.** After a reboot `s_active` is false,
so a resumed or new run gets a new seq. The earlier file keeps `closed:false` forever and looks like a
firing still in progress in the list. No id or slot mixup was found: the seq is restored as the highest
valid seq + 1, the slot is `seq % 4`, and `firing_trace_open` checks the seq. Consider marking files left
open at boot as interrupted.

**FY-06: the freed aux (monitor-only) zone.** `_Static_assert(MAX31856_CHANNEL_COUNT == FT_ZONES)` and the
fixed `z0..z2` CSV columns are consistent with the hardware. The trace blanks only zones in `inactive_mask`,
though. A relay-less HEATER (owner 2026-10-05 monitor-only) is not inactive, so its duty column shows
`0.0` instead of blank, and that reads like "heater commanded off". Blank the duty when the zone has no
relay.

**FY-07: the end flush blocks the executor or the halt caller.** `firing_trace_end()` runs a synchronous
28.8 KB atomic write through `flash_hop_run`, on the executor task (run end) or on the halt caller. It is
outside `s_exec.lock` and next to the existing `firing_stats_persist` NVS write, so the pattern is not new.
But it adds a temp-file write plus rename (tens to hundreds of ms) before the stats persist. Outputs are
already off on these paths, so this is not a safety problem. Note it in the timing budget.
Also: if `flash_hop_run` returns an error after a job was queued, `s_job_busy` is cleared, and a new
firing could reuse `s_buf` while that job is still reading it. The file stays self-consistent (the CRC is
taken over what was written), but it may mix two firings.

## INFO

- **FY-08 (cfg space):** each flush needs a free 28.8 KB temp copy. 4 x 28.8 KB = 115 KB is retained, on a
  2.3 MB partition. If space runs out, `cfg_fs_write_atomic` fails, the code logs it, and it retries one
  sample later. The older file survives (atomic rename). The traces do compete with config saves for
  space, so they could push a near-full cfg partition over the edge. Today's margin is large.
- **FY-09 (power cut mid-rename / boot recovery):** the atomic temp + rename leaves the old file or the new
  one. At boot, `firing_trace_init` validates the magic, version, zones, rec size, both CRCs, the length
  and `seq % 4 == slot`, and ignores anything else. Behaviour was not checked against a leftover temp
  file, which is `cfg_fs`'s job.
- **FY-10 (httpd stack):** the list path puts about 0.6 KB on the stack (json 432 B, entries 48 B,
  query/disp/id). The CSV path puts about 0.1 KB on the stack and uses 28.9 KB of heap-allocated PSRAM per
  request. Against 3152 B free this is acceptable, but it is the largest new frame. Re-measure the httpd
  high-water mark on the bench.
- **FY-11 (RAM / executor):** the persistent buffer is 28,824 B in PSRAM only, with no internal fallback
  (8 KB floor respected). `firing_trace_note()` under the lock is RAM-only: `time()`, `lroundf`, 20 B of
  stores. Writing NaN into `actual_c`/`duty` for inactive zones comes after their last use
  (`history_record`). Executor control behaviour is unchanged.
