# REVIEW_OR08_2026_10_19

Scope: OR-08 on origin/dev, 962e5ea21..85d4cec3e. `ota_http_pico.c` Pico rollback worker is now one persistent
static task (`xTaskCreateStaticPinnedToCore`, 4096 B static stack, parks on `ulTaskNotifyTake`). Also reviewed:
host stubs, `test_ota_http.c`, `test_stack_margin_registry.c`, `check_all_task_stack_budgets.py`,
`check_stack_margin_registration.ps1`. Code review only, no fixes.

Counts: HIGH 0, MED 0, LOW 2, INFO 5. KNOWN_ISSUES prefix: OW.

## Findings
- **OW-01 LOW.** The `.dram0.bss` ceiling is stale and loose. `CEILING_BYTES = 81500` (set 2026-10-13 at a
  measured 80728). The dev-batch ELFs that contain OR-08 (C:\wt\devbatch_d277, checkbuild_471a538569) measure
  0xfea0 = 65184 B, so the check passes honestly but leaves about 16 KB of headroom. It would not catch UR-01
  (+5120 B stack) plus OR-08 (+4208 B measured, 0xfea0 - 0xee30 against the main-tree ELF) happening again
  several times over. Re-baseline the ceiling to measured + ~500 B, as the data-ceiling comment says.
- **OW-02 LOW.** The host tests never run the worker body. The `ulTaskNotifyTake` stub returns 0 and the static
  create never calls the task function. `xTaskNotifyGive` counts calls but does not record which handle it
  received. Nothing checks that the notify targets `s_ota_pico_rollback_task`, that the worker releases the claim
  after `ota_pico_rollback_run()`, or that the run stores its outcome before `ota_http_update_end()`. Only the
  source scan (no `vTaskDelete(NULL)` and no `stack_margin_task_exit` anywhere in the file) pins persistence. Suggested fix:
  record the notified handle in the stub, and make `ota_pico_rollback_run` callable from the test (or add a
  span scan that puts `ota_http_update_end()` after the async-result store). Negtest both.
- **OW-03 INFO. No notify/claim race.** A second POST must win the `OTA_HTTP_CONTEXT_PICO` claim before it gets
  to `xTaskNotifyGive`. The worker releases the claim as the last statement of a run, after it stores the
  outcome. If a POST notifies before the worker loops back to `ulTaskNotifyTake`, the notification value
  latches (counting, clear-on-exit), so the take returns at once and no notification is lost. "Notify while
  busy" cannot happen because the claim is held. `safety_link_send_rollback_ex` does not use the calling task's
  notification slot, so the default index 0 is free.
- **OW-04 INFO. Handle publication and registration are sound.** The handle is written once by the httpd task
  (an aligned pointer store) and then `stack_margin_register` runs. The worker runs at `tskIDLE_PRIORITY+1`,
  below httpd, and never touches the handle. A failed create leaves the handle NULL, answers 500 and releases
  the claim, so the next POST retries. The registration is not retried if `stack_margin_register` itself
  refuses (table full). Under UW-03 that refusal is a pre-existing, check-gated condition.
- **OW-05 INFO. No update-claim leak.** Every path after the claim releases it exactly once: early refusals
  (existing code), create failure, or the end of the worker run. The worker loop has no early `continue`.
- **OW-06 INFO. RAM impact.** OR-08 permanently costs about 4.2 KB of internal DRAM. It frees the transient
  4 KB heap stack plus TCB that each rollback used to take. Benchmain13 min_free was 88871. The expected value
  is about 84.6 K, far above the 8192 B floor (owner 2026-10-01). Peak usage during a rollback does not change,
  and it no longer depends on fragmentation. Still BENCH-PENDING per OR-08.
- **OW-07 INFO. Stubs are faithful enough.** `StackType_t` is `uint8_t`, which matches ESP-IDF
  `portSTACK_TYPE` (depth in bytes), so the 4096-entry array is 4096 B on target. `StaticTask_t` is an opaque
  host size, and `xTaskCreateStaticPinnedToCore` has the right signature and returns NULL when told to fail.
  `tskNO_AFFINITY` matches the old unpinned `xTaskCreate`. In `check_stack_margin_registration.ps1` the comment
  still says "liveness: on-demand". That is accurate because the worker only exists after the first POST. The
  registry test `test_ub01` correctly drops the exit-site row and adds a persistence scan.
