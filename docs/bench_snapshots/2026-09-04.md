## 7. Follow-up investigation (2026-09-04, later same day) — the two flagged anomalies

Both items below were re-examined by reading source (read-only on the
board itself, per that task's constraints) rather than guessing from this
snapshot's numbers alone.

### `frames_routed_nowhere: 1` — benign, identified

Counted in `uart_protocol.c`'s `handle_raw_frame()`
(firmware/KilnFW/App/drivers/owners/uart_protocol.c:230,242,282):
three distinct branches share this one counter — a stale ACK/NACK matching
no outstanding exchange, a BROADCAST addressed to an unregistered task
(fire-and-forget, no NACK, no retry), and a point-to-point DATA frame
addressed to an unregistered task (which DOES get NACKed, unlike the other
two).

`safety_link.c` (firmware/KilnFW/App/drivers/safety/safety_link.c:272-286) explains
why the BROADCAST/unregistered-task branch is the live candidate here:
SaftyFW's boot-time `FW_VERSION` push is unsolicited and sent as a
**4-copy burst** specifically because it "is still sent into a link that
has JUST come out of reset" and any single copy can lose the race against
this side registering its consumer task. The cmd histogram in both this
snapshot's and the follow-up's `safety_get_link_stats()` reads shows
exactly `fw_version=1` against tens of thousands of `status`/`power`/`diag`
frames — consistent with one copy of that 4-copy burst arriving before the
registration point and the remaining copies (one of which is all that's
needed) landing after it and being applied normally. `trip_event=0` in the
same histogram, and `frames_routed_nowhere` stayed pinned at exactly 1 as
the link's other counters climbed by ~1,500 frames during the follow-up's
own read (52,084 deframed vs. 50,511 at the original snapshot) — a single
startup-transient event, not an ongoing loss.

**Verdict: benign.** This is the boot-time-frame-before-consumer-registered
candidate, and it is not a TRIP_EVENT or any safety-relevant frame type —
the burst-of-4 design exists precisely so losing one copy has no effect.
The device log kept on the board does not currently retain far enough back
to show the actual boot (its ring buffer only reached back to uptime
~14,209 s against an already-then ~16,852 s / ~4h40m uptime), so this is
inferred from the counter/histogram arithmetic and the burst design in
safety_link.c's own comments, not from a boot-time log line — but the
inference does not depend on the log and is not weakened by its absence.

### Two LOW stack margins — not yet cleared; the existing "no deep call chain" note is inaccurate

`firmware/KilnFW/App/test/baselines/stack_margin_idle_2bcdc2d_20260904T215500Z.json`
already recorded both tasks as LOW at this same commit (`system_uart_bridge`
900 B/3072 B, `telemetry_log` 1064 B/4096 B — close to, not identical to,
this snapshot's live re-read, both consistent with a growing/idle-boot
high-water mark). `tools/check_stack_margin_baseline.py`'s
`KNOWN_LOW_ALLOWLIST` (lines 68-79) allowlists both explicitly as
**"not yet investigated"**, and its comment characterizes them as "plain
UART framing and ring-buffer writers" with "no known deep call chain."
Reading the actual call paths shows that characterization is not accurate
for either task, and — more importantly — that the idle-only capture this
baseline is built from cannot have exercised either task's deepest branch:

- **`system_uart_bridge`** (firmware/KilnFW/App/drivers/bridge/uart_bridge_system.c:47-138,
  3072 B stack): every subcommand except one is a few shallow locals and a
  direct reply. `SYSTEM_CMD_FACTORY_RESET`
  (uart_bridge_system.c:74-91) calls `factory_reset_execute()` →
  `execute_scope()` (firmware/KilnFW/App/drivers/http/factory_reset.c:145-151,101-139),
  which calls `profiles_builtin_restore_all()` and, for each partition in
  scope, ESP-IDF's `nvs_flash_erase_partition()` — a library call whose
  own internal stack usage this codebase does not control or have measured
  here. This bench has been idle the whole capture (no firing, no config
  write, read-only per task constraints), so `SYSTEM_CMD_FACTORY_RESET` has
  almost certainly never run this boot — the recorded 884-900 B free is the
  high-water mark of the OTHER, shallower subcommands only, not of the one
  branch that reaches into NVS partition erasure.
- **`telemetry_log`** (firmware/KilnFW/App/drivers/persist/telemetry_log.c:134-274,
  4096 B stack, PSRAM-backed): the poll loop keeps a 320-byte `line` buffer
  (`TELEMETRY_LOG_LINE_BUF`, telemetry_log.c:68) on its own stack and, only
  while a firing or a tune is actually active/reaching its DONE state,
  calls `telemetry_format_firing()`/`telemetry_format_autotune()`
  (firmware/KilnFW/App/drivers/persist/telemetry_format.c:40-113+), each of which
  builds that line through several chained `snprintf()` calls with `%.2f`/
  `%.3f`/`%.4f` float conversions per active zone — including, on
  `AUTOTUNE_ENGINE_DONE` with a valid step model, the longest format string
  in the file (telemetry_format.c:107-113). This snapshot's own
  `adaptive_tune_get_status()` read showed `observations=0` for all zones
  this boot, and `io_read`/`profiles_exec_status` showed no firing running
  — so neither the multi-zone firing line nor the autotune-DONE line has
  been formatted this boot, meaning the float-snprintf call depth (deeper
  than this task's other branches, which only call `ESP_LOGI`/
  `event_log_emit` with short fixed strings) is also unmeasured by the
  recorded high-water mark.

**Verdict: not established as benign or as at-risk — genuinely unmeasured.**
Both tasks are below the 30% LOW cut point on a reading taken while their
single deepest branch (NVS erase for one, multi-zone float-formatted
telemetry / autotune-DONE model dump for the other) was never exercised, so
the checked-in baseline is a floor, not the worst case, exactly as
`check_stack_margin_baseline.py`'s own docstring says an idle-only capture
is. Neither showed signs of actual overflow (no crash, no corrupted
neighbor, no missing stack-margin registration) at either read. No stack
size was changed as part of this investigation, per task constraints; the
concrete next step is a fresh `get_stack_margin()` read taken once during an
active multi-zone firing with a completed step-method autotune in the same
boot (covering `telemetry_log`'s worst branch) and once immediately after a
`SYSTEM_CMD_FACTORY_RESET` (covering `system_uart_bridge`'s), before
`KNOWN_LOW_ALLOWLIST`'s "not yet investigated" comment is closed out or
either stack size is resized — that measurement and any resulting resize is
its own reviewed firmware change, not done here.
