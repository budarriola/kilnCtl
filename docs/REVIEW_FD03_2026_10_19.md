# Review: FD-03 boot history ring (2026-10-19)

Scope: code commit e7816dadf, KNOWN_ISSUES row a9ddf82cc (origin/dev). Code review only, no target build or bench run.

Counts: **HIGH 0, MED 0, LOW 3, INFO 7**

## LOW

- **BH-01** `boot_history_reason_name()` table stops at EFUSE (13). `hal_reset_reason_t` also has `HAL_RESET_PWR_GLITCH` (14) and `HAL_RESET_CPU_LOCKUP` (15), so both appear as `UNKNOWN` in the JSON, the web table and the LCD. The stored byte is correct; only the name is lost. No test or static assert ties the table length to the enum. Fix: add the two names and a `_Static_assert` on `HAL_RESET_CPU_LOCKUP + 1`.
- **BH-02** `wall_time` is always 0. `main_record_boot_history()` passes `0u` and nothing fills it in later, so every row's "Time" column reads `unknown` and the JSON `time` field is dead until FD-04. Documented in the FD-03 row. Either backfill the newest entry after SNTP sync (one extra write per boot, opt-in) or drop the column until FD-04 lands.
- **BH-03** LCD Crash Report subpage, 320x480 no-scroll rule: the page now holds the wrapping summary label, a new six-line `LV_LABEL_LONG_WRAP` resets label (header plus 5 rows of up to about 36 chars) and the ack row. Whether this fits without scrolling, with a long crash summary, has not been checked on a target or by camera (the FD-03 row says so). Needs a bench capture with a crash record present before this is closed.

## INFO

- **NVS readiness / boot order:** `boot_history_record_boot()` calls `hal_kv_init_partition("kiln_nvs")`, which is idempotent and handles erase-and-retry, so NVS is ready. The call follows `crash_report_init()`, so the RTC beacon snapshot (`crash_report_prev_boot_uptime`) is valid. Failures are logged and never fail app_main.
- **Boot loop / wear:** exactly one 524 B blob write and commit per boot (no heartbeat). In a fast boot loop this is one blob rewrite (about 17 NVS entries, about 7 rewrites per 4 KB page) per reset on the shared kiln_nvs partition. The rate is bounded by the boot rate and matches the 1-write-per-boot spec. An optional improvement is to stop writing after N identical consecutive entries.
- **Load errors reset the ring:** any load failure (missing, corrupt, wrong size, wrong version, or a read-only open error) gives a fresh ring that the next write persists over the old blob. This is correct for corrupt or first-boot data. A transient read failure would also discard history, but that is unlikely at boot.
- **Wrap / CRC:** head/count/next_seq arithmetic is correct (newest = head-1, capped at 16, seq skips 0 on wrap). The CRC is computed over the blob with crc32 zeroed, and validation also checks version, count, head and next_seq != 0. Tests cover first boot, wrap (seq 6..21), CRC mismatch, wrong size and a bad head.
- **RAM/stack:** the JSON buffer (4096) and the ring copy (524) are both SPIRAM heap allocations, freed on every path. httpd_worker stack growth is only about 100 B (entry 32 B, fw_esc 27 B, locals), well inside 3152 B free. Worst-case body: 16 rows at about 175 B (about 2.8 KB) plus the crash record with 16 backtrace PCs (about 0.8 KB) stays under 4096; overflow returns 500 and does not truncate. app_main gets a 524 B blob and a 228 B record in a noinline helper frame. The 5-entry RAM cache costs 160 B BSS internal. The LVGL task reads only the RAM cache (no NVS); it is written once in app_main before the UI starts.
- **Auth / secrets:** `/api/crash_report` GET stays `ROUTE_TIER_ADMIN` in route_tier_table.h. The fields are reason, uptime, dump_id and a short firmware hash that is filtered to `[A-Za-z0-9._-]`. It is JSON-escaped server-side and `kcEscapeHtml`'d in the page, so no secrets or injection. A factory reset erases kiln_nvs and so the history; that is acceptable.
- **Tests:** not vacuous. They exercise the real boot_history.c over fake_kv, and test_diagnostics_http asserts exact row text from the real handler. The FD-03 row reports negtest 7/7 CAUGHT. That was not re-run here.
