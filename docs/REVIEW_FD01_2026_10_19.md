# REVIEW_FD01_2026_10_19: FD-01 support bundle

Scope: origin/dev at f817f21ca. Files: `drivers/http/diag_bundle.{c,h}`, `diag_bundle_http.{c,h}`,
GET /api/diag/bundle (ADMIN), `tools/PcTools/src/kilnctrl/diag_bundle.py`, MCP `diag_bundle_fetch`,
tests `App/test/test_diag_bundle.c` and `tools/PcTools/tests/test_diag_bundle.py`.
Review only, no code changed. KNOWN_ISSUES rows use prefix **DB**.

**Counts: HIGH 0, MED 4, LOW 6, INFO 5.**

## MED

**DB-01 MED: stack depth on the httpd worker (3152 B free).** `diag_bundle_run()` keeps `char json[1536]`
(DIAG_JSON_MAX) on the stack for the whole run. Every producer runs below that frame.
- The firing and autotune paths add `stream_log` -> `log_store_reader_next` (64 B scratch) -> `reader_open_current`
  (`char path[600]`) -> `fopen`/`fread` through VFS and LittleFS (about 1 KB or more).
- `sec_ota_record` adds `ota_record_t`, about 330 B of escape buffers and `json[512]`.
- `sec_crash_report` adds the record and its escape buffers.

The existing log handlers already reach the reader and VFS depth, so the 1536 B frame is new depth on top of
the measured 3152 B margin. That probably fits, but only by a few hundred bytes, and nobody has measured it.
Fix: allocate the manifest and trailer JSON in PSRAM. Then measure the httpd stack high-water on target with
a bundle run that has a coredump and full logs present.

**DB-02 MED: the coredump puts secrets into a file people share.** sdkconfig has
`CONFIG_ESP_COREDUMP_CAPTURE_DRAM=y`, so the dump holds DRAM .data/.bss and task stacks. That can include the
Wi-Fi STA/AP PSK (driver config and the provisioning statics), live session tokens, the password-hash and
lockout tables, and TOTP state held in RAM. An admin can already read the same bytes from
`/api/coredump/chunk`, so the device admin gains no new exposure. But a "support bundle" is made to be
emailed or attached. Session tokens stop working after a reboot. The PSK keeps working.
Recommendation (owner decision), one of:
- (a) Make the coredump opt-in (`?coredump=1`, PC flag `--include-coredump`).
- (b) Keep it, have `diag_bundle_fetch` write `SECRETS_WARNING.txt` and print a warning, and add a manifest
  field `"contains_ram_dump":true`.
- Accept it as admin-only.

Whichever is chosen, fix the header. The SECRETS paragraph in diag_bundle.h is false for the coredump section.

**DB-03 MED: path traversal in PC pc_supplement file names (Windows).** `_fetch_supplements` builds the file
name as `"supplement_" + path.strip("/").replace("/", "_") + ".json"` from the manifest. It replaces only `/`.
On Windows `\` is also a separator, so a manifest entry like `"/api/..\\..\\..\\Users\\x\\evil"` writes outside
out_dir. The device controls the manifest, and the MCP host runs on Windows. Frame names are safe, because
`_NAME_RE` allows no separators. Fix:
- Replace every character outside `[a-z0-9_.-]` with `_`.
- Assert `os.path.realpath(fp)` stays under `realpath(out_dir)`. Add the same check in `put()` as defence in depth.
- Add tests with backslash, `..` and absolute entries.

**DB-04 MED: a negative frame length hangs the PC parser.** `int(head[2])` accepts `-N`, `+N`, `1_0` and
padding. With `length = pos - nl - 2`, `end` lands on the previous frame's trailing `\n`. The terminator check
passes, and `pos = end + 1` equals the old pos. The parser loops forever and hangs the MCP server or tool.
Fix: require `^[0-9]{1,10}$`, require `pos` to advance strictly, cap the length at the data remaining, and
add a test.

## LOW

**DB-05 LOW: the httpd worker is blocked for the whole transfer.** One handler streams the whole coredump
(DRAM capture, tens to hundreds of KB) and both logs, in 1 KB chunks, on the single httpd task. Every other
request waits, and a stalled client can hold each chunk for up to send_wait_timeout. This is acceptable
for a rare ADMIN action but should be documented. Options: an async handler on a PSRAM-stack worker, or a
cap on total time.

**DB-06 LOW: boot_history and trip_history are NOT in the bundle.** `sec_crash_report` serializes only
`crash_report_record_t`, and it also drops `reset_reason` and `exc_a0/a1`. Only `/api/crash_report` in
diagnostics_http.c appends `boot_history` (FD-03) and `trip_history` (FD-05). That route is not in
`DIAG_BUNDLE_PC_SUPPLEMENT_JSON`, so neither array reaches the bundle by any path. Fix: add `/api/crash_report`
to pc_supplement, or add the two arrays as sections. Also include reset_reason.

**DB-07 LOW: a section name can overwrite the tool's own files.** A section named `manifest` or `trailer`
overwrites manifest.json or trailer.json. A section named `supplement_api_status` gets overwritten by the
supplement fetch, and `coredump.symbolize` collides too. Fix: write sections under `sections/` or with a
fixed prefix, and reject names that start with `.`.

**DB-08 LOW: the parser accepts structurally wrong bundles.**
- It does not require the manifest first or the trailer last. Frames after the trailer and duplicate
  manifests are accepted.
- It does not compare the trailer's per-section `bytes` with the bytes received.
- JSONDecodeError escapes instead of being raised as BundleError.
- `resp.read()` has no size limit.
- A truncation in the middle of a frame raises and throws away all partial data. INCOMPLETE.txt is written
  only when the cut falls on a frame boundary.

Fix: enforce the frame order, check the byte counts, wrap the JSON errors, cap the size, and on a partial
transfer unpack whatever parsed and mark it INCOMPLETE.

**DB-09 LOW: weak tests.**
- (a) The secret pin scans the words in diag_bundle_http.c. It cannot see what the coredump section emits,
  which is all of DRAM, so it stays green while secrets ship (DB-02). It also ignores callees and headers.
  Reword its claim, or pin the coredump decision explicitly.
- (b) No host test compiles diag_bundle_http.c. These are all untested: stream_log coalescing at the 1 KB
  boundary, coredump chunk offsets and the last partial chunk, the http_sink 1 KB flush, and the abort path
  that sends no terminating chunk.
- (c) The PC tests cover none of DB-03, DB-04, DB-07 or DB-08.
- (d) Fault injection fails only at sink call 5. A failure inside a multi-frame section is not covered.

**DB-10 LOW: log reads take no lock while appends and rotation run.** `log_store_reader_open` copies
`s_state[kind]` without a lock, and it opens segments while appends or rotation may be running. This was
already true of the existing log export, and it fails safely: a missing segment is skipped, and a short
record ends that segment.

Flash contention is small. Coredump reads are 2 KB partition reads and LittleFS reads are small. No lock is
held across `httpd_resp_send_chunk`, so the flash worker waits for at most one read, never for the network.

## INFO

- **DB-11** Client disconnect: `httpd_resp_send_chunk` fails and the error stays set in `sink_err`. Producers
  stop at their next emit, the buffers are freed, and no terminating chunk is sent. Correct.
- **DB-12** Auth: ROUTE_TIER_ADMIN, the same tier as /api/coredump/chunk and /api/crash_report. The response
  sends `Cache-Control: no-store` with an attachment disposition. Correct.
- **DB-13** Memory: every bundle buffer is in PSRAM (1 KB sink, 1 KB+64 log, 1 KB crash JSON, 2 KB core) and
  is freed on every path. No effect on the internal-RAM floor.
- **DB-14** The raw firing and autotune logs are 32 B event records with no credentials. build, boot_guard,
  ota_record and crash_report hold no secrets.
- **DB-15** A producer failure is recorded in the trailer and the run continues. A transport failure stops
  the run with no trailer, and the PC reports that as INCOMPLETE. This matches the design.
