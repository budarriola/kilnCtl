# Review: FD-05 Pico trip history (f8e684ba4), 2026-10-19

Scope: drivers/persist/trip_history.{c,h}, safety_link_frames.c hook, telemetry_log.c flush,
diagnostics_http.c (`trip_history` in GET /api/crash_report, buffer 4096 -> 8192 B), diagnostics_page.html, tests.

Counts: **HIGH 0, MED 0, LOW 3, INFO 7**

## LOW
- **TH-01** Unvalidated wire floats can overflow the 8192 B crash_report buffer. `safety_tc_c` and `threshold`
  come straight from the TRIP_EVENT frame and are printed with `%.1f`. A garbage/huge float prints up to ~40
  chars; 16 such rows (~4.2 KB) + 16 boot rows (~3.2 KB) + the crash record (~1 KB) exceed 8192, and the whole
  route returns 500, hiding the crash record too. Fix: clamp/`isfinite` the floats at note time (or print
  `null`), or let the trip array truncate instead of failing the response.
- **TH-02** A failed NVS write drops the batch. In `trip_history_flush()` the tail advances whenever
  `flash_hop_run()` returned ESP_OK, even if `flush_job` set `recorded = 0` after `hal_kv_open`, `set_blob` or `commit`
  failed (or `hal_kv_init_partition` failed). Only a hop refusal keeps the queue. This is documented in
  KNOWN_ISSUES FD-05 but has no test, and a transient NVS failure loses the trip for good. Fix: keep the tail
  on a write failure (the dedupe makes the retry idempotent), and add a test with a fake_kv write fault.
- **TH-03** `trip_history_dropped()` is never shown. Nothing reports the overflow counter (route, LCD, log), so a
  lost trip cannot be seen. Fix: add `trip_history_dropped` to the crash_report JSON.

## INFO
- **TH-04** Locking: the queue is a lock-free SPSC ring. The one producer is safety_poll (safety_apply_trip_event via
  safety_link_inbox.c), and the one consumer is telemetry_log. The note runs after `safety_unlock(link)`, and no lock
  is held across producers or across the flash hop. The indices are `volatile` with no explicit barrier. GCC on
  Xtensa emits `memw` for volatile accesses, so the slot write is ordered before the head publish. That holds, but it
  is implicit. A `__atomic_store_n(..., __ATOMIC_RELEASE)` would document it.
- **TH-05** RX context: there is no allocation and no flash. The new calls are `esp_timer_get_time`, `time_sync_get_status`
  (a short critical section, then `time(NULL)`) and `boot_history_recent` (a memcpy of a RAM copy written once at
  boot). The safety_poll stack (8192 B, PSRAM) gains about 200 B of frame (a 160 B boot copy plus a 36 B entry).
  Stack margins have not been measured on target.
- **TH-06** Safety behaviour is unchanged. The hook only runs when `is_new_event` is true, after every cached
  trip field is set and the lock is released. It does not change any return value or trip decision.
- **TH-07** Dedupe: the key (Pico trip_seq, reason, Pico uptime at trip) correctly suppresses the resend after an ESP
  reboot, where `is_new_event` is true again. It also records a Pico reboot that reuses trip_seq, because the uptime
  differs. A trip evicted from the ring (more than 16 newer trips) and then resent would be recorded again. That is
  benign: the Pico latches, so only the newest trip is ever resent.
- **TH-08** Flash wear: there is at most one 588 B blob write per new trip, at most one per second (the telemetry
  tick), and none for duplicates. A new trip needs a clear on the Pico, so a trip storm is bounded by how fast trips
  are cleared. Queue overflow (more than 3 new trips within one tick, or a stalled worker) loses entries, which is
  counted but not shown (TH-03).
- **TH-09** Route, auth and httpd: no URI is added. /api/crash_report keeps its existing tier. The rows hold no
  secrets, only numbers. The 8192 B buffer and the 588 B ring are in PSRAM heap, and the httpd frame grows only
  by a 36 B entry. `trip_history_load` reads NVS on httpd, which matches the existing boot_history pattern. The
  page builds `innerHTML` from numeric fields only.
- **TH-10** Tests are not vacuous. They cover the dedupe write-trap, a CRC/head/count/version/short-blob corruption,
  wrap eviction, queue bound plus hop refusal and retry, note-once wiring on resend, and the JSON rows. Two gaps: the
  write-failure path (TH-02) and the overflow-size path (TH-01). No negtest evidence was supplied with the commit.
