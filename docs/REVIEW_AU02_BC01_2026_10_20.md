# Review: AU-02 / AU-01 and BC-01 (2026-10-20)

Static review of origin/dev commits 55e41f09d and 3b73b7bf6 (AU-02 / AU-01, `web_auth_store_load_policy`) and 96b02712e (BC-01). No code was changed and the board was not used.

Totals: HIGH 1, MED 1, LOW 5, INFO 2.

## AU-02 / AU-01

### RV-01 HIGH: first setup (and every credential set with no policy record) locks the web out
- Where: `firmware/KilnFW/App/drivers/persist/web_auth_store.c:1009`. Related: `drivers/http/setup_wizard_page.html:1544`, `drivers/net/security_page.html:452`, `drivers/http/http_session_iface.c:278`, `drivers/ui/lcd_credential_bridge.c:39`.
- Problem: `web_auth_store_set_password` never writes a policy record. Both the setup wizard and the Security page send `cmd=set_web_password` first and `cmd=set_policy` second. On a never-provisioned board the first POST succeeds while auth is still off (the board is open). From then on, `load_policy` sees an admin credential with no policy and no marker, so it returns UNREADABLE. That causes three things:
  - Web auth is effectively on.
  - `resolve_timeout_s()` reports unreadable, so every session resolves to ROLE_NONE. Even a correct admin login cannot get past an ADMIN-tier route.
  - The admin is configured, so bootstrap is closed.

  The `set_policy` POST that follows is therefore refused, and the board stays on dashboards only. The LCD lock also becomes effectively on, with no PIN set and no banner (see RV-04). The LCD reset gesture puts the board back to never-provisioned (ABSENT, open), but the same wizard order locks it again, so the user goes round in a loop. A field board that has passwords set but never enabled auth (no policy record) gets the same lockout on its first boot of this firmware.

  So the answer to "can a never-provisioned board still reach first setup in AP mode?" is: it can reach setup, but it cannot finish it.
- Fix: when `load_policy` is ABSENT, store a both-off policy record in the same operation as the first credential, before the credential itself (in `web_auth_store_set_password`, or in `web_auth_backend_set_web_password`). Then "credential present, policy absent" can only mean the policy was lost. Field boards already in that state need a one-time boot migration that writes a both-off policy, or a recorded owner decision that pre-release boards are re-provisioned. Add a host test that drives set_web_password and then set_policy through the security route on a fresh store.

### RV-02 MED: the test-helper change in test_web_auth_login_http.c hid RV-01
- Where: `firmware/KilnFW/App/test/test_web_auth_login_http.c:356` and `:760`.
- Problem: `set_admin_credential` and `set_user_credential` now always store a `web_enabled=true` policy. These helpers had to change because a credential without a policy now makes every session resolve to NONE, and that is exactly the production behaviour behind RV-01. After the change, no test stores a credential on a store with no policy and then goes through login or session resolution, and no test follows the real wizard or Security-page write order.
- Fix: keep the helpers, but add explicit tests for two cases:
  - Fresh store, then set_web_password, then set_policy: expect OK and a usable admin session.
  - Credential with policy and marker lost: expect dashboards only and a defined recovery path.

  Negtest both with `tools/negtest.ps1`.

### RV-03 LOW: if only a USER credential exists and the policy is lost, open admin bootstrap is reachable
- Where: `web_auth_store.c:1009` with `http_auth_policy_iface.c:32`.
- Problem: this case returns UNREADABLE, so web auth is effectively on. `web_auth_store_admin_configured_or_unreadable()` is false, so bootstrap is needed, and any unauthenticated caller can claim the administrator account. This is no more open than before the fix (ABSENT used to mean fully open), but the comment calls this case "fails closed", and that overstates it.
- Fix: correct the comment. Alternatively, while the AU-02 state holds, require the LCD reset gesture (the `must_change` blob) before bootstrap, the same way RT-01 gates the latched FS-02 case.

### RV-04 LOW: in the AU-02 state the LCD locks with no banner
- Where: `web_auth_store.c` `lcd_pin_pending_refresh()` (about line 918) and `lcd_credential_bridge.c:41`.
- Problem: an UNREADABLE policy turns the LCD lock on. The pending-PIN banner only reads the raw policy blob, which is absent in this state, so a board with no LCD PIN locks the panel and shows no reason.
- Fix: show a banner when `load_policy` returns UNREADABLE while the storage-reset latch is clear. For example: "AUTH: login policy lost; admin log in and save security settings". This becomes useful once RV-01 makes that admin login work.

Paths checked with no new finding:
- Factory reset: erases `kiln_auth`, so FS-02 handles it as before.
- `clear_credentials`: the policy record is kept, so bootstrap stays reachable.
- Backup restore: does not touch `kiln_auth`.
- FS-02 latch and `storage_reset_resolve`: write the policy themselves.
- Physical reset gesture with the policy intact: the `must_change` blob reopens bootstrap.

## BC-01

### RV-05 LOW: `_wait_boot_soak` is defined twice
- Where: `tools/PcTools/src/kilnctrl/mcp_server_debug.py:532` and `:543`.
- Problem: the two definitions are identical copy-paste, and the second one silently shadows the first.
- Fix: delete one of them.

### RV-06 LOW: debug_reset sleeps before its refusals, and also in mode="halt"
- Where: `mcp_server_debug.py:432` (wait), then `:433` (dark-rereset guard).
- Problem: the soak wait (up to 35 s) runs before the dark-rereset refusal and before mode validation. A call that will be refused sleeps first. For `mode="halt"`, often used to catch a misbehaving core, the halt is delayed by up to 35 s.
- Fix: move the wait after all refusals, and skip it for `mode="halt"` (or only do it for `mode="run"`).

### RV-07 LOW: the soak wait does not re-check uptime after sleeping and has no cap
- Where: `tools/PcTools/src/kilnctrl/reset_probe.py:381-387`.
- Problem: it reads uptime once, sleeps `need`, then returns, even if the board rebooted during the sleep, in which case the reset still lands on a young boot. `sleep(need)` is outside the try, and a non-finite `uptime_s` value would raise there (the docstring says the function never raises). `need` is not clamped to `target_s`. The firmware sends `uptime_s` as `%lu`, so `need` cannot actually go above 35 s today.
- Fix: clamp `need` to `[0, target_s]`, reject non-finite values, and re-read uptime once after the sleep, returning a note if it went down.

### RV-08 INFO: behaviour in the edge cases asked about is acceptable
- Recovery mode: the recovery image has no `/api/status` (only `KilnFW/App/drivers/http/dashboard_http.c` serves it). The 404 becomes a note and there is no wait. That is correct, because recovery boots are not soak-confirmed.
- Unreachable board: costs host resolution plus a 3 s GET timeout, then a note. Nothing hangs.
- Pico peer: the wait is skipped.
- Auth-gated `/api/status`: it goes through `http_auth.urlopen`; a 401 becomes a note and the reset is not blocked.
- Callers: no in-repo caller passes peer="esp" or `sw_reset_esp`. The bench scripts only use `debug_reset(peer="pico")`. The worst case is one 35 s sleep per call.

### RV-09 INFO: the `MAIN_OTA_CONFIRM_WARN_MS` change is correct
- Where: `firmware/KilnFW/App/main_network_http.c:155`.
- Finding: it is now `BOOT_CONFIRM_SOAK_MS + 15000` = 45 s. `boot_guard.h` is included at line 26. The value only controls when the one-shot warning log fires (line 312) and gates nothing, so there is no behaviour risk.
