Owner requirement, verbatim: *"The esp should always in the real fw check the pico version on boot and update it if needed automatically"*. Read precisely: **"the real fw" is the application image**, explicitly not the recovery image, which by the same day's decision carries no Pico firmware and no safety link at all (`docs/OTA_SINGLE_SLOT_PLAN.md:110`); **"always on boot"** is unconditional in the application boot path; **"automatically"** means no operator action.

## 0. The tradeoff, stated first

Today a Pico update is an operator action: somebody uploads a `SaftyFW` binary to `POST /api/ota/pico`, which stages it and starts the relay (`firmware/KilnFW/App/drivers/http/ota_http_pico.c:69`). After this change the ESP application carries the Pico image it expects, compares it against what the Pico reports at boot, and reflashes the Pico on its own when they differ.

What that buys: the two processors can never sit at mismatched builds without someone noticing, and nobody has to remember to update the safety processor after an ESP OTA.

What it costs, and this is the whole of the cost: **the ESP now reprograms, unattended, the one processor whose entire purpose is to be an independent second opinion.** Every mitigation below exists for that single sentence. Two consequences are accepted deliberately rather than engineered around:

1. **A boot that decides an update is needed is a boot that cannot fire.** The kiln is unavailable for the update window and, if the update fails, until somebody repairs it at the bench. That is the wanted direction — a Pico of unknown state with heaters available is never acceptable, an unfirable kiln always is.
2. **The ESP application image and the Pico image become one versioned unit.** Rolling the ESP application back rolls the Pico back with it. See §8 (Q7); this is chosen, not overlooked.

> **CORRECTION 2026-09-18 — the embed proposal below is not implementable in this tree, and was not implemented.** *(Superseded above, 2026-09-20 — kept verbatim as the evidence record it always was.)* Evidence, in the order it decides the question:
> **Slot-selection / position-dependent-image hazard, recorded for the boot-time wiring (§9 step 5) to account for:** the two slot images are NOT interchangeable — each is linked for its own slot's base address (position-dependent code), so the ESP relaying `SaftyFW_slotA.bin` into slot B's flash region (or vice versa) produces an image that boots to garbage rather than failing a checksum cleanly at the wrong address space. The boot-time decision logic must select the embedded image matching the *target* slot (the slot NOT currently active, per the two-slot bootloader's normal A/B convention), never assume "the" embedded image. This is a new correctness requirement, not present in the 2026-09-18 manifest design (which staged exactly one image with no slot ambiguity), and is the reason the bench harness TODO in `kilnlink_capture.py` anticipates a distinct "image not linked for target slot" failure enumerator from the firmware side.
>
>
> 1. **The ESP build cannot produce a `SaftyFW` binary.** `KilnFW` builds under ESP-IDF/CMake with `xtensa-esp-elf`; `SaftyFW` builds under the pico-sdk with `arm-none-eabi-gcc`. Neither build can invoke the other, so an embedded image would have to be a **checked-in prebuilt artifact**.
> 2. **No such artifact existed, or could, as a committed one, at the time of this correction.** `pico_add_extra_outputs(SaftyFW)` is deliberately disabled (`firmware/SaftyFW/CMakeLists.txt`), because picotool has no prebuilt binary for this pico-sdk version and building it needs a host compiler this machine lacks, so no `.uf2` is produced. (As of the 2026-09-20 re-adoption note below, the build's POST_BUILD step does emit a plain position-dependent `.bin` per slot straight from the linked `.elf` via `${CMAKE_OBJCOPY} -O binary`, which needs nothing picotool-specific — this correction's original claim that "the build emits only `.elf`, never `.bin`" no longer holds.) And `firmware/SaftyFW/.gitignore:14` ignores `*.bin` (along with `.elf`/`.hex`/`.uf2`), so nothing of the sort is committable. Embedding would mean committing a gitignored blob that goes stale silently — the "MANUAL SYNC HAZARD" that file already names — which is why the re-adopted embed path consumes the `.bin` straight out of the build directory, never from git.
> 3. **§10.5's flash-budget concern is moot either way.** The `app` partition is `0x800000` (8 MiB) against a ~1.94 MB image, so there was never a size question to answer.
>
> **What was implemented instead (2026-09-18): the existing `pico_img` staging partition IS the image source, made durable.** `POST /api/ota/pico` already stages a full image there; it now also persists a read-back-verified manifest (length + CRC-32, `App/drivers/persist/pico_image_manifest.c`) so a later boot can identify and re-verify those bytes (`App/drivers/net/pico_image_source.c`, one pass: CRC-32 over the image while scanning it for the identity record of G2). This keeps the relay's single-reader contract and its partition lookup exactly as §1 records them, and adds no new writer to `pico_img` at all.
>
> **What this costs, stated honestly:** the feature is not "always armed out of the box" — a board that has never had an image staged has no expectation to compare against, so the boot check is **inert** on it (it logs and returns, it does NOT block). That is a deliberate deviation from §9 step 5's literal wording and it is the safe direction: calling `decide()` with no expectation resolves to `ABANDONED_NO_IMAGE`, which with step 6 live would permanently refuse firing on every board in the fleet. `ABANDONED_NO_IMAGE` keeps its real meaning — an image *was* staged and is unusable (fails CRC, or carries no identity record).

**Image source (closes G1) — RE-ADOPTED 2026-09-20, see the note directly above: embed BOTH `SaftyFW` slot images in the ESP application build (corrected — the body below used to say one slot, ~95 KB; see the 2026-09-20 note above for why it is two).** The build embeds the matching `SaftyFW_slotA` and `SaftyFW_slotB` binaries plus each one's length, CRC32 and a version string. At boot, when and only when an update is needed, the ESP copies the chosen slot's embedded bytes into `pico_img` and starts the existing relay unchanged. The relay keeps its single reader contract and its partition lookup; `pico_img` gains a second writer, which is the entire new write path.

Rejected alternative: teach the relay to read straight out of embedded `.rodata`. It saves one ~119 KB copy and a partition erase, and costs a change to the one module whose wire behaviour is exercised and recorded. Not worth it.

Cost: the ESP application grows by both Pico slot images, 238,616 B (two 119,308 B slot binaries) against today's ~2.7 MB `KilnCtrl.bin`. Irrelevant under the 8 MiB slot of `docs/OTA_SINGLE_SLOT_PLAN.md:22`, and a real constraint worth naming if that plan does not land first.

**The decision (closes G2): exact match on an identity string, not an ordering.** The build stamps the expected Pico identity — the `SaftyFW` commit the embedded image was built from — into the application. At boot the ESP compares it against the `commit` the Pico already reports (`firmware/CommonFW/include/kilnlink/kilnlink_fw_version.h:67`). Equal, and `dirty == 0`: nothing happens, no flash is touched, no counter moves. Unequal: update.

Why an exact match and not "newer than": there is no monotonic version number on the wire to compare, only a commit string; inventing an ordering means inventing a version field on both sides and trusting it. Exact match makes the ESP application and the Pico image one tested pair, which is also the answer to Q7. A `dirty` Pico build always mismatches, which is correct — a hand-built Pico is not a known state.

**Interlocks and a latched safety trip.** `ota_interlock_check()` (`App/drivers/net/ota_interlock.c`) does not check for a latched safety trip today, and this is deliberate rather than an oversight: a trip forces relays off (`ARMED` is a latch, see the safety-processor docs), so an update proceeding during one costs nothing a firing could exploit -- the failure mode this interlock set otherwise guards against (an update racing a live heater command) cannot occur while tripped. Not added to the interlock set.

**The trigger (closes G3): in the application boot path, after the link is up, before anything can fire.** Placed after `safety_link_start()` (`firmware/KilnFW/App/main_control_bringup.c:60`) so a version has actually arrived, and gated on `!ctx->recovery_mode` in the same style as the subsystem starts at `firmware/KilnFW/App/main_control_bringup.c:268`. In-application recovery mode is being deleted by the OTA plan; until then, not updating in it is the safe reading.

## 3. Q1 — the Pico is not guarding during the update

**Nothing is bypassed.** The link going quiet during a relay trips `SAFETY_FAULT_SRC_SAFETY_LINK`, and every relay-on path is blocked while it is asserted (`firmware/CommonFW/docs/UPDATE_PROTOCOL.md:105`). The Pico independently trips link-dead and holds K4 open. `safety_link_set_update_in_progress()` changes only which log line is emitted and does not touch the fault bit (`firmware/KilnFW/App/drivers/net/ota_pico_relay.h:68`). **This plan adds no update-mode carve-out to `relay_authority_on_blocked()` or anywhere else, and no relay is ever driven outside `kiln_io_owner`.**

So the heating block during the window is not new work — it is a property already there, and the work is to not break it. One thing is added: the boot-time updater calls the existing interlock check (`firmware/KilnFW/App/drivers/net/ota_interlock.h:240`) before starting, so it refuses rather than relying solely on the link-dead trip. Belt and braces, in that order.

Residual, inherited from `ota_interlock.h`'s own documented gap: a relay held on by a manual or rule-driven path with no profile running is not visible to the snapshot. At boot that state cannot exist yet, which is precisely why the boot path is the safest place this feature could live.

## 4. Q2 — never during a firing, and refusing to fire on an unrecoverable mismatch

An ESP reboot can land inside a live firing, so "we are in the boot path" is not by itself proof the kiln is idle.

**Rule: the updater runs before any firing may start or resume, and if a firing is running, paused, or resumable, it does not update at all.** Concretely: check for a running, paused or resumable profile *before* the profile executor is allowed to resume; if any exists, record "deferred: firing present" and return without touching flash. The next boot that comes up idle performs it.

**A version mismatch by itself still only defers — that half of Q2 is unchanged.** A mismatched Pico during a live firing is not by itself proof of an unsafe Pico, and blocking mid-schedule for a version string would strand a kiln on a cosmetic difference. The one exception already existed and is not changed: a config-divergence or link fault blocks heat on its own merits.

**What §10.3 changes is the *unrecoverable* case, decided 2026-09-16 as an OVERRIDE of this plan's original "defer only" recommendation: once the ESP has determined the mismatch cannot be fixed by itself, the kiln refuses to fire until the versions match — a hard interlock, not a warning.** "Unrecoverable" is a specific, decidable state, not "any mismatch": no staged `SaftyFW` image is available to attempt with (G1 unmet, or the embedded image itself is unusable); or an attempted update itself failed (§7, Q5) and left the Pico on its old firmware, still mismatched. In every one of those states an update is not "about to happen" — nothing further will change the mismatch on its own, so continuing to allow firing means running indefinitely on an unconfirmed safety processor. A live firing already in progress when the state is reached is not aborted by this rule (that would itself be a hazard); the block applies to the *next* start.

> **OWNER DECISION 2026-09-20, option (c) — budget-spent is no longer one of the blocking causes above.** A review of the embedded-image landing found that a board whose relay can never succeed (a bad cable, a wedged Pico bootloader, anything short of the image itself) burns its 3-attempt budget once and then latches a permanent structural refusal of every firing start, with no operator escape short of a bench SWD flash — worse than the status quo before this feature existed. Corrected: exhausting the attempt budget (`PICO_AUTO_UPDATE_ABANDONED_BUDGET_SPENT`) now logs at WARN and surfaces as a non-blocking `READY_CANNOT_YET` warning on `/readiness` (naming the attempt count and the embedded commit) instead of calling `pico_auto_update_state_set_blocking(true)` — the board keeps firing on whatever `SaftyFW` it already has, exactly the pre-feature status quo. The remaining unrecoverable causes are `ABANDONED_NO_IMAGE` and `ABANDONED_CHAIN_GAP`, and those still block: neither self-heals on its own, and neither is caused by a flaky relay retrying a perfectly good image against uncooperative hardware.
>
> **Follow-on, Opus review 2026-09-20 — `ABANDONED_PRIOR_FAILED` joined budget-spent as non-blocking too.** A separate defect meant this cause could be reached wrongly in the first place: `pico_auto_update_boot.c`'s relay-hand-off path was persisting a terminal failure (`pico_update_attempts_record_failure()`) whenever `ota_pico_relay_start()` returned false — an ESP-local failure (task-create, typically) that never touched the Pico at all, saying nothing about the Pico or the staged image. That call site is removed (the existing per-pair attempt budget above still bounds retries without it), and, since even a clean rebuild of that fix cannot un-persist a `prior_attempt_failed=true` already written to NVS by earlier firmware, `ABANDONED_PRIOR_FAILED` is now ALSO consumed with `pico_auto_update_state_set_warning()` rather than `set_blocking(true)` — same rationale as budget-spent: the only clear for either cause is a verified MATCH, which an abandoned pair can never attempt again to reach, so neither may be allowed to latch a permanent refusal. `ABANDONED_NO_IMAGE` and `ABANDONED_CHAIN_GAP` are the only two causes still blocking as of this note.

**Wiring, not a new gate shape.** `firmware/KilnFW/App/drivers/safety/readiness_gate.h` already implements exactly this pattern for five existing conditions — `recovery_mode`, `safety_trip`, `crash_report`, `estop_verified`, `safety_ceiling_match` (`READINESS_GATE_KEY_*`, `readiness_gate.h:95`-`99`) — each consumed by `profile_executor_run()` before anything else starts, with **no override of any kind** (`readiness_http.h:20`-`29`). A sixth key, e.g. `READINESS_GATE_KEY_PICO_UPDATE_UNRECOVERABLE`, is added the same way: the boot-time decision function's `abandoned`/`failed` outcome (§9 step 3) sets it, and `readiness_gate_check()` refuses every start path — `POST /api/profile_exec/start`, both LCD start buttons, and the benchproto `RUN` command — the same paths the existing five keys already refuse (`readiness_http.h:27`-`28`). `check_readiness_gate_display_agreement.ps1` and `test_readiness_gate.c` (named at `readiness_gate.h`'s header) extend to the new key with no new mechanism — `readiness_gate.h:105`-`106`'s comment holding the page and the interlock to "the same five keys" becomes six once this lands.

**Legibility — both surfaces, not just a log line.** The existing keys already render on `GET /readiness` / the page it backs (`readiness_http.h:12`) and are the same predicates the LCD start buttons consult before refusing, so the new key rides the existing plumbing: the web readiness page shows `pico_update_unrecoverable: READY_NOT_DONE` with the reason string the decision function attached (which of the three unrecoverable causes above applies), and the LCD start screen, which already reads the same gate to grey out its start button for the other keys, does the same for this one and shows the reason text rather than only refusing silently. This plan does not invent a new alarm channel (as this section already said); it uses the one every other safety condition already uses, so a blocked kiln reads as "blocked, and why" on both surfaces rather than as an unexplained dead kiln.

No web or LCD action clears the gate — it is cleared only by the Pico actually reaching a matching, verified version, which is the point. (Budget-spent, per the 2026-09-20 note above, no longer needs this path at all — it does not block firing; the same SWD escape still clears its warning and its counter once the Pico reports a match.)

## 5. Q3 — `abs_max_temp_c` equality, and the Pico never unarmed

**The favourable finding first: a Pico firmware update does not wipe its configuration.** The config store sits outside both application slots, and `flash_layout.h` says so in those words (`firmware/SaftyFW/bootloader/flash_layout.h:74`, offset at `:77`, slot A at `:70`, metadata at `:64`). `abs_max_temp_c` and the arming state survive an update by construction. On the bench board this is observable: `config_crc` matches live and S1 reads `abs_max_temp_c=80C ARMED` today.

So there is no restore to perform in the normal case, and the work is verification, not restoration:

1. After the Pico reboots into the new image, wait for `FW_VERSION` and compare `config_crc` against the value cached before the update (`firmware/KilnFW/App/drivers/safety/safety_cfg_store.h:222` — the CRC is the authority, never the cache).
2. Run the existing link-up ceiling reconcile (`firmware/KilnFW/App/drivers/safety/safety_ceiling_sync.h:114`) and the existing divergence check (`firmware/KilnFW/App/drivers/safety/config_divergence.c:134`). A mismatch is a fault: alarm and heaters disabled, exactly as today. No new policy.
3. Only if the config genuinely did not survive, write it back from the 68-param cache with confirm-by-read-back (`firmware/KilnFW/App/drivers/safety/safety_cfg_write.h:125`), **raising the Pico's ceiling first and only then the ESP's** (`firmware/KilnFW/App/drivers/safety/safety_ceiling_sync.h:60`, `:68`). The Pico's ceiling is never left tighter than the ESP's.

**The residual risk this plan originally deferred to a human, now closed by a project-wide policy decided the same day (§10.4, OVERRIDE):** the owner's requirement is not "warn and let a human fix it" but *"handle it automatically — find a way to carry the CT calibration."* The owner also settled, separately, a project-wide one-step-at-a-time config-migration policy that applies to both processors' versioned config stores (`docs/CONFIG_MIGRATION_CHAIN_PLAN.md`, referenced here and not edited, another session's plan): **every firmware that bumps its own config format version ships exactly one migration step — the step that carries the immediately preceding version forward to its own — and an older stored record is brought current by applying the steps between its version and the running firmware's in sequence, CRC-verified once against the blob's own claimed layout before the first step, never re-verified between steps. Migration is forward-only, with no downgrade path, and existing monolithic converters are not decomposed retroactively — the chain begins at the next version bump.** `config_store_unpack_ex()`'s v1 branch is already a correctly-shaped single step in this sense (`firmware/SaftyFW/src/config_store.h:62`-`75`); §6 below adopts extending this chain, not a new mechanism, as the way the CT normals are carried — and states the actual blocker `CONFIG_MIGRATION_CHAIN_PLAN.md` also identifies, which is not the migration shape.

## 6. Q4 — the Pico's CT normals, OVERRIDE 2026-09-16: carried automatically across a format bump

`i_normal_a[0..2]` are params `0x031A`–`0x031C` (decimal 794–796) in the Pico's own config store (`firmware/SaftyFW/src/config_params.c:128`-`130`, write path at `:496`-`498`, the required-mask bits at `config_store.h:357`-`359`). The owner's instruction, verbatim, was *"Handle it automatically. Find a way to carry the ct calibration."* — an OVERRIDE of this plan's original recommendation to exclude a format-version bump from automatic update. This section states the mechanism.

**Ground truth that shapes the answer: the config store sits physically outside both application slots** (`firmware/SaftyFW/bootloader/flash_layout.h:70` application slot, `:74`/`:77` config store). An ESP-driven reprogram of the Pico's *application* image — everything this feature's relay touches (§1's already-built transfer) — never writes the config sector at all, with or without a format bump. So the CT normals are never physically at risk from the update itself; the only way they end up "lost" is that the *new firmware*, on its first read of the still-present, old-format bytes, decides not to trust them.

**Mechanism adopted: in-place step migration inside the Pico's own config store, extending the chain `config_store_unpack_ex()` already has — not a link-based read-out/write-back from the ESP.** `docs/CONFIG_MIGRATION_CHAIN_PLAN.md` §2 ("The Pico half, and the CT normals") reaches the same conclusion independently and is more precise about the actual blocker, worth restating exactly rather than paraphrased: **the blocker is not the migration shape.** `config_store_unpack_ex()`'s v1 branch is already a correctly-shaped single step — it starts from `config_store_default()` and overlays exactly the fields v1 held, including the legacy `ct_cal` (`firmware/SaftyFW/src/config_store.c:757`, `unpack_ct_cal()` at `:354`-`356`). **The actual blocker is one line: `scratch.calibration_missing = true;` at `firmware/SaftyFW/src/config_store.c:763`, which the v1 branch sets unconditionally, with no path for any future step to leave it `false`.** No migration shape — in-place step or link-based read-out/write-back — can preserve `i_normal_a`'s effect on arming while that assignment is unconditional; carrying the raw floats forward is worthless if the flag that gates S14/S15 is hardcoded regardless.

So the mechanism has two parts, not one: (1) the step-chain shape itself, already 90% present per the v1 branch above, formalised into a table per the project-wide policy; and (2) **making `calibration_missing`/`fields_set` a per-step declaration instead of a blanket assertion** — each future step states which `fields_set` bits (including `CONFIG_STORE_SET_I_NORMAL_A_0/_1/_2`, `firmware/SaftyFW/src/config_store.h:357`-`359`) it carries forward, and sets `calibration_missing` true only if *that step's own* new fields have no safe default the migrated record cannot answer — recomputing `calibration_missing` as `!config_params_all_required_set(&rec)` (`firmware/SaftyFW/src/config_params.c:949`, invoked the same way a live commit already does per the comment at `:957`-`959`) is the honest way to state "nothing this step added is unanswered." `config_params_validate_ranges()` still runs on the migrated record regardless (existing behaviour, unchanged), so a carried-forward `i_normal_a` that fails range validation still invalidates the slot. Part (2) is the whole mechanism per `CONFIG_MIGRATION_CHAIN_PLAN.md` §2's own conclusion — without it, carrying the normals forward is impossible regardless of how the migration is shaped.

**Why not the ESP-side capture/replay this plan first considered** (read the 68 cached params via `safety_cfg_store.h:154`/`:162` before reprogramming, write them back after via `safety_cfg_write_apply_pairs()`/`safety_cfg_write_apply_package_and_confirm()`, `firmware/KilnFW/App/drivers/safety/safety_cfg_write.h:59`, `:125`, confirmed by read-back): it solves a problem that does not exist here. The config sector is untouched by the application reflash (previous paragraph), so there is nothing to "carry" across the link — the bytes never left the device. Using the SET_PARAM/COMMIT_CONFIG wire path as a migration mechanism would duplicate, with a second, externally-driven code path, work the firmware itself is already the sole owner of every time it changes its own on-flash format, and it fits the project-wide policy less well than the in-place step does: the policy places migration inside the firmware version that bumps the format, not bolted on by a tool that happens to be reprogramming that firmware at the time.

**Invariant this plan holds regardless of mechanism:** after the update completes, `calibration_missing` must read `false` and S14/S15 must be armed — the calibration demonstrably survived, not merely "structurally should have." **On this bench board `i_normal_a` is unset on all three channels today (`has_value: false`, S14/S15 render DORMANT)**, so the bench cannot itself prove the carry works — a v2→v3 migration step run against an all-defaults record proves nothing about a step run against a genuinely commissioned one. Proving it needs a record with `i_normal_a` actually set (a bench CT commissioning pass, or a synthetic v2 record built by `test/test_config_store.c`'s host harness with the bits set) put through the future step and checked both for the raw values and for `calibration_missing`/`config_params_all_required_set()` afterward — a host test, not a hardware run, and buildable now if the future step's shape is stubbed for it.

**The abort invariant, and where it has to live given migration is one-way.** The project-wide policy is explicit that migration has no downgrade path, and by the time a migration step runs the Pico has already rebooted into the new image — there is no "run the step, don't like the result, roll back" available to this feature. So the check that "an update which cannot demonstrably carry the calibration aborts and leaves the old image running" has to be a *pre-flight* gate on the ESP, before the relay starts, not a post-hoc undo: the decision function of §9 step 3 must know, from the embedded image's own build-time record of which format-version steps it ships (extend the identity stamped in §9 step 1 to also carry `CONFIG_STORE_FORMAT_VERSION` and the list of steps the image's `config_store.c` actually contains), whether every step between the running Pico's `config_version` and the target is present. If any step in that range is missing — a gap in the chain — the outcome is `abandoned`/deferred exactly like a spent attempt budget (§7), the relay never starts, and the Pico stays on its old, still-armed image. Only once the update completes does the ESP get a second, confirming check: after `FW_VERSION` and `config_crc` come back (§5 step 1), it also reads back `calibration_missing`/arming via the existing 68-param refetch (`safety_cfg_store.h:197`, `:222`) and the existing divergence check (`config_divergence.c:134`); a record that migrated but still reads `calibration_missing = true` where it did not before is a fault under that existing policy — alarm, heaters disabled — and, per §4's new gate, an unrecoverable mismatch that blocks the next firing until a human intervenes.

**Open question the code does not answer today:** there is no v2→v3 step yet, so nothing in the tree proves the recompute-rather-than-force approach above actually holds for whatever fields a real future bump adds — that step has to be written and host-tested (`test_config_store.c`) against the specific fields it introduces, and only that test can say whether *its* new fields are "safe to default" (recompute) or "must force `calibration_missing`" (some future field might have no safe default the way `abs_max_temp_c` does not, in which case forcing true for a *record missing only that field* is still correct, mirroring v1→v2 exactly). This plan states the policy and the pre-flight/post-hoc gate around it; it does not and cannot pre-write a migration step for a format version that does not exist yet.

## 7. Q5 and Q6 — a failed update, and a wrong decision, DECIDED (§10.2)

**Q5, failure.** The Pico's two-slot bootloader is why a failed relay is survivable: the image is written into the inactive slot and the metadata record is only flipped once the image verifies by read-back from flash. A transfer that dies mid-way leaves the previously-good slot still selected, so the Pico comes back on its old firmware and keeps guarding. A failure *after* the flip that will not boot leaves the Pico dead, the link dead, and K4 open — the kiln cannot heat. Both outcomes are acceptable; an unarmed Pico with heaters available is not reachable from either.

The ESP may retry, bounded as below. **The physical escape is `debug_program(peer="pico")` over the SWD probe**, which is a different path from this feature and is the recovery-of-last-resort already recorded in `firmware/CommonFW/docs/UPDATE_PROTOCOL.md` §5. This plan uses the ESP-driven link relay, never the host programmer; the host programmer is only how a human repairs a board that this feature broke. **A failed update is the third unrecoverable cause of §4/§10.3: once retries stop (whether from the budget below or an earlier abandon), the readiness gate refuses the next firing start until that same SWD path (or a restaged corrected image) produces a matching, verified Pico identity.**

**Q6, a wrong decision.** A version check that is wrong — a mis-stamped expected string, a Pico that reports a commit the ESP will never match — retries forever, and a RAM-only counter bounds nothing because it resets on the reboot the update itself causes. This exact shape bricked the board three times in the `boot_guard` area.

The bound, copying `boot_guard.c`'s hard-won mechanics rather than re-deriving them:

- A counter persisted in NVS, **keyed by the pair (expected identity, observed Pico identity)**, so a new mismatch gets its own fresh budget and a stuck one cannot ratchet.
- Every write read back before being reported as success, with one bounded erase-then-retry — `persist_count()` / `verify_persisted_count()` / `erase_then_persist_count()` (`firmware/KilnFW/App/drivers/persist/boot_guard.c:213`, `:313`, `:348`). **A bare `HAL_OK` from an NVS write is not evidence in this module's neighbourhood; 2026-09-08 proved the write can report success while the value never changed.**
- Budget: **3 attempts per pair, decided (§10.2).** On exhaustion the ESP stops attempting, reports "Pico update abandoned after 3 attempts", and leaves the Pico alone. **This is one of the three unrecoverable causes in §4/§10.3: exhaustion now also sets the readiness-gate key that refuses the next firing start, until a human clears it at the bench** — an OVERRIDE, decided the same day as the budget itself, of this section's original "does not refuse to fire on that ground alone."
- The counter clears only on a verified success, i.e. the Pico reporting the expected identity.

## 8. Q7 — downgrade and rollback, DECIDED (§10.1)

If the ESP application is rolled back to an image carrying an older embedded Pico image, the exact-match rule of §2 means **it will push that older image to the Pico.** That is the intended behaviour and the reason exact match was chosen: the pair was built and tested together, and a rolled-back ESP running against a Pico from a newer, now-rejected build is a combination nobody has exercised. Rolling back the ESP should roll back the whole controller.

Two guards keep it from becoming a loop. The per-pair counter of §7 bounds a downgrade exactly as it bounds an upgrade. And the compatibility floor (frame ids 0x00–0x0F, `firmware/CommonFW/include/kilnlink/kilnlink_fw_version.h:20`) guarantees that even a mismatched pair can still exchange versions, so the ESP can always see what it is talking to; where both need updating, `UPDATE_PROTOCOL.md` §4's existing rule is to update the ESP first, which this ordering follows for free.

The case this plan still does *not* cover, unaffected by §6's OVERRIDE: a downgrade across a `CONFIG_STORE_FORMAT_VERSION` bump, where the older `SaftyFW` refuses the newer config record outright (`firmware/SaftyFW/src/config_store.h:72`). §6 adopts *forward* in-place migration per the owner's project-wide policy, and that policy is explicit that migration is one-way with no downgrade path — so a downgrade across a format bump was never a candidate for the automatic carry §6 describes, and the pre-flight gate of §9 step 3 treats it exactly like any other missing step in the chain: `abandoned`, the relay never starts, and per §4/§10.3 the kiln refuses to fire until a human resolves it at the bench.

## 11. Bench-install feasibility verdict (2026-09-21, source-only review)

**NO-GO** for installing the two-slot bootloader on the bench Pico until three things resolve. No hardware touched for this review.

1. **Metadata sector seeding is unverified end to end.** Nothing PC-side writes an initial record to flash offset `0x00010000` (`BOOTLOADER_METADATA_FLASH_OFFSET`, `firmware/SaftyFW/bootloader/flash_layout.h:64`) before a first boot. `firmware/SaftyFW/test/test_bootloader_metadata.c:109-117` and `:160-164` confirm `bootloader_metadata_unpack()`/`_find_latest()` reject an all-0xFF erased sector rather than crashing, and `firmware/SaftyFW/bootloader/main.c:207-213` confirms the caller treats `BOOTLOADER_METADATA_NO_SLOT` as `enter_recovery()`, not a call into `bootloader_decide_boot()` with garbage. That path is sound as read, but nothing exercises it as one integrated sequence (fresh-erase -> boot -> recovery), and no tool seeds a real first record, so a from-scratch bench install has no confirmed path to slot A becoming active without a manual step not documented anywhere in this plan.
2. **Restore path after install is unverified.** Both the flat `SaftyFW.elf` and the bootloader itself link from XIP `0x10000000` (`flash_layout.h:17-18`, `:41` — "Bootloader region: written once over SWD, never updated in the field"). Once a bootloader is installed, whether `debug_program(peer="pico")` with the default flat ELF still boots correctly (or instead lands on top of the bootloader/metadata region and bricks it) is not verified in source or in any doc. Owner decision needed on the overlap and on what the sanctioned restore path is post-install.
3. **No atomic multi-image flash tool.** An install is three separate `debug_program(peer="pico", elf_path=...)` calls (bootloader, `SaftyFW_slotA`, optionally `SaftyFW_slotB`) with no post-write check tying metadata and slot CRCs together as one verified unit.

Positive findings, briefly: `firmware/SaftyFW/bootloader/main.c:13` drives GPIO6 low as its first statement, before anything else; the bootloader is bare-metal with no watchdog, so the erase-watchdog class does not apply; the manual-sync hazard between `BOOTLOADER_SLOT_A/B_FLASH_OFFSET`, `app_slot.ld.in`'s hardcoded FLASH length, and `flash_layout.h`'s macros is now enforced: `firmware/SaftyFW/tools/check_flash_layout_sync.cmake`, wired into the build as `add_custom_target(saftyfw_check_flash_layout_sync ALL ...)` in `firmware/SaftyFW/CMakeLists.txt` (~479-489), parses all three sources and fails loud with the specific mismatched numbers on every build, not just on reconfigure.

## 13. The embedded identity was keyed on repo HEAD, not SaftyFW's own inputs — FIXED 2026-09-21, revised in review rounds 2-3

**Bug, confirmed on the bench:** `pico_auto_update_identity_matches()` (`firmware/KilnFW/App/drivers/net/pico_auto_update.h:121`) decides "update needed" by comparing the commit string embedded in the ESP's staged SaftyFW slot images against the commit the running Pico reports, byte-for-byte. That embedded string came from `SAFTYFW_GIT_COMMIT`, which `firmware/SaftyFW/tools/gen_build_info.cmake` stamped from a plain `git rev-parse --short HEAD` of the **whole monorepo**. Since the repo is shared by KiCad hardware, KilnFW, SaftyFW, CommonFW and docs, that hash changes on every commit anywhere in the tree — including a KilnFW-only commit that touches nothing SaftyFW reads. Bench evidence: the embedded image was stamped `8ab3b81a` against a running Pico at `a57d0138`, while `git log a57d0138..8ab3b81a -- firmware/SaftyFW firmware/CommonFW firmware/hwAbstraction` was empty — the identical SaftyFW binary, restamped by unrelated KilnFW work, tried to reflash the Pico with a byte-for-byte copy of what it already had, on every ESP flash.

**Fix, landed this pass:** `gen_build_info.cmake` now stamps `SAFTYFW_GIT_COMMIT` from `git log -1 --format=%h -- firmware/SaftyFW firmware/CommonFW firmware/hwAbstraction/pico firmware/hwAbstraction/common firmware/hwAbstraction/interface` (the trees this build actually compiles from, links, or includes — `CMakeLists.txt`'s `add_subdirectory(${CMAKE_CURRENT_LIST_DIR}/../CommonFW kilnlink)`, its `add_library(hwabstraction_pico STATIC ...)` from `firmware/hwAbstraction/pico/*` + `firmware/hwAbstraction/common/hal_status.c`, and its `target_include_directories` pulling from `firmware/hwAbstraction/interface` are the only cross-tree dependencies; the pico-sdk/FreeRTOS-Kernel/toolchain inputs are external and not tracked by this repo's history at all), instead of repo-wide HEAD. The dirty-tree marker (`SAFTYFW_GIT_DIRTY`) is scoped to the same five paths too — round 1 had left it scoped to `firmware/SaftyFW` alone, which under-covered CommonFW/hwAbstraction edits; round 2 widened it to the whole `firmware/hwAbstraction` tree; round 3 narrowed it back to just the three subdirectories actually reached, matching the commit-stamp pathspec exactly. Bench-verified: rebuilding at `06ac13cd` stamped commit `22b080bd` (the last commit that had actually touched `firmware/SaftyFW`/`firmware/CommonFW`); a KilnFW-only dummy commit landed on top, moving HEAD to a new hash, and a forced full rebuild reproduced the identical `22b080bd` stamp — the dummy commit was then dropped (`git reset --soft` + hand-restore, never `git checkout --`) and the working tree is unchanged. Round 2 additionally verified with an hwAbstraction-only dummy commit: the stamp moved to the dummy commit's own hash (proving hwAbstraction edits are then seen). Round 3 re-verified both ways under the narrowed scope: a dummy commit touching only `firmware/hwAbstraction/interface/` moved the stamp (the narrowed subdirectories are still tracked), and a dummy commit touching only `firmware/hwAbstraction/host/` did NOT move the stamp (proving the narrowing actually excludes the unreached subtree) — both dummy commits were dropped the same way afterward.

**hwAbstraction is a real, separate input, not folded into CommonFW — but only three of its subdirectories reach the Pico image.** `firmware/SaftyFW/CMakeLists.txt:242-265` builds `hwabstraction_pico` as its own static library from `firmware/hwAbstraction/pico/*` and `firmware/hwAbstraction/common/hal_status.c`, links it into every SaftyFW target, and includes headers only from `firmware/hwAbstraction/interface` — a change under any of those three subdirectories (e.g. `5671ee03`, touching `firmware/hwAbstraction/interface/hal_barrier.h`, which `config_store_flash.c` includes) produces a different image with no change under `firmware/SaftyFW` or `firmware/CommonFW` at all. Round 1 of this fix missed this path entirely — an hwAbstraction-only commit landing after a SaftyFW rebuild would have produced a stale-but-matching stamp (the ESP would report MATCH against a Pico that needed no update, silently correct by luck, but for the wrong reason). Round 2 closed that gap by adding the whole `firmware/hwAbstraction` tree to all three copies of the pathspec, but that over-covered `esp/`, `host/`, `idf/`, `test/` and `README.md`, none of which reach the Pico image — of the last 62 hwAbstraction-only commits, 33 touched only those unreached paths, and each would have spuriously restamped `SAFTYFW_GIT_COMMIT` under round 2's scoping. `aa2c484d` is one such example: it touches only `firmware/hwAbstraction/host/fake_kv.c`/`.h`, not `interface/hal_barrier.h` — a commit that must NOT restamp under the round-3 narrowing, not a second example of one that should. Round 3 closed this by narrowing the pathspec in all three copies to just `firmware/hwAbstraction/pico`, `firmware/hwAbstraction/common`, `firmware/hwAbstraction/interface` (see below).

**Content hash vs. path-scoped commit — considered, path-scoped commit chosen.** A content hash of the built `.bin`/`.elf` was considered as the alternative identity source and rejected: this build is not reproducible byte-for-byte (`SAFTYFW_BUILD_DATE`/`SAFTYFW_BUILD_TIME` are baked into the image on every build, plus ordinary non-determinism from absolute paths and object ordering across separate `idf.py`/`ninja` invocations), so a content hash would report "different" between two builds of the *same* source and defeat the whole point of `pico_auto_update_identity_matches()` — every ESP flash would decide an update is needed even when SaftyFW itself hasn't changed, which is the identical bug this pass fixes, reintroduced through a different door. A git-commit identity is stable across rebuilds of unchanged source by construction; a content hash is not, given this tree's build setup.
