# Review: FS-02 login storage reset latch (2026-10-17)

Scope: origin/dev c9cbe11ca (code) and 165d659be (docs), with FS-01 (7166f4218, docs 7e702425b).
Owner decision: wiped auth storage on a board with surviving Wi-Fi credentials is a reset, not a fresh
board. Web stays dashboards only until an admin is set, LCD banner, readiness auth item.

Result: HIGH 0, MED 1, LOW 4, INFO 4. Host tests `-Only web_auth_store`: all 15 executables pass.

## Mechanism
`web_auth_store_storage_reset_evaluate()` runs in `main_boot_early.c` right after `wifi_prov_start()`
(both `nvs` and `wifi_nvs` are initialised there, before the HTTP server and LVGL start). If the `nvs` sentinel
`kiln_auth/nvs_seen` is missing, there is no policy record and no `auth_ever` marker, and the `wifi_nvs` mirror exists
(or `nvs` was auto-erased this boot and STA credentials survive), it latches. `load_policy()` then reads UNREADABLE
(effective enabled, admin unconfigured, so bootstrap is offered). Setting the admin web password runs
`storage_reset_resolve()`: enabled policy (marker first), then the `nvs` sentinel, then the mirror, then the latch clears.

## Bypass
None found. While the latch holds, every policy reader goes through `load_policy()`, so web auth is on.
`POST /api/security/policy` is ADMIN tier and refused while bootstrap is needed. The latch is recomputed each
boot from persisted evidence, so a reboot keeps the board locked. Bootstrap is open to the first LAN client,
the same as the existing AU-02 marker-only state.

## Write order and power cuts
- Fresh boot, sentinel then mirror: a cut between them leaves the sentinel present. The next boot backfills the mirror. No false lock.
- Resolve, policy then sentinel: a cut after the policy write leaves a policy without a sentinel. The upgrade
  branch writes the sentinel on the next boot. The order is correct; the reverse order would open the board.
- Resolve, password then policy: see F2-02 (stays locked, no lockout).
- Deliberate `clear_policy_and_marker()` leaves the sentinel in place, so the board returns to fresh-open as
  intended. No code path erases the whole `kiln_auth` namespace. Factory reset scopes never erase `nvs`.
  The `wifi`/`all` scopes erase the mirror, and the next boot backfills it.

## Unlock paths
Bootstrap: `security_backend_web_auth.c` calls `web_auth_store_set_password(ADMIN)`, which resolves (tested).
Physical reset gesture: clears credentials and leaves policy and latch alone. The admin becomes unconfigured,
then bootstrap, then resolve. Works by composition; no direct test.

## Findings
- **F2-01 MED** `web_auth_store.c` `storage_reset_resolve()`: the recovered policy is hard-coded
  `lcd_enabled = false`. While latched, the LCD reads UNREADABLE and fails closed. Once the web admin is set,
  the LCD becomes fully open without a PIN, even if the board had LCD auth before the wipe. This is the
  factory-fresh outcome that the owner decision rejects, reached silently. Suggest keeping LCD fail-closed
  (`lcd_enabled = true` with admin PIN bootstrap) or showing the LCD state explicitly in the banner or readiness item.
- **F2-02 LOW** A cut, or a failed `set_policy`, after the bootstrap password commits but before the policy
  write: the next boot latches again with the admin configured. The admin can log in, and auth is on, but the
  banner and readiness item stay until the admin password is set again or a policy is saved and the board reboots.
  It fails closed and is not a lockout. Neither the documentation nor the tests cover it.
- **F2-03 LOW** Only the web admin password clears the latch. An LCD admin PIN never does, so an LCD-only
  operator cannot clear the banner.
- **F2-04 LOW** Residual gap: an IDF NVS format change (NEW_VERSION_FOUND) affects every partition. `nvs` and
  `wifi_nvs` are erased together, so the mirror and the STA credentials disappear with the sentinel and the board
  boots factory-fresh with auth off. The same happens on a pre-FS-02 board whose `nvs` was lost before the upgrade.
  The board leaves the LAN (AP mode), which limits exposure.
- **F2-05 LOW** Test coverage: the readiness helpers are identity inlines, so their checks prove nothing about
  the handler. The LCD banner branch, the `main_boot_early` call, mirror backfill, both power-cut windows,
  set_policy failure keeping the latch, the USER role not resolving, and the gesture path are untested.
  The commit records no negtest run. The checks that exist do assert the real decision: fresh-open versus latched,
  bootstrap needed, and the persisted policy.
- **F2-06 INFO** Upgrade heuristics are sound. If a policy or marker exists, the board is healthy and the sentinel
  is written. If only an admin record exists with no policy, the board is treated as fresh, which matches its auth-off
  state. A read error on `nvs` skips latching, and AZ-02 already fails closed in that case. An `nvs` auto-erase with
  STA credentials kept latches an auth-off board too, per the owner decision.
- **F2-07 INFO** RAM: 128 B of new `.bss` (`s_auto_erased[8][16]`) plus one bool. The policy blob on the
  main stack is transient. This is negligible against the 8 KB internal floor.
- **F2-08 INFO** Boot order is correct. Both partitions are up, `wifi_prov` state is set synchronously in
  `wifi_prov_start()`, and HTTP and LVGL start later. The latch bool is written by main or httpd and read
  without a lock. A torn read is impossible for a bool; at worst a stale banner lasts one frame.
- **F2-09 INFO** FS-01 interaction: there is none at the storage level. FS-01 covers `cfg` and `kiln_nvs` zones,
  and FS-02 covers default `nvs` auth. Both add readiness detail independently, and the FS-04 wording does not
  collide. The auth item is advisory and outside the four firing-gate items.
