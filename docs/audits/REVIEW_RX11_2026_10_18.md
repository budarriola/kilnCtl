# REVIEW_RX11_2026_10_18 (HIGH 0, MED 1, LOW 2, INFO 4)

Scope: commit 62410ada5 (RX-11). The new `firmware/KilnFW/App/drivers/update/stage_image_verify.c/.h` replaces
`esp_image_verify()` over the 4 KB-offset stage image in two places: `update_http.c` io_image_verify (upload_finish,
which also runs on the `update_fetch_wr` task) and `recovery_apply_esp.c` cb_stage_verify (before `app` is erased).
Compared against IDF v6.0.2 `components/bootloader_support/src/esp_image_format.c` (image_load,
verify_image_header, verify_segment_header, process_segment, process_checksum, process_appended_hash_and_sig) and
`bootloader_common_loader.c` bootloader_common_check_chip_validity.

## Parity that holds
- Magic 0xE9, chip id 9, segment count <= ESP_IMAGE_MAX_SEGMENTS (16). nseg == 0 is also refused (stricter, fine).
- Segment length `& 3` and `>= 16 MB` (ESP_IMAGE_MAX_FLASH_ADDR_SIZE) match verify_segment_header.
- should_map ranges match ESP32-S3 soc.h (DROM 0x3C000000-0x3E000000, IROM 0x42000000-0x44000000).
- Alignment is computed image-relative. This is correct because app partitions are 64 KB aligned. It is the RX-11 fix, and it is right.
- The SHA covers the header, segment headers, data, and padding including the checksum byte, as IDF does. The byte-XOR fold equals IDF's word-XOR fold.
- Bounds: `off <= avail` is an invariant. Every subtraction (`avail - SEG_HDR_LEN`, `avail - off`) is guarded once
  `avail >= 72`, and `dlen < 16 MB`, so `off + dlen` cannot wrap. Reads stay within `image_len`, which update_stage
  limits to the stage size, and esp_partition_read also checks bounds. No overflow found.
- PSA lifecycle: sha_finish runs exactly once on every path (walk sets `finished` before its own call, and the wrapper
  calls it otherwise). The callbacks abort on a finish failure and clear `active`. No leak found.

## Findings
- **RY-01 MED** The chip revision range is not checked. IDF verify_image_header calls bootloader_common_check_chip_validity,
  which refuses an app whose min_chip_rev_full/max_chip_rev_full (header bytes 15..18) excludes this chip. The walker
  does not check it. In recovery, the stage verify passes, `app` is erased and copied, and then cb_app_verify (full
  esp_image_verify) fails. `app` is gone and the board stays in recovery until a good image is uploaded. In the app
  path, such an image is marked VERIFIED. RX-11 says "bootloader and cb_app_verify still check it", but both of those
  checks run after the erase, which is the case OP-01 was added to prevent. Fix: call
  bootloader_common_check_chip_validity(hdr, ESP_IMAGE_APPLICATION) on the 24-byte header through an io callback (this
  keeps the walker pure), and add a host test with a min_rev above the chip.
- **RY-02 LOW** BX-03 stack. io_image_verify puts `iv_sha_t` (psa_hash_operation_t) on the stack, along with a 512 B
  chunk in feed() and about 120 B of header and digest locals. All of this sits under update_stage_upload_finish on the
  4096 B `update_fetch_wr` stack. Recovery made its op static for this reason, but the app did not. The frame is likely
  smaller than the old esp_image_verify frame, but it is unmeasured. Fix: make the op static (upload_finish is
  serialized by the stage claim) and read the update_fetch_wr high-water mark on the RX-06 bench run.
- **RY-03 LOW** The host tests do not cover a chip-revision mismatch. They also do not test truncation inside the checksum
  padding separately from truncation of the digest. Truncation is reported as STAGE_IMG_TOO_LONG, although it means
  too short. This affects only diagnostics. Add the tests with RY-01.
- **RY-04 INFO** hash_appended == 0 is refused, while IDF accepts it with the checksum only. This is deliberately
  stricter, since IDF app builds always append the hash. Fine.
- **RY-05 INFO** Load-address range validation (verify_load_addresses) is BOOTLOADER_BUILD only. The old
  esp_image_verify, the walker and cb_app_verify all skip it. So an image with a bad load address passes every
  pre-erase gate and fails only in the bootloader. This is unchanged from before the commit, and
  ric_validate_first_chunk plus the project check make it unlikely.
- **RY-06 INFO** Secure boot and signed apps are not handled. A signature block after the digest is ignored and passes
  as trailing bytes (`len <= image_len`). This is fine while secure boot is off (owner 2026-10-07: no release signing).
  If secure boot is ever enabled, signature verification must be added before the erase.
- **RY-07 INFO** esp_cpu_dbgr_is_attached(): IDF skips the checksum and hash while JTAG is attached, but the walker always
  checks them. This is stricter. It changes behaviour only on the bench with a probe attached, and there it is the
  safer choice.
