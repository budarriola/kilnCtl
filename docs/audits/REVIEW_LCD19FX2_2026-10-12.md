# Review: LCD-19 fix round 2 (origin/dev 1e7f983b5), 2026-10-12

Adversarial review of `1e7f983b5`, which fixes `REVIEW_LCD19FX_2026-10-12`
LOW-1..4 and INFO-1..7 in
`tools/PcTools/src/kilnctrl/bench_test/cases_lcd.py` and
`tools/PcTools/tests/test_bench_test_cases_lcd.py`. No board access. All runs
were made in a minted worktree at `1e7f983b5`.

**Verdict:** no HIGH. One MED: LOW-1's reclassification turned two real
firmware-defect shapes, which used to FAIL, into INCONCLUSIVE with a
misleading reason. Six LOWs and four INFOs follow. Negtest: 13 of 16
mutations caught; the 3 misses map to MED-1, LOW-2 and LOW-6.

## Firmware facts checked

- `login_backoff.c:3`: `LOGIN_BACKOFF_LADDER_MS[5] = { 5000u, 10000u, 30000u, 60000u, 300000u }`.
  `ui_lcd_keypad.c` prints N = ceil(remaining/1000) once, at submit. The
  label is never refreshed, so N <= 300 always, and the client cap of 300 s
  is sound.
- `ui_lcd_keypad.c`: dots and status share `s_info_label`.
  - DENIED sets "Wrong PIN". LOCKED_OUT sets "Wrong PIN -- try again in %us".
  - A digit or backspace calls `refresh_dots()`, which clears the status.
  - OK on a too-short entry is a no-op. The label is kept.
  - `ui_lcd_keypad_show` resets the label. A backdrop click cancels the keypad.
- The `kiln_ui.c` tap walk names a container after its first visible label
  grandchild. Its `char name[32]` holds "Wrong PIN -- try again in 300s"
  (30 chars).
- `ui_lcd_lock.c:365` `gate_keypad_done_cb`: on GRANTED with a role below
  `min_role`, the keypad closes and returns with no confirm dialog.
- `display_power_policy.c`: a touch is swallowed in OFF (it wakes the panel)
  and in ERROR_HOLD (it dismisses the hold, and the panel is already on).
  LVGL sees only the release, so a swallowed tap makes no click.

## Focus items

1. **LOW-1, lost click versus genuine denial.**
   - A wrong-PIN acceptance bug still FAILs. Probe P1: a keypad that accepts
     any PIN gives FAIL "a wrong PIN was not refused".
   - The genuine right-PIN DENIED shape (dots cleared plus "Wrong PIN")
     still FAILs.
   - Two other shapes no longer FAIL. See MED-1.
2. **300 s cap test.** `test_lockout_cap_pinned_to_firmware_last_rung`
   really parses `login_backoff.c`. Its regex takes the
   `LOGIN_BACKOFF_LADDER_MS[...] = {...}` body, asserts five `(\d+)u`
   entries, and compares `rungs[4]` against `_LCD19_LOCKOUT_MAX_S*1000`.
   Mutations N5 (client 600) and N6 (firmware 600000u) are both caught. See
   the appendix.
3. **LOW-3 wake and the keypad backdrop.**
   - The wake taps (5,5), which sits inside the backdrop (x<40), whenever the
     power state is not confirmed ON. On an awake panel in state ON it never
     taps (P5).
   - In ERROR_HOLD it taps. The panel is awake, but the policy swallows that
     touch as the dismissal, so the backdrop is not hit.
   - One hole: with `power_state` absent and `screen_on=None`,
     `bool(None)` is False, so it taps. That is LOW-3 below.
   - There is a TOCTOU between reading OFF and injecting. The panel could
     wake in between, for example from a status-driven forced-on. The window
     is milliseconds wide, and the cost is a cancelled keypad, which reads
     INCONCLUSIVE or entry_incomplete rather than a false PASS.
4. **Fake versus firmware.**
   - The `PinKeypadUiTest` `_label` now persists until the next digit, a
     Cancel, or a show. `BackoffUi` fixes N at submit. Both match firmware.
   - Remaining gaps: OK on a short entry sets "Wrong PIN" in the fake but is
     a no-op in firmware (INFO-3). Backspace is not modelled. Neither gap is
     reached by the current case flow.
5. **Changed test `test_verified_complete_entry_keypad_stays_open_after_ok_is_fail`.**
   Coverage was lost. See LOW-2.
6. **Adapted anchors M1, M7, M8, M10.** All four still match uniquely in the
   LF blob and are still meaningful. They were re-run as N1-N4, and all four
   were caught. See the appendix.

## Findings

### MED-1: right PIN accepted but no firing start now reads INCONCLUSIVE with a generic reason (regression)

Before `1e7f983b5`, any stabilized post-right-PIN read without the
Start/Cancel confirm set `right_pin_started = False`, so the case FAILed. Now
only "OK" plus cleared dots plus "Wrong PIN" FAILs. Everything else falls
into `right_pin_outcome = "indeterminate"`, and that outcome has no specific
reason. It ends INCONCLUSIVE with the generic "could not exercise ... missing
UI_TEST API or camera" text.

- **P2.** The keypad closes after the right PIN and no confirm appears, for
  example a granted role below `min_role` (`gate_keypad_done_cb`), or a
  gated action that never runs. This is a genuine firmware defect: the right
  PIN does not start the firing. It used to FAIL. It now reads
  INCONCLUSIVE, and the reason points at the instrument.
- **P3.** The keypad stays open with dots cleared and no label. Firmware
  always labels DENIED, so this shape should not occur. It is now
  INCONCLUSIVE and untested.

**Fix.**
- If the stabilized read shows no "OK" and no "Cancel" (the keypad and the
  confirm are both gone), set `right_pin_started = False`, which FAILs.
- Otherwise give "indeterminate" its own reason that names the names seen.
- Add a test for each shape.
- Mutation N16 shows the gap: forcing "indeterminate" back to FAIL is
  MISSED by the suite, so neither the current INCONCLUSIVE nor the old FAIL
  is pinned.

### LOW-1: a lock that outlasts its own countdown reads "duration could not be read"

P4 makes every right-PIN submit show "try again in 10s", on both attempts.
The case sleeps N+1 = 11 s, retries, and gets locked again. Attempt 1 sets
`pin_lockout` with no retry, so the reason is "the right PIN landed in a
login lockout whose duration could not be read". That is false: N was read
(`right_pin_lockout_retry = 10`).

A lock still active after its own countdown plus 1 s is a firmware defect
(or a fresh wrong submit). The case should say so: either a specific
INCONCLUSIVE reason ("still locked after waiting N+1 s"), or a FAIL.

### LOW-2: the rewritten "stays open after OK" test is now a duplicate of the DENIED test

`test_verified_complete_entry_keypad_stays_open_after_ok_is_fail`, in
`Lcd19Test`:

- Both if/else branches now set `_entry=""; _label="Wrong PIN"`, so the
  branch is dead.
- The docstring still describes a stuck submit where the keypad never
  closes. The test now exercises genuine DENIED, the same as
  `test_right_pin_genuinely_denied_is_fail`.
- The stuck shape with no label, P3, is pinned by no test. No test asserts
  `right_pin_outcome == "indeterminate"`.
- It has no `_sleep` in ctx, so it really sleeps about 6.5 s.
- Mutation N12 (the DENIED branch drops its `"Wrong PIN" in names` check)
  is MISSED for the same reason: no test presents cleared dots without a
  label.

### LOW-3: `_lcd19_wake_if_blanked` taps on an unreadable state

The docstring says an unreadable state never taps. With `power_state` absent
and `screen_on=None`, `on = bool(None)` is False, and the helper taps (5,5),
inside the keypad backdrop. On an awake panel that cancels the keypad.

**Fix:** treat `screen_on is None` as unreadable and return None. Also add
the missing test cases: no `power_state`, and ERROR_HOLD.

### LOW-4: the wake is never exercised end to end

`FakeSrvFull` has no `_touch`, so `right_pin_retry_wake` is None in every
end-to-end LCD-19 test (P6). Only the unit test of the helper covers it.
Mutations N9 and N10 (always tap, never tap) are caught only by that unit
test.

### LOW-5: `test_retry_clears_attempt0_diagnostics` does not assert the verdict

It checks the `attempt0_*` keys but not the final verdict. A retry that
renames correctly and then FAILs would pass this test.

### LOW-6: the "at cap" test never presents N = 300

`test_lockout_at_cap_waits_in_logged_chunks_and_passes` starts a 300 s lock
at the wrong-PIN submit. The case then waits 6.5 s, so the right-PIN label
reads 294, not 300. The cap boundary itself is never exercised: mutation N7
(`> _LCD19_LOCKOUT_MAX_S` to `>=`, which would refuse to wait out a genuine
300 s label) is MISSED. In this flow firmware can print 300 only for a submit
in the first second of a fresh 300 s lock, so the practical risk is small,
but the test name overclaims. Add a case that presents a label of exactly
300 and expects a wait.

### INFO-1: the long-rung comment overstates the 60 s rung

The comment above `_LCD19_LOCKOUT_MAX_S` says "the 60 s and 300 s rungs
outlast the MCP client's 300 s idle watchdog". The 60 s rung alone does not.
`log.info` progress lines do not keep the client alive either. The advice
(`bench_test_start`) is right; the wording is not.

### INFO-2: the `pin_lockout` reason also covers attempt 1

Any lockout on the second attempt, readable or not, reports "duration could
not be read". This is the general form of LOW-1.

### INFO-3: fake short-OK gap

`PinKeypadUiTest` sets "Wrong PIN" on OK with a short entry. Firmware no-ops
OK on a short entry. No current flow reaches it.

### INFO-4: LCD lock tick during a long wait

`ui_lcd_lock`'s LCD_LOCK_TICK_EXPIRED can close the keypad during a 300 s
wait only when a session was active. That fails safe, as entry_incomplete,
not as a PASS.
