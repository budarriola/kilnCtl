## HIGH

### H1. Target build broken: `-Werror=format-truncation` in the new ROLLBACK REFUSED message

`firmware/KilnFW/App/drivers/persist/kiln_cfg_swap.c:542-545` (added by `ea86f4d43`):

```
..\App\drivers\persist\kiln_cfg_swap.c:543:26: error: 'snprintf' output may be truncated before the last format character [-Werror=format-truncation=]
note: 'snprintf' output between 141 and 201 bytes into a destination of size 200
```

The fixed prefix is 141 bytes and `%.60s` adds up to 60, so the output can reach
201 bytes in a 200-byte buffer. The other `ROLLBACK FAILED` messages in the same
function cap `sub` so the total fits (`%.138s`, `%.136s`). GCC/xtensa rejects
this; MSVC host builds do not, so the host tests passed and the break got
through. `check_00_kilnfw_target_build.ps1` failed in this review's worktree, and
the line is unchanged on origin/dev `295c8cae3`. Every KilnFW target build,
flash and release from origin/dev is blocked until it is fixed. Fix: `%.59s`, or
shorten the prefix.

## LOW

### L1. Live `save_as` storage failure: "retry" fails as a duplicate name and leaves a RAM-only profile

`profiles_live_http.c:606-664` (S5) with `profiles_http.c:1771-1960`
(`profiles_http_save_ex`). When `nvs_save_slot_locked` fails (a file-write
failure, or the rev-unknown refusal at `profiles_http.c:1397`), the slot stays
applied in RAM (`profiles_slot_set`) with `out_persisted=false`. The live decide
call then returns 500 "storage save failed; the edit is kept, retry". A retried
`save_as` picks a new first-free slot. `live_edit_name_collides_ex` excludes only
the target id, so it finds the RAM-only copy holding the same name and refuses
with 400. The operator's retry fails unless they rename. The phantom RAM-only
profile is also listed until reboot. `overwrite` retries target the same origin
slot and work, except under rev-unknown, where they always fail. Fix: roll back
the RAM slot on a persist failure in the save_as path, or exclude the unpersisted
slot from the collision check.

### L2. kiln_nvs fence flag is overwritten by a second, narrower reset while one is in flight

`factory_reset.c:521-528` (`execute_scope`) and `relay_authority.c:238-313`
(`relay_authority_reset_set_erases_kiln_nvs`). The flag is assigned, not ORed,
and nothing refuses a second reset while one is in flight
(`reset_other_writer_refuses`, `factory_reset.c:472`, checks only
sweep/backup/convert). After a `kiln`/`all` erase, depth stays at 1 until
`reboot_task` reboots (about 500 ms). A `wifi`/`profiles` reset in that window
(HTTP or UART `factory_reset_execute`) calls `set_erases(false)`, which disables
the kiln_nvs fence for the partition that was just erased. Writers on other tasks
(wear, lockout, boot_guard, run_state) can then recreate pre-reset keys before the
reboot. A refused second reset's `end()` also does not restore the flag. Fix: make
the flag sticky (OR) while depth > 0, or refuse a reset while one is in flight.
The new test (`test_link_watchdog.c`, `test_kiln_nvs_fence_only_when_scope_erases_it`)
covers only sequential begin/end.

### L3. `rev_unknown` is surfaced only for used slots

`profiles_catalog_http.c:340-346` emits `rev_unknown` only for listed (used)
slots. When the floors are unknown, every slot is rev-unknown, unused ones
included (`profiles_http.c:1088-1091`). A new save into the first free slot then
fails, and the page shows no notice, because `revNotice`
(`profiles_page.html:1447`) is keyed off the listed profiles only. Fix: add a
catalog-level `floors_unknown` flag.

### L4. Empty `id=` on kiln_configs save is treated as absent and creates a new slot

`kiln_cfg_http.c:223-243`. The strict parse refuses `+`, `-2` and junk. For
`id=` with nothing after it, `http_form_find_field` returns 0 and the handler
falls through to the "no id" path, which saves to a NEW slot rather than refusing
with 400. `test_save_optional_id_strict` (`test_kiln_cfg_http.c`) does not cover
`name=a&id=`. The shipped page (`kiln_configs_page.html:433/446`) never sends an
empty id, so only a hand-made or scripted client is affected.

## INFO

- **I1. The static `err_msg` buffers are safe as written.** `dashboard_exec_http.c:824`:
  httpd runs one worker task, and the profile_exec_start route is synchronous
  (`dashboard_http.c:830`, not wrapped in `http_async_job`; only `backup_import.c`,
  `diagnostics_http.c` and `safety_cfg_http.c` use that). `uart_bridge_ext_control.c:569`:
  `profiles_handle_message` is reached only through
  `uart_bridge_ext_run_on_flash_worker` (`uart_bridge_ext_control.c:659`), which
  serializes jobs on one worker (`bx_run_on_internal_stack`, `uart_bridge_ext.c:615`:
  recursive lock + queue + done semaphore, inline when already on the worker).
  Converting either path to an async or second worker later would make these
  buffers racy, and the comments say why they are safe. Cost: 2 x 192 B
  (`READINESS_GATE_MSG_CAP`, `readiness_gate.h:127`) of internal-DRAM `.bss`. The
  autotune paths (`dashboard_autotune_http.c:340`, `uart_bridge_ext_autotune.c:140`)
  still hold 192 B on the stack.
- **I2. `used_bitmap` u8 fallback is correct.** Checked against the ESP-IDF v6.0.2 NVS
  source: `Storage::findItem` (`nvs_storage.cpp:257`) turns a page-level type
  mismatch into `NOT_FOUND`, and `writeItem` (`nvs_storage.cpp:380`) replaces an
  existing key of any type. Minor: in `profiles_http.c:816-843`, a u8 read error
  other than NOT_FOUND is reported as `HAL_NOT_FOUND`, which masks the error. The
  older block comment near `profiles_http.c:806-812` (TYPE_MISMATCH ->
  HAL_INVALID_ARG) is now stale.
- **I3. recovery_exit does not strand the operator.** `ota_http_recovery.c:146-157`
  now answers 500 and does not reboot when `boot_guard_mark_healthy()` cannot
  verify the clear. Before this change, the reboot went ahead and, with the
  counter still set, landed the board back in recovery mode. So the operator
  loses nothing: they get an honest error instead of a reboot that changes
  nothing. The background confirm task keeps retrying and the operator can call
  again. There is one narrow case where the new behavior is worse: the write
  persisted but its read-back failed. That case now needs a retry where it used to
  exit. The separate recovery image (`firmware/KilnFW_recovery`, `recovery_http.c`)
  is untouched by both commits, so its escape path is intact. The reply-after-task
  ordering in `ota_http_esp.c` (rollback, about :815-850) and
  `ota_http_recovery.c:171-194` is correct. On a task-create failure it answers 500
  and calls `ota_http_update_end`.
- **I4. ROLLBACK REFUSED:** no code outside `kiln_cfg_swap.c` matches on the
  `ROLLBACK FAILED`/`REFUSED` text. The function still returns false, the journal
  is kept and boot recovery retries. Apart from H1, the semantics are fine.
- **I5. SaftyFW tests** (`test_config_store_flash.c`): the one-ulp raise tests pin
  the `<=` comparisons. The clamp test relies on `config_store_write` accepting an
  out-of-range `tc_offset_c`; if a write-side range check is added later, that test
  fails on a fixture message. Only the positive bound is exercised.
