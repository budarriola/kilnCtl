# Review 2026-10-17: KilnFW_recovery end to end

Static, read-only review of `firmware/KilnFW_recovery` on `origin/dev` b44f30112. No board access.
Result: HIGH 0, MED 0, LOW 2, INFO 2. KNOWN_ISSUES rows RC-01..RC-04.

## Scope and verdicts

| Area | Verdict |
|---|---|
| Boot path (`recovery_main.c`) | OK. Relays held off and the S6b keepalive start before NVS init. NVS is never erased. Unattended install runs before httpd (REVIEW_AUTOFX LOW-4). The HTTP restart waits for a running apply (RO-01 fixed, `recovery_health.c:70`). |
| Install/apply, attempt counting (`recovery_install.c`, `update_install_record.c:311-367`) | OK. The request is decoded and checked against the verified stage (length, SHA-256). The attempt counter is raised and read back before any erase. A refusal before erase drops the request. A failure to drop it gives CLEAR_FAILED (STAY). `update_install_after_fail()` stays when the reason is NVS, counter, result, clear or outcome-unknown. |
| Power loss mid-install | OK. A cut during the copy leaves `app` invalid. The bootloader falls back to `recovery` (factory), the stored counter advances the retry, and after `UPD_INST_MAX_ATTEMPTS` it refuses with app_modified forced on, so it stays unless the app verifies. A cut between `set_boot` and the request clear boots the app, and the app's `update_install_http_drop_stale_request()` drops the leftover request. A bootloader rollback rewrites a stale OK as rolled_back (`load_last`, MED-3). |
| AP and route exposure | Matches the owner decision (2026-10-02). WPA2-PSK SoftAP only, no STA. 12 characters from a 32-symbol alphabet (60 bits), drawn with `bootloader_random_enable()` + `esp_fill_random()` before Wi-Fi init. The passphrase goes to the LCD only. The log line names only the SSID, and status reports `auth_mode: lcd_passphrase`. Routes are unauthenticated by design. A cross-origin/Host guard refuses state-changing methods (MED-1). the route table is static-asserted to fit `max_uri_handlers` 16. No passphrase is quoted in this document. |
| Image verification | OK. `ric_validate_first_chunk()` checks magic, chip id, segment and app descriptor, the main application project name (`RIC_EXPECTED_PROJECT`), and size before anything is written. Staged apply: header SHA over the stage, copy, re-hash `app`, `esp_image_verify` bounded by the staged length, then `set_boot` with read-back. There is no signature (owner 2026-10-07: no release signing). |
| Handoff to the app | OK. Order is boot_guard clear (verified) -> supersede the request -> set the boot partition and read it back -> restart. This holds for `/api/recovery/exit`, `/api/ota/esp`, the manual apply and the unattended apply (pre_boot/post_boot). |

## Findings

**RC-01 LOW.** `recovery_install.c:238-262` (`recover_task`) against `recovery_http.c:216` (`ota_esp_post`). After a failed unattended install, `recover_task` runs a whole-image verify of `app`, which takes seconds. It then checks only `recovery_apply_busy()` and `recovery_pico_busy()` before `recovery_http_select_app_and_restart()`, and on the RESTART path before a 3 s delay and `esp_restart()`. httpd is already up at that point. An operator `POST /api/ota/esp` that starts in that window writes `app` without any claim, so the task can switch the boot target to a half-written `app`, or restart mid-upload, based on a stale "verifies". The bootloader then falls back to recovery and the upload is lost. The window is narrow, since the operator must first join the AP. Fix: make the direct upload take the same claim as `recovery_apply_esp_start()` (`s_running`, or a shared "app writer" flag), and re-check it in `recover_task` right before the switch or restart.

**RC-02 LOW.** Check coverage. `run_all_checks -Fast` filters out `check_00_kilnfw_recovery_target_build.ps1` (`tools/run_all_checks.ps1:632-637`). `check_recovery_image_size` then reports SKIP-FAST. So the coordinator's batch runs on the dev tip never compile the recovery image. The target-only files (`recovery_http.c`, `recovery_install.c`, `recovery_apply_esp.c`, `recovery_wifi.c`) link application sources (`update_install_record.c`, `stage_header.c`, `update_semver.c`, `ota_image_crc.c`, the http_origin helpers). An app-side signature change can therefore break the recovery build with no signal until the full (non-Fast) run that `dev_promote.ps1:148` requires, or until `make_release.ps1`. Fix: add a compile of the recovery project to the batch, or note the gap.

**RC-03 INFO.** The `build_kilnfw` warning `recovery app partition too small for KilnCtrl.bin (overflow 0xf97f0)` comes from ESP-IDF `components/partition_table/check_sizes.py:88-102`. That script checks the app binary against EVERY app partition in `firmware/KilnFW/partitions.csv`. `app` (ota_0, 0x400000) fits. `recovery` (factory, 0x1E0000) does not: KilnCtrl.bin is about 0x2D97F0, so the overflow is 0x2D97F0 - 0x1E0000 = 0xF97F0. Because one app partition fits, IDF only warns ("1/2 app partitions are too small"). This is expected and harmless: KilnCtrl.bin is never written to `recovery`, `flash_recovery` refuses any image whose project name is not `recovery`, and the build becomes an error once the app outgrows `app` itself. The real recovery size gate is `check_recovery_image_size.py`, run against recovery.bin. Fix (optional): document the warning in `build_kilnfw` output or the docs so it is not mistaken for a real overflow.

**RC-04 INFO.** How recovery.bin is produced and released. `check_00_kilnfw_recovery_target_build.ps1` builds it in `C:\wt\checkbuild_recovery_<tag>` and publishes it to `firmware/KilnFW_recovery/build/recovery.bin`. It runs only in a full `run_all_checks`, not under -Fast. `make_release.ps1:284-297` runs that check, then passes `--recovery` to `release_manifest.py`, which attaches it as the `recovery` image. No field path writes the `recovery` partition: the application never updates it, and USB recovery was dropped (owner 2026-10-09). A released recovery.bin reaches a board only through `flash_recovery` (JTAG/OpenOCD). This is an observation, not a defect.
