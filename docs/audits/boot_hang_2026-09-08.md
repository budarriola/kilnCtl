# ESP32-S3 boot hang after flashing `218f65f7` (2026-09-08)

## Symptom

After OpenOCD flash+verify of `218f65f7` reported OK, the board never answered
HTTP on either `192.168.1.156` or `192.168.4.1`, `get_device_log` stayed frozen
at pre-flash lines, and the CONTROL UART link (COM14) never replied. JTAG
(`debug_read_registers(peer="esp")`) showed both cores alive and halted, not
reset-looping.

## JTAG evidence (gathered before reflashing)

Three successive attach/halt cycles all reported the **identical** PCs:

- cpu0: `PC=0x40380318`, reset cause "Software CPU0 reset"
- cpu1: `PC=0x40389E35`, reset cause "Software CPU1 reset", halt cause
  "Level-1 interrupt"

Symbolized against `C:/wt/espflash/firmware/KilnFW/build/elf_archive/KilnCtrl-latest.elf`
(built from `218f65f7`, matching size/timestamp to the flashed binary):

- `0x40380318` → `vPortExitCritical` (`FreeRTOS-Kernel/portable/xtensa/port.c:510`)
- `0x40389E35` → `_xt_context_save` (`xtensa/xtensa_context.S:159`)

Both addresses are generic FreeRTOS/interrupt-entry machinery, not
application code, and identical across three independent attaches. That is
most consistent with OpenOCD's connect sequence performing its own reset before
halting (both cores report "Software CPU reset" as their halt-time reset
cause) — i.e. **this is not strong evidence of a spin location**; it does not
by itself confirm the CPU was stuck inside the LittleFS mount/format path.
Treat it as inconclusive rather than confirming.

## The actual evidence: a persisted crash report

After recovery (below), `get_heap_status` surfaced a crash record that
survived the reflash (crash reports are stored independently of the flashed
app image):

```
!!! UNACKNOWLEDGED CRASH REPORT !!! exc_task='main' exc_cause_str='IllegalInstruction'
reset_reason='PANIC' -- this board panicked and nobody has reviewed it yet
```

This is from the `218f65f7` boot, not the recovery boot (the recovery boot's
own `reset_reason` was `software (esp_restart)`, `uptime_s=11`, i.e. the
reset the flash tool itself issued). **This changes the diagnosis**: the
`218f65f7` boot did not merely hang in a long-running mount/format call — the
`main` task took an `IllegalInstruction` panic. A panic handler configured to
halt the core for a debugger (rather than reboot) would explain both the
frozen JTAG PCs (generic interrupt/critical-section addresses reached while
unwinding into the panic path) and the total silence on HTTP/UART: nothing
after the panic point ever ran, including Wi-Fi/HTTP bring-up and the RTC
watchdog's feed task, so the board simply sat halted with no external sign of
life beyond "CPU alive over JTAG."

## The leading hypothesis was checked, and is WRONG as written

The task hypothesis was: `117fc6f9` wired the `cfg` LittleFS mount into
`main_boot_early.c` immediately after `boot_guard_init()` and **before**
`rtc_watchdog_start()`, so a long/hanging format on a blank partition could
stall boot with no watchdog running to recover it.

Reading `firmware/KilnFW/App/main_boot_early.c` (HEAD, same content at
`218f65f7`) shows the opposite ordering:

```c
boot_guard_init();
ctx->recovery_mode = boot_guard_is_recovery_mode();
rtc_watchdog_start();      // <-- watchdog armed FIRST

// cfg_fs_mount_device() ... placed HERE
{
    esp_err_t cfg_fs_err = cfg_fs_mount_device();
    ...
}
```

`rtc_watchdog_start()` runs at line 408, `cfg_fs_mount_device()` at line 433 —
the watchdog is armed *before* the mount, not after. The commit that added
the mount (`117fc6f9`) explicitly says it is placed "right after
recovery_mode is known," which is after both `boot_guard_init()` and
`rtc_watchdog_start()`. So the specific mechanism in the hypothesis (mount
races ahead of watchdog arming) does not exist in this tree.

Separately, `9d5da657`'s auto-format gate is not a blind auto-format: on an
ambiguous/non-blank partition it sets a "format confirmation pending" flag and
refuses to touch it (`cfg_fs_mount_format_confirmation_pending()`), logging a
loud banner instead of formatting. It does not block boot either way — mount
failure degrades every cfg_fs-backed setting to NVS-only and continues.

**Conclusion: the watchdog-ordering hypothesis is refuted by inspection.**
The watchdog was armed first, and would have been available to catch a true
infinite loop in the mount/format path — except a *panic* (illegal
instruction), not a hang, is what actually happened, and depending on the
panic handler's configured behavior (halt-for-gdb vs. reboot), the watchdog
may never get a chance to act on a panic at all. The proximate cause is a
genuine code fault reached from inside or shortly after `cfg_fs_mount_device()`
during first-boot-on-a-freshly-flashed-partition conditions, not a starved
watchdog. The exact faulting instruction/line was not captured (the crash
record surfaced by `get_heap_status` gives task and cause but not a PC/backtrace;
no separate tool in this session's kilnctrl surface exposes `/api/crash_report`
directly), so the specific line inside the mount/format path is still
unidentified and should be the next thing pulled (read `/api/crash_report`
directly, or reproduce under JTOAD with the watchdog panic handler set to
halt-for-gdb and single-step through `cfg_fs_mount_device()` on a blank
partition).

## Is mounting/formatting before `rtc_watchdog_start()` safe in general?

Moot for this incident (the actual ordering already runs the mount *after*
the watchdog is armed), but worth stating for future boot-order changes:
mounting/formatting a filesystem in the main boot task, watchdog-armed or not,
is only as safe as (a) the watchdog's feed cadence actually covering that
call's worst-case duration, and (b) nothing in the filesystem library's error
paths taking a fault the watchdog can't observe (a real panic bypasses a
watchdog-recovery story entirely, as this incident shows). A bounded-time
format (with an explicit timeout/abort rather than trusting the watchdog as
the only backstop) would be the more robust fix; that is not implemented here
per this task's recovery-only scope.

## Recovery performed

1. In `C:/wt/espflash` (isolated worktree, never the main tree):
   `git checkout --detach 6427502a`, `idf.py -C C:/wt/espflash/firmware/KilnFW fullclean && build`.
2. `flash_firmware(kiln_fw_root="C:/wt/espflash/firmware/KilnFW", verify=True, allow_stale=True)`
   — `allow_stale` was required only because the *main* repo's HEAD (`218f65f7`)
   is newer than the worktree's deliberately-older checkout; this is expected
   and not a sign of a bad build. Flash + verify succeeded: board now running
   `6427502a`, matching build timestamp confirmed against the running
   partition.
3. Full health check post-recovery:
   - HTTP up on `192.168.1.156`.
   - `get_heap_status`: healthy heap figures; the only concerning item is the
     `218f65f7` crash record described above (pre-existing, from the bad
     boot, not new).
   - `safety_get_status`: link up, thermocouple valid, `tx_dropped 0`.
   - `safety_get_fw_version`: Pico on `6427502a`, protocol v12, commissioned.
   - `control_get_zones`: gains and coupling matrix match the known-good
     values exactly —
     Zone0 Kp=0.0318 Ki=0.0001 Kd=0.8401,
     Zone1 Kp=0.0485 Ki=0.0002 Kd=1.0548,
     Zone2 Kp=0.0631 Ki=0.0002 Kd=1.0690;
     coupling z0(27.32,21.72) z1(14.30,22.15) z2(8.33,12.42).
   - No restore from `tools/PcTools/board-backups/20260908T002029Z/board_backup.json`
     was needed — gains/coupling/profiles were intact on `6427502a` as flashed.

## Do not reflash `218f65f7`

It panics (`IllegalInstruction`) on boot before Wi-Fi/HTTP/UART bring-up and
bricks the board into a JTAG-only-recoverable state. See the warning added to
`docs/FILESYSTEM_PLAN.md`.
