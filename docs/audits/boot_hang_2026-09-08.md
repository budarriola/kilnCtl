# ESP32-S3 boot hang after flashing `218f65f7` (2026-09-08)

## Symptom

After OpenOCD flash+verify of `218f65f7` reported OK, the board never answered
HTTP on either `192.168.1.156` or `192.168.4.1`, `get_device_log` stayed frozen
at pre-flash lines, and the CONTROL UART link (COM14) never replied. JTAG
(`debug_read_registers(peer="esp")`) showed both cores alive and halted, not
reset-looping.

## JTAG evidence (gathered before reflashing)

Three successive attach/halt cycles all reported the **identical** PCs:

- cpu0: `PC=0x40380318`, reset cause "Software CPU0 reset"
- cpu1: `PC=0x40389E35`, reset cause "Software CPU1 reset", halt cause
  "Level-1 interrupt"

Symbolized against `C:/wt/espflash/firmware/KilnFW/build/elf_archive/KilnCtrl-latest.elf`
(built from `218f65f7`, matching size/timestamp to the flashed binary):

- `0x40380318` → `vPortExitCritical` (`FreeRTOS-Kernel/portable/xtensa/port.c:510`)
- `0x40389E35` → `_xt_context_save` (`xtensa/xtensa_context.S:159`)

Both addresses are generic FreeRTOS/interrupt-entry machinery, not
application code, and identical across three independent attaches. That is
most consistent with OpenOCD's connect sequence performing its own reset before
halting (both cores report "Software CPU reset" as their halt-time reset
cause) — i.e. **this is not strong evidence of a spin location**; it does not
by itself confirm the CPU was stuck inside the LittleFS mount/format path.
Treat it as inconclusive rather than confirming.

## The actual evidence: a persisted crash report

After recovery (below), `get_heap_status` surfaced a crash record that
survived the reflash (crash reports are stored independently of the flashed
app image):

```
!!! UNACKNOWLEDGED CRASH REPORT !!! exc_task='main' exc_cause_str='IllegalInstruction'
reset_reason='PANIC' -- this board panicked and nobody has reviewed it yet
```

This is from the `218f65f7` boot, not the recovery boot (the recovery boot's
own `reset_reason` was `software (esp_restart)`, `uptime_s=11`, i.e. the
reset the flash tool itself issued). **This changes the diagnosis**: the
`218f65f7` boot did not merely hang in a long-running mount/format call — the
`main` task took an `IllegalInstruction` panic.

(An earlier draft of this section guessed the panic handler was halting the
core for a debugger. It is not: `CONFIG_ESP_SYSTEM_PANIC_PRINT_REBOOT=y` with
`CONFIG_ESP_SYSTEM_PANIC_REBOOT_DELAY_SECONDS=0`, so the board rebooted
immediately and panicked again on the next boot, and so on -- a reset loop,
never reaching Wi-Fi/HTTP/UART bring-up. OpenOCD reset-halts on attach, which
is why three attaches reported identical generic PCs.)

## ROOT CAUSE (identified 2026-09-08): `main` task stack overflow

The `main` task overflowed its 8192-byte stack
(`CONFIG_ESP_MAIN_TASK_STACK_SIZE`) during `app_main()`, smashed a return
address, and executed it.

`GET /api/crash_report` on the recovered board returns the record from that
boot in full:

```json
{"exc_cause":0,"exc_cause_str":"IllegalInstruction","exc_pc":"0xfffffffd",
 "exc_addr":"0x00000000","exc_task":"main","found_on_boot_reset_reason":"PANIC",
 "backtrace":["0xfffffffd"],"backtrace_corrupted":true}
```

**There is no line number to symbolize and never was.** `exc_pc` is
`0xfffffffd` -- not an address in the image -- and the backtrace is a single
corrupted frame. That combination *is* the diagnosis: nothing jumped to a
wrong function, the return address itself was garbage. Rebuilding `218f65f7`
and running `addr2line` on `0xfffffffd` yields nothing, correctly.

What does identify it is measuring the whole call tree at once. Disassembling
a from-source rebuild of `218f65f7` and summing each function's `entry a1, N`
frame along the deepest statically-reachable path from `app_main`:

```
    app_main                          32 B
    main_network_http_bringup         80 B
    kiln_cfg_store_init              144 B
    nvs_load_store_with_cfg_fs      7552 B   <- kiln_cfg_store_blob_t on the stack
    kiln_cfg_store_cfg_fs_resolve     96 B
    kiln_cfg_store_cfg_fs_load_raw  7536 B   <- a second one
    cfg_fs_read                      640 B
    path_join_ok                      32 B
                                  -------
                                   16112 B   on an 8192 B stack
```

Two ~7.5 KiB `kiln_cfg_store_blob_t` locals (`KILN_CFG_MAX_COUNT` entries,
each carrying a full `ZONES_CONFIG_BLOB_MAX_SIZE` blob), nested, on the boot
task. Contributing frames elsewhere on the same path: `scan_partition()`'s
4128 B `uint8_t buf[CFG_FS_SCAN_CHUNK_BYTES]` in `cfg_fs_mount.c`, and
`zones_config_cfg_fs_load_raw()`'s 1904 B (a 1 KiB file buffer plus an 812 B
`zones_cfg_t`).

Notes on why this was not caught, and on what is NOT the cause:

* **It does not depend on the mount succeeding.** GCC allocates the whole
  frame in the prologue, so the `if (!cfg_fs_is_available()) return;` early
  exits at the top of each of these functions do not save a byte. The board
  was going to panic on the `218f65f7` image whatever state the `cfg`
  partition was in -- blank, formatted, or absent.
* **The auto-format gate is not implicated.** `cfg_fs_format_gate.c` is pure,
  its bounds arithmetic is correct, and its host tests are honest; it is
  simply not where the fault is. Neither is the LittleFS subtype (0x83 is
  looked up with `ESP_PARTITION_SUBTYPE_ANY`), nor the write-fn wiring
  installed at `finish_mount_after_register()` -- every one of those function
  pointers is statically initialised to a real function and reassigned only
  to another real function.
* **Host tests could not have seen it.** The host build runs on a PC stack of
  megabytes, and `build_host_tests.ps1` passes 31/31 on the unfixed code. No
  host fake models a stack ceiling. This is not a gap a better fake closes --
  stack depth is a property of the target build, so only the target build can
  be measured.
* The three modules involved each looked reasonable in isolation. Only the
  sum is wrong, and nothing was summing it.

### Fix

1. The oversized locals moved to the heap (or removed by decoding straight
   into the caller's buffer):
   `kiln_cfg_store.c: nvs_load_store_with_cfg_fs()`,
   `kiln_cfg_store_cfg_fs.c: kiln_cfg_store_cfg_fs_load_raw()`,
   `zones_config_cfg_fs.c: zones_config_cfg_fs_load_raw()`,
   `cfg_fs_mount.c: scan_partition()`. Every allocation failure degrades
   exactly like "no `cfg` partition": the NVS candidate stands, boot
   continues.
2. `firmware/KilnFW/App/test/check_main_task_stack_budget.py` (+ a `.ps1`
   wrapper, so `run_all_checks.ps1`'s glob picks it up) makes the measurement
   above a standing check: it fails if the deepest `app_main` path can exceed
   75% of the configured main-task stack. Its negative test is not synthetic
   -- run against the pre-fix ELF it reports `16112 B exceeds the 6144 B
   budget` and exits 1; against the fixed build it reports 4864 B and passes.
   Its limits are stated in its docstring: it does not follow indirect calls
   and cuts recursion, so it under-estimates, never over-estimates.

**Enlarging `CONFIG_ESP_MAIN_TASK_STACK_SIZE` was deliberately NOT the fix.**
The frames are cumulative and this path grows with every future cfg_fs-backed
item; a bigger stack buys one release and hides the next overflow.

### Can a filesystem mount still panic the board?

The design intent -- "mount failure never blocks boot" -- was true of every
*error path* and always has been: `cfg_fs_mount_device()` returns an error and
every consumer degrades to NVS. What was never true is that the mount could
not take the board down by other means, and a try/catch-shaped wrapper could
not have helped: a stack overflow is not an error return, so there is nothing
to wrap. The honest defence is the budget check above, which is mechanical and
runs on every build. Any *new* way for this path to panic (a wild pointer, an
assert) remains possible in principle; nothing in this fix claims otherwise.

### Auto-format on a blank partition: safe to re-enable?

Yes -- it was never the defect, and it is not gated off by this fix. The gate
refuses to format anything showing a LittleFS superblock or more than the
non-erased-byte threshold, refuses on any scan read error, and asks for
operator confirmation instead. That policy stands. The one change it needed is
the heap buffer in `scan_partition()`.

The remaining caution is empirical, not structural: the auto-format path has
still never completed on real hardware, because the board panicked before
reaching it. It should be watched on the first boot after the reflash below
(boot-log banner, `GET /api/cfgfs/format_pending`, `GET /api/cfgfs`), not
assumed.

### A reflash is required to validate this, and should be done cautiously

Nothing here is confirmed on hardware. The board is currently healthy on
`6427502a`, whose flashed partition table has **no `cfg` entry at all**
(`GET /api/partitions` ends at `logs`) -- the recovery flash rewrote the
partition table from the older checkout. So the validating flash also
re-introduces the `cfg` partition, and the first boot on it is the first time
the auto-format path runs anywhere. Flash from a clean worktree, keep JTAG
attached, and read `/api/crash_report` and the boot log before trusting it.

## Earlier hypothesis (refuted, kept for the record)

The task hypothesis was: `117fc6f9` wired the `cfg` LittleFS mount into
`main_boot_early.c` immediately after `boot_guard_init()` and **before**
`rtc_watchdog_start()`, so a long/hanging format on a blank partition could
stall boot with no watchdog running to recover it.

Reading `firmware/KilnFW/App/main_boot_early.c` (HEAD, same content at
`218f65f7`) shows the opposite ordering:

```c
boot_guard_init();
ctx->recovery_mode = boot_guard_is_recovery_mode();
rtc_watchdog_start();      // <-- watchdog armed FIRST

// cfg_fs_mount_device() ... placed HERE
{
    esp_err_t cfg_fs_err = cfg_fs_mount_device();
    ...
}
```

`rtc_watchdog_start()` runs at line 408, `cfg_fs_mount_device()` at line 433 —
the watchdog is armed *before* the mount, not after. The commit that added
the mount (`117fc6f9`) explicitly says it is placed "right after
recovery_mode is known," which is after both `boot_guard_init()` and
`rtc_watchdog_start()`. So the specific mechanism in the hypothesis (mount
races ahead of watchdog arming) does not exist in this tree.

Separately, `9d5da657`'s auto-format gate is not a blind auto-format: on an
ambiguous/non-blank partition it sets a "format confirmation pending" flag and
refuses to touch it (`cfg_fs_mount_format_confirmation_pending()`), logging a
loud banner instead of formatting. It does not block boot either way — mount
failure degrades every cfg_fs-backed setting to NVS-only and continues.

**Conclusion: the watchdog-ordering hypothesis is refuted by inspection.**
The watchdog was armed first, and would have been available to catch a true
infinite loop in the mount/format path — except a *panic* (illegal
instruction), not a hang, is what actually happened, and depending on the
panic handler's configured behavior (halt-for-gdb vs. reboot), the watchdog
may never get a chance to act on a panic at all. The proximate cause is a
genuine code fault reached from inside or shortly after `cfg_fs_mount_device()`
during first-boot-on-a-freshly-flashed-partition conditions, not a starved
watchdog. The exact faulting instruction/line was not captured (the crash
record surfaced by `get_heap_status` gives task and cause but not a PC/backtrace;
no separate tool in this session's kilnctrl surface exposes `/api/crash_report`
directly). It was read directly afterwards, and there is no line to find --
see ROOT CAUSE above. The fault is not inside the mount/format path at all;
it is the cumulative stack cost of the whole `app_main` call tree, of which
the mount is one contributor.

## Is mounting/formatting before `rtc_watchdog_start()` safe in general?

Moot for this incident (the actual ordering already runs the mount *after*
the watchdog is armed), but worth stating for future boot-order changes:
mounting/formatting a filesystem in the main boot task, watchdog-armed or not,
is only as safe as (a) the watchdog's feed cadence actually covering that
call's worst-case duration, and (b) nothing in the filesystem library's error
paths taking a fault the watchdog can't observe (a real panic bypasses a
watchdog-recovery story entirely, as this incident shows). A bounded-time
format (with an explicit timeout/abort rather than trusting the watchdog as
the only backstop) would be the more robust fix; that is not implemented here
per this task's recovery-only scope.

## Do not reflash `218f65f7`

It panics (`IllegalInstruction`) on boot before Wi-Fi/HTTP/UART bring-up and
bricks the board into a JTAG-only-recoverable state. See the warning added to
`docs/FILESYSTEM.md`.

`218f65f7` itself remains unflashable for the reason above. The fix described
under ROOT CAUSE lands on top of it; flash *that*, never `218f65f7`.
