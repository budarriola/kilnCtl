## Verdict

No HIGH and no MED findings. The MED-1 fix is sound: `closed_no_confirm` is a real
firmware defect for the Start flow, so FAIL is the right verdict. The wake step
cannot tap a live control and cannot tap during a firing. The 300 s cap is

fake's short-OK no-op. Both are LOW test gaps, not defects in the judge.

## Firmware facts checked

- `ui_page_home_actions.c` `ui_home_fire_btn_cb`: Start and Stop both gate on
  `LCD_PIN_ROLE_USER`, the lowest role a PIN can be granted. Under the owner rule
  (the LCD Safety page needs a USER PIN; LCD reads stay USER), no granted PIN is
  below USER.
- `ui_lcd_lock.c` `gate_keypad_done_cb`: when the granted role is below
  `min_role`, it returns without acting. This branch cannot be reached for Start.
- `ui_home_show_start_confirm` always calls `ui_confirm_show`, even when no
  profile is identified. The confirm has the title "Confirm Start" and "Start" and
  "Cancel" buttons. `ui_confirm_show` returns early only when `lv_malloc` or the
  msgbox allocation fails (OOM). It has no auto-close.
- The keypad and confirm are closed only by the following:
  - `ui_lcd_lock.c` `tick_timer_cb`, when the policy is disabled, the session
    expires (`LCD_LOCK_TICK_EXPIRED`, minutes of inactivity), or the state goes
    from unlocked to locked (a policy or credential change forces a lock).
  - `network_manage`.
  - `screen_idle` does not close the keypad.
- `ui_lcd_keypad.c` `try_submit`:
  - A too-short entry is a no-op.
  - GRANTED calls `finish()`, which hides the overlay.
  - LOCKED_OUT clears the dots and prints "Wrong PIN -- try again in %us" with
    ceil(remaining/1000). It records no failure.
  - DENIED prints "Wrong PIN".
- login_backoff ladder: `{5000, 10000, 30000, 60000, 300000}` ms. `locked_until`
  is `now + ladder[k]`, so the label never exceeds 300. The LCD's own
  `s_ks.lockout` lasts for the whole boot, because `build_overlay` runs once.
- `kiln_ui.c` tap listing: overlay layers are walked first, and hidden widgets
  are excluded. So a listing taken after the keypad closes, while the confirm is
  shown, puts the confirm's "Cancel" early.

## Check 1: judge paths against firmware

The right-PIN branches, in order, all map to firmware behaviour:

- "try again in": the case went into the lockout path (`pin_lockout`), which is
  correct.
- No OK, Cancel present: the keypad closed and the confirm is open, so
  `started=True`. This is correct.
- OK present, dots not cleared: `submit_not_applied`, giving INCONCLUSIVE. This is
  correct, because firmware always clears the dots on DENIED and on LOCKED_OUT.
- OK present, "Wrong PIN": a real DENIED, so `started=False` and the judge FAILs.
  This is correct.
- Neither OK nor Cancel present (`closed_no_confirm`): the keypad closed with no
  confirm. Because Start needs USER, this means one of three things:
  - a real defect;
  - an OOM in `ui_confirm_show`;
  - an external relock or credential write that landed during the case.

  FAIL is the right verdict. Replacing the judge reason is also safe, because
  `judge_lcd_pin_lock` checks `right_pin_started` before `stop_gated`, and
  `observed` keeps every field.
- Anything else is `indeterminate`, giving INCONCLUSIVE with the names seen. This
  is correct: firmware never leaves an open keypad with cleared dots and no label.
- The "still locked out after its own countdown" reason is correct. A LOCKED_OUT
  submit records no failure, so a lock that lasts past N+1 s means a defect or
  another submit on the panel.

## Check 2: wake

`_lcd19_wake_if_blanked` runs in only one place: the retry after attempt 0
LOCKED_OUT, before the `allow_heat` block. No firing started by this case can be
running at that point. It taps (5,5) only in two cases:

- `power_state` reads something other than ON. OFF and ERROR_HOLD both swallow
  the touch.
- `power_state` is missing and `screen_on` is False.

An unreadable state returns None and does not tap. If the panel wakes between the
read and the tap, the tap lands on the keypad backdrop, which cancels the keypad.
The retype then finds no keypad, and the case reports INCONCLUSIVE or FAIL. It
never starts a firing. This race fails safe.

## Check 3: 300 s cap

Correct. A LOCKED_OUT submit made at least 1 ms after the lock started prints at
most `ceil(300000/1000) = 300`. 300 itself can appear during the first second of
a fresh 300 s lock, so the out-of-range test must be `>` (not `>=`). Mutation X9
confirms the test pins this. The retry waits N+1 s first and at most
`_LCD19_LOCKOUT_MAX_S + 5` = 305 s in total, which is enough.

## Check 4: fake divergences

- The `closed_no_confirm` fake shows a home page of just `["Start"]`. The real home
  page has many tap targets. The verdict assumes none of them is named "OK" or
  "Cancel", which holds on today's home page.
- The fake keypad lists the dots `""` and the label as separate entries. Firmware
  uses one label for both. The judge does not depend on the difference.
- The end-to-end wake fake does not swallow or blank the next `click_by_name`.
  It also does not model a backdrop cancel when the panel is awake.
- The end-to-end wake fake clears `injected` on every sleep, so only taps in the
  last window can be seen.

## Findings

### HIGH
None.

### MED
None.

### LOW-1: the ERROR_HOLD wake path is untested (carried over from FX2 LOW-3)
Mutation X6 makes the wake treat ERROR_HOLD as ON, so it never taps in
ERROR_HOLD. It was MISSED. No test feeds `power_state=ERROR_HOLD`, or any
`power_state` value at all, to `_lcd19_wake_if_blanked`. Add a case that gives
`power_state=2` and asserts that a tap is sent, and a case that gives
`power_state=0` with `screen_on=False` and asserts that no tap is sent.

### LOW-2: the fake's short-OK no-op is not pinned by any test
Mutation X12 restores the old fake behaviour, where OK on a short entry is judged
as a wrong PIN. It was MISSED. `PinKeypadUiTest` was changed to match
`ui_lcd_keypad.c`, but no test presses OK with fewer than 4 digits. Add one that
asserts the label and state stay the same.

### INFO-1: the "role below min_role" example in a comment is wrong
The comment on the `closed_no_confirm` branch in `cases_lcd.py`, and the matching
test docstring, give "granted role below min_role" as the example cause. Start
requires USER, the lowest role, so that cannot happen for Start. The real causes
are confirm OOM, an external relock or credential write, or a defect.

### INFO-2: rare false-FAIL paths for `closed_no_confirm`
Three rare events could each produce a false FAIL:
- the LCD session expiring or a policy change during the case;
- a credential write from another client;
- an OOM when the confirm is allocated.

In addition, `_lcd19_overlay_raw` treats a truncated non-empty listing as a real
read. All of these are low probability, so the FAIL is still the right verdict.

### INFO-3: unknown `power_state` values count as not ON
If a future firmware adds a new `power_state` value, the wake will tap on it. If
the panel is awake in that state, the tap lands on the backdrop and cancels the
keypad. That fails safe, as described under Check 2.

### INFO-4: the `screen_on is None` guard is reachable only from fakes
The real `devices_touch` decoder always returns a bool for `screen_on`. The guard
is harmless.

### INFO-5: the end-to-end wake test is weak
The test only sees taps in the last sleep window. It does not model an awake
backdrop cancel. Mutation X5 (never tap) is caught only through the
`right_pin_retry_wake` assertion.
