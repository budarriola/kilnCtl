# Review: LCD19FX7 (0f777c012, a6d475e8b) -- 2026-10-12

This is an adversarial review of the LCD19FX7 fix as it landed on origin/dev. The code is in `0f777c012`
("wip: stack-margin check hardening (LCD19FX6)"), and `a6d475e8b` adds the doc follow-up. Together they fix

The fix changes four things:

- **`tools/lib_code_only_lines.ps1`:** the per-character PowerShell stripper is replaced by one compiled
  .NET regex. Results are cached per full path and mode.
- **`tools/check_stack_margin_registration.ps1`:**

  - each recovery file's blank-literal call count must equal its match count;
  - there is a recovery create floor of 5;
  - non-literal creates are pinned by their first argument;
  - `$exemptCreatePin` pins each exempt name to `file|task function`;
  - `ota_confirm` moves from the exemption lists to `$requiredNames` (`# liveness: boot-once`).
- **`firmware/KilnFW/App/main_network_http.c`:** registers `ota_confirm` with `stack_margin_register()`. The
  task clears its handle before each `vTaskDelete(NULL)` and when the create fails.
- **`firmware/KilnFW/App/test/check_all_task_stack_budgets.py`:** adds an `ota_confirm` row with a 3760 B
  ceiling.

## MED-1: the recovery floor fails a pytest on origin/dev -- FIXED (lcd19fx8: floor applies only without -RecoveryDir)

The new floor (`$minRecCreated = 5`) runs on every call, including when `-RecoveryDir` points at a test
fixture. `tools/PcTools/tests/test_stack_margin_registration_recovery.py::test_reported_recovery_task_passes`
passes a temporary `-RecoveryDir` that holds a single reported task and expects exit 0. It now fails:

```
only 1 recovery-image xTaskCreate*() site(s) found (floor 5)
```

I ran this with `uv run pytest` in the worktree. `test_task_liveness.py`, `test_stack_margin_baseline.py` and
`test_stack_margin_registration_recovery.py` gave 48 passed and 1 failed, and this test was the one failure.
The fix commit did not touch that test file. Nothing on origin/dev (`7daf20324`) has changed it or the check
since.

**Fix:** apply the floor only when `-RecoveryDir` is not given, which is the real tree. A test-supplied
directory proves the pattern by its own assertions. Alternatively, make the floor a parameter that the test
sets to 1. Keep the floor for the default directory: `C03` and `C10` below show it catches a lost recovery
create.

  - I copied the pre-fix `Get-CodeOnlyLines` into a harness as `Get-OldCodeOnlyLines`. I then compared both
    functions case-sensitively (`-cne`), in both modes (plain and `-BlankLiterals`), checking line count and
    every line.
  - The comparison covered 1516 files: the 1493 `.c`/`.h` files under `firmware/` and `tools/`, plus 23 edge
    fixtures. 0 differ.
  - The fixtures covered:
    - a macro line continuation;
    - `"//"` and `"/*"` inside strings, `'"'` and `'\\'`;
    - comment-like text inside comments;
    - a backslash-newline inside a string;
    - CRLF, lone CR and mixed line ends;
    - an unterminated string, an unterminated char and an unterminated block comment;
    - an empty file, a lone newline and a backslash at EOF;
    - a BOM, ANSI bytes and surrogate-pair characters.
  - As a self-test, a copy with the char-literal alternative disabled produced 4 differing files, so the
    harness can see a difference.
  - Both strippers still diverge from C in the two ways REVIEW_LCD19FX6 INFO-1 already records: a `//`
    comment ending in `\` leaves the next line visible, and a string continuation blanks the next line.
    These are shared and unchanged.
- **The cache cannot serve stale content in practice.**
  - The cache key is the full resolved path plus the mode.
  - `$script:CodeOnlyCache` is reset every time the lib is dot-sourced.
  - Every consumer runs the check in a fresh process: `run_all_checks.ps1` uses `Start-Process`, and the
    pytest files and the uri-cap tests use `subprocess` or `& powershell`.
  - No caller mutates a returned array.
  - Mutant `T05` (cache key ignores the mode) is caught.
- **Registering `ota_confirm` is correct for a self-deleting task.**
  - `stack_margin_read` loads the handle slot fresh on every read.
  - The task clears `s_ota_confirm_task` on both exit paths before `vTaskDelete(NULL)`, and the create-failure
    branch clears it too. This is the same pattern `pico_auto_update` already uses.
  - The create is unconditional on every boot. `main_network_http_bringup()` is called from `main.c` with no
    early return before it.
  - So a `boot-once` ABSENT result in `check_task_liveness` means the create or the context alloc really
    failed. Either failure also raises a `startup_fault_note`.
  - The register size (5120) matches the create literal, and mutants `C09`/`C13` prove the size comparison
    covers it.
  - `test_task_liveness.py` and `test_stack_margin_baseline.py` pass.
- **The pins work.** Each of these fails the check with its own message:
  - reusing an exempt name in another file;
  - changing an exempt create's task function;
  - swapping a pinned non-literal create's first argument;
  - wrapping the name in parentheses.

## INFO

- **INFO-1: race when reading a self-deleting task's handle.** This class is pre-existing and shared with
  `pico_auto_update`.
  - `stack_margin_read` can load a non-NULL handle just before the task clears it and calls
    `vTaskDelete(NULL)`.
  - It can then call `uxTaskGetStackHighWaterMark()` on a TCB the idle task is freeing.
  - The window is a few instructions wide, and it opens only once per boot.
  - A fix would take the read and the clear under the same critical section, or use a suspend-scheduler
    read.
- **INFO-2: the `Add-Type` guard can keep an old type.** The `-as [type]` guard keeps an older
  `KilnCodeOnlyStripper` in a long-lived PowerShell session that dot-sources an edited lib. No consumer does
  that today, because every one runs a fresh process.
- **INFO-3: a missing file now throws.** The old stripper returned an empty result under `Continue`. The new
  one throws: `Resolve-Path` reports an error and returns nothing, so `Get-Content -LiteralPath $null` fails
  parameter binding. That fails loud and is harmless.
- **INFO-4 (FIXED lcd19fx8: tools/check_code_only_lines.ps1): no unit test pins the tokenizer.** Mutants `T01`, `T06`, `T07` and `T08` survive the check
  because the current tree never feeds the stripper those inputs. Those inputs are a char literal holding
  `"`, an escaped quote that matters, CR line ends, and an unterminated block comment. The 23 fixtures above
  (in the reviewer's scratchpad) would catch all four if they were committed as a pytest that compares the
  lib's output to expected text.
- **INFO-5: a `#define` alias of `xTaskCreate` bypasses the check.** Mutant `C04` adds an alias call,
  `XTC(sneaky_task, "sneaky", ...)`, which is never registered, and the check passes. This is out of the
  check's documented scope, and no such alias exists in the tree.
- **INFO-6: the code commit carries a `wip:` subject.** The code landed as `0f777c012`, "wip: stack-margin
  check hardening (LCD19FX6)". The descriptive message and the equivalence and timing evidence sit on the
  docs-only `a6d475e8b`, so `git log` or `git blame` on the changed scripts points at a WIP subject.
