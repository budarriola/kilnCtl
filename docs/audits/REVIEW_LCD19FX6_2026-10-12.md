## Verified

- **The stripper is correct on every case asked about.** I ran it on a scratch file containing each of
  these. Every one is handled as C handles it:
  - `"x\"y // c"`
  - `'\\'` followed by a create on the same line
  - `'"'` and `'/*'`
  - `"\\"`
  - adjacent strings
  - `"/* not */"`
  - a multi-line block comment
  - `u8"//x"`
  - `L'\''`

  Raw strings are C++ only, and digraphs do not form comment or quote tokens, so neither applies.
  The remaining divergences are listed under INFO-1. Each of them leaves a site more visible than C
  would, or makes the check fail loud. None of them hides a site.
- **On the real tree, the switch only revealed sites. It hid nothing.** I compared the old and new
  strippers over all 1085 `.c`/`.h` files under `firmware/KilnFW/App`, `firmware/hwAbstraction` and
  `firmware/KilnFW_recovery`. 577 lines differ, and in every one the old stripper had cut code that
  the new one keeps:
  - `main_network_http.c:560-807`: 248 lines hidden after `"/api/logs/*"`. This range holds the
    `ota_confirm` create.
  - `sim_credibility_gate.c:519-674` and `firing_score_from_capture.c`: hidden after
    `"logs/coupling/*.jsonl"`.
  - `test_update_url.c` and `test_http_auth_enforce.c`.
  - Single-line `"http://..."` tails in several files.

  I diffed the four checks' output before and after. The uri, bridge and uart outputs are identical.
  The stack check's only changes are 47 to 48 create sites and 23 to 24 skips, the added one in each
  case being `ota_confirm`.
- **The new count and ratchet checks fire with their own messages.** See the negtest table. R4 and R5
  both stop at `no readable literal task name`:
  - R4 adds a second non-literal create in `http_async_job.c`, giving delta 2 against an allowance
    of 1.
  - R5 replaces `"ota_confirm"` with a macro name in a file that is not on the list.

  R7 removes the `ota_confirm` skip entry and is caught by the set ratchet. R9 changes a reason's
  class and is caught by the class check.
- **Second creates through the old blind spots are caught.**
  - R1 puts a `"/*"` string before a second create.
  - R2 casts the first argument.
  - R3 puts a `'\\'` char and an `&fn` before a second create.

  All three are caught by `STACK MARGIN STACK-SIZE CHECK FAILED` (4096 against 2048).
- **The uri cap check sees routes placed after literals that contain comment tokens.** U1 (`"/*"`)
  and U2 (`"a\"//"`) each add one route with the cap lowered to 176. Both are caught by the check's
  own `below the real worst-case route count (177)` throw.
- **Every CAUGHT below comes from the check's own throw, not from a crash.** I read each log. R8's
  message is the pair-count floor rather than the dead-alias throw; see INFO-3.

## LOW-1: the recovery-image section still matches only a bare-identifier first argument

**Location:** `tools/check_stack_margin_registration.ps1:777`, the `$recCreateRe` pattern
`'xTaskCreate\w*\s*\(\s*[A-Za-z_][A-Za-z0-9_]*\s*,\s*"([^"]+)"'`.

The fix for LOW-2 widened `$createPattern2` (`:496`). It did not widen the recovery section's own
pattern, and it gave that section no non-literal call count either. The recovery section also prints
how many sites it saw, but has no floor on that number.

**Failure scenario:** someone adds `xTaskCreate((TaskFunction_t)worker, "rec_worker", 2048, ...)` to a
recovery file that never calls `uxTaskGetStackHighWaterMark()`, for example `recovery_http.c`.
Nothing reports that task's stack margin, and the check still passes. It prints "4 xTaskCreate*()
call site(s)" where it printed 5 before, and nothing compares that number.

**Evidence:** R6, which makes this exact edit, was MISSED (exit 0). R6b, the same edit without the
cast, was CAUGHT by `A recovery-image task is created without any stack high-water-mark reporting`.

**Fix:**
- Use the `$createPattern2` form here.
- Add the same `\bxTaskCreate\w*\s*\(` count on `-BlankLiterals` text.
- Add a floor on `$recCreated`.

## LOW-2: `ota_confirm` is exempt from both stack checks but is not a one-shot task, and nothing measures it

**Locations:**
- `tools/check_stack_margin_registration.ps1:545` (`$exemptCreatedNames`) and `:613`
  (`$stackSkipAllowed`).
- `firmware/KilnFW/App/main_network_http.c:153`, `:180`, `:266` and `:766`.

The new skip entry is consistent with the existing "create site only" class, and the
`$exemptCreatedNames` entry predates this change. The `$stackSkipAllowed` row is therefore justified
as a description. What the two entries describe is a real measurement gap, though, and both texts
overstate how safe the task is:

- **It is not one-shot.** `main_ota_rollback_confirm_task` loops `for (;;)` (`:180`). It retries
  `boot_guard_mark_healthy()` every 500 ms until the clear verifies, and keeps polling while
  nvs/web/ota are not all true (`:291`). If the clear never verifies, the task lives for the whole
  boot.
- **It is the heaviest of the unregistered helper tasks.** Its stack is 5120 B. After the clear it
  runs `update_http_stale_stage_check()`, which does a PSA SHA-256 with a 1 KB work buffer.
- **Its only measurement is lost.** The task's only measurement is one `ESP_LOGI` of its high-water
  mark (`:266`). `docs/audits/boot_guard_recovery_loop_2026-09-08.md:264` records that `ota_confirm`'s
  `ESP_LOGI` lines do not reach the captured log, because uart_log_bridge drops them.
- **No other check covers it.** It has no stack_margin registration and no row in
  `check_all_task_stack_budgets.py`.

**Failure scenario:** a change to the stale-stage check makes it use more stack, for example a larger
work buffer or a deeper PSA call. `ota_confirm` then overflows only on boots where the stage check
runs. Nothing grades its margin, and the one log line that would show the shrinking margin never
arrives. This is the stack-overflow class that bricked the board into recovery three times.

**Fix:**
- Register `ota_confirm` with `stack_margin_register()`, using the comparable boot-once task
  `pico_auto_update` (`:161`, `# liveness: boot-once`) as the precedent, and add it to
  `$requiredNames` tagged `boot-once` or `on-demand`. Then drop both exemptions.
- Correct the "one-shot ... self-deletes" text in both entries.

## LOW-3: the stack check roughly doubled in run time

**Location:** `tools/lib_code_only_lines.ps1:11-41`. The check strips files at
`check_stack_margin_registration.ps1:229`, `:441`, `:512`, `:514`, `:643`, `:679` and `:781`.

I ran these sequentially on this machine, under 80%+ background CPU load from other sessions:

| Check | Before (`4c7bd00af^`) | After (`1b95ab190`) | Earlier run, heavier load |
|---|---|---|---|
| check_stack_margin_registration | 34.8 s | 65.4 s | 73.0 s / 158.6 s |
| check_uri_handler_cap | 7.6 s | 13.3 s | 14.1 s / 16.8 s |
| check_bridge_reject_reason | 0.7 s | 1.5 s | 6.9 s / 1.8 s |
| check_uart_version_independence | 0.6 s | 1.2 s | 3.4 s / 2.5 s |

**Cause.** The per-file stripper itself is not slower: over the 1085 files, the old one took 56.6 s
and the new one 37.9 s. The extra time comes from the number of passes. The stack check now strips
every `drivers/` file four times: registration, the cross-check plain and `-BlankLiterals`, and the
size loop. On top of that are the hwAbstraction and recovery passes. Each pass is a per-character
PowerShell loop.

**Risk.** Phase 2's per-check cap is 900 s, so there is no timeout risk, and the `# checkcache: ok`
marker skips the check on clean-tree reruns. It is still the slowest phase-2 check, and it makes
every dirty-tree run longer.

**Fix: a .NET regex tokenizer over the whole file.** I tested a prototype that runs one compiled regex
and keeps only the newlines of each comment:

```
"(?:\\.|[^"\\\n])*(?<cq>")?|'(?:\\.|[^'\\\n])*(?<cq>')?|//[^\n]*|/\*[\s\S]*?(?:\*/|$)
```

It produced the same output as `lib_code_only_lines.ps1` on all 1085 files in both modes, except for
one line. On that line, PS 5.1's `Get-Content` read a non-ASCII byte as ANSI. The prototype took
3.3 s against 37.9 s. Use it, and strip each file once per mode into a cache keyed by path.

## INFO-1: the remaining stripper divergences fail visible or loud

- A `//` comment ending in `\` continues onto the next line in C. The stripper leaves the next line
  visible. That over-reports and never hides a site.
- A string continued with backslash-newline loses its string state at the line end. If the next line
  holds a create, `-BlankLiterals` blanks it and the plain pass does not. The per-file count then
  mismatches and the check fails loud.
- An apostrophe in `#error`/`#warning` text (`#error don't /* x`) is read as a char literal, so it
  swallows the `/*` that C would honour. The following lines stay visible, so again this
  over-reports.
- A C23 digit separator (`4'096`) is mis-lexed. The size becomes unevaluable, which makes it a new
  skip, and the ratchet fails loud.

## INFO-2: the one-per-file non-literal allowance can be traded

**Location:** `tools/check_stack_margin_registration.ps1:504-508`.

A second non-literal create in an allowed file is caught (R4). So is any literal create, because it
is matched normally. What the allowance cannot see is a swap: the wrapper's own create becomes
literal or disappears, and a new non-literal create appears in the same file in the same commit. The
delta stays 1.

Separately, callers that pass a literal name into the wrappers (`http_async_job_start(...)` and
`uart_bridge_ext`) are never cross-checked against registrations. That gap predates this change.

A create inside a macro body counts once, at its definition. Its expansion sites are invisible.

**Fix:** also pin the allowed site by its first argument, for example
`http_async_job.c = 'http_async_job_task'`.
