## Findings

### MED-1: HP-03 and HP-07 restores now always get 409 `zones_config_stale`

Where: `tools/PcTools/src/kilnctrl/bench_test/cases_heat.py`

- HP-03 builds `restore_body` at line 948.
- HP-07 builds `restore_body` at line 1499 and calls `_restore_zone_max_temp`/`_post_zones_restore` at line 1583.
- `_post_zones_restore` is at line 1130.

Both cases build `restore_body = build_post_body(snapshot, {})` from the pre-case GET. Since webfx5, `build_post_body` adds `expected_generation=<snapshot generation>`. The case then POSTs its own change (`on_off_body`, `limited_body`), and that commit bumps `s_config_generation`. Every restore attempt, the first and the retry alike, therefore carries a stale generation, and the firmware answers 409 `zones_config_stale` without writing anything.

The result is that HP-03 leaves the zone at `zone_type` 1 (on/off), and HP-07 leaves `max_temp_c` lowered. This is the exact HP-02 failure shape (2026-09-25..27): a 3-zone firing would never close that zone's relay. The case does fail loudly ("restore by hand"), so this is not silent, but it fails on every run.

Fix: build the restore body inside `_post_zones_restore` from a fresh `get_zones()` on each attempt. Take the snapshot's `zone_type`/`max_temp_c` values as overrides, or GET fresh and copy only the generation over. Do not strip `expected_generation` entirely: a fresh GET keeps the guard working. Add a fake-board test in which the case's POST bumps the generation and the restore must succeed.

### MED/LOW-2: relay names and types bypass both lost-update guards

Where:

- `firmware/KilnFW/App/drivers/persist/zones_config_accessors.c:585` (`zones_config_set_relay_name`)
- `zones_config_accessors.c:633` (`zones_config_set_relay_device_type`)
- `firmware/KilnFW/App/drivers/http/zones_http_post.c:835-836`

Every other `zones_config_set_*` setter bumps `s_config_generation`. These two do not. POST /api/zones, however, commits `s_relay_names.cfg = tmp_relay_names` as a whole struct, and `tmp_relay_names` is seeded from the live state at parse time.

The setters' only caller outside the file is the backup import (`backup_import.c:3430/3433`). If a backup import lands while a zones page is open (or between a tool's GET and POST, or during an in-flight POST's Pico ceiling raise), the next zones save silently reverts the imported names and types. Neither `expected_generation` nor the internal commit re-check (`zones_config_changed_concurrently`) can see it, because the generation never moved.

Fix: bump `s_config_generation` in both setters, under `zones_cfg_lock()` as the others do.

### LOW-3: the zones page can 409 on its own adaptive-tune clicks

Where: `firmware/KilnFW/App/drivers/http/zones_page.html:4243` and `:4269`

The adaptive-tune Enable and Revert POSTs reach `zones_config_set_*` (via `adaptive_tune_set_enabled()`/`adaptive_tune_revert()`), which bumps the generation. The page then calls only `pollAdaptiveTune()` and does not refresh `current.generation`. The next Save on the same page gets 409 `zones_config_stale`, with text blaming "elsewhere (autotune, another page or a tool)". No data is lost, but the operator has to reload and redo the edit.

Revert also changes the PID gains on the board. If the page form still holds the pre-revert gains, the 409 is the correct outcome, so a blind refresh is the wrong fix.

Fix: after either POST, call `reloadUnlessDirty()` (the convention used for sweep completion and autotune accept). When the form is dirty, say that the page will need a reload.

### LOW-4: the RAM-only tokens can collide across a reboot

`s_config_generation` starts at 1 at every boot. `s_slot_gen[]` is also RAM-only. A page loaded before a reboot holds a token that a fresh counter can reach again after the same number of bumps:

- Zones has no second identity check, so a matching number lets a stale page overwrite.
- Profiles checks `expected_name` only on the first save after load. `profiles_page.html:2335` sets `editingName = null` after a successful save, so later saves are pinned by the rev alone.

This needs a reboot plus an exact count match, so it is unlikely. Fix (optional): seed both counters from a per-boot random or boot id in the high bits, or add the boot id to the token.

### LOW-5: LCD profile edits are not guarded

Where: `ui_page_profile_builder_review.c:99` (`profiles_http_save(slot, ...)`), reached from `ui_page_profile_detail.c` edit.

The LCD path loads a profile, edits it, then overwrites it after a confirmation that shows the name only. It holds no `slot_rev`. A web save made between the LCD load and the LCD confirmation is overwritten silently. The window is long on a touch UI, but it needs two operators at once.

Fix (optional): capture `profiles_http_slot_rev()` at load and refuse in `profiles_http_save_ex` when it moved, or show "changed elsewhere, reload?".

### LOW-6: a profile delete on a rev-unknown slot now answers 500, not 409

Where: `firmware/KilnFW/App/drivers/http/profiles_edit_http.c:870`

persfx3 made the plain `cfg_fs_http_persist_failed()` never send the 409 (MED-2: no blanket 409 from another store's degradation). The delete handler still calls the plain form. A delete refused because the slot's rev floor is unknown (`nvs_erase_slot`, profiles_http.c:1467, `ESP_ERR_INVALID_STATE`) used to answer 409 `store_unreadable_at_boot` and now answers 500 "could not be saved to flash". The text is misleading and sends the operator after flash hardware.

Fix: thread the error through `PROFILES_DELETE_PERSIST_FAILED` and use `cfg_fs_http_persist_failed_state(req, s_profile_rev_unknown[id], err, -1)`, as the save path does at line 782. The `kiln_cfg_http.c` and `diagnostics_http.c` plain callers were not checked for a refusal they could now mislabel.

### LOW-7 (test gap): the persfx3 LOW-1 test is vacuous

Where: `firmware/KilnFW/App/test/test_zones_http.c:2185` asserts "persfx3 LOW-1: no Pico ceiling write at all for a POST that can never commit".

Negtest mutation `zones_undecided_precheck_off` changed the new early-out at `zones_http_post.c:699` to `if (0)`, and the run was **MISSED** (exit 0). The commit-point check still answers the 409, and the ceiling-writer count does not move even without the fix, so the test never forces a raise. Raising the live config's `max_temp_c` to 100 is not enough when the body/cached-ceiling arrangement needs no raise.

Fix: make the body's `max_temp_c` exceed the cached Pico ceiling (seed the ceiling cache low), confirm with the precheck removed that `s_ceiling_writer_calls` moves, then restore.

### LOW-8: retired mode has no NVS fallback for a store whose file was never written

Where: `firmware/KilnFW/App/drivers/persist/pref_cfg_fs.c:488` (retired branch), used by the five stores.

What is correct:

- NVS is erased only after `used_file`, which means the cfg file was read and passed the store's validator. The erase is a key-by-key erase with commit and an existence read-back (`legacy_nvs_erase.h`).
- No path erases NVS before the file is proven good.
- An absent, corrupt or unreadable file, or an unmounted cfg, gives defaults and leaves NVS untouched. The data stays recoverable by downgrade.

Trade-off to record:

- A board that boots this firmware with a valid NVS copy and no file now runs defaults, with a log-only warning. Such a board is one that skipped every dual-write release, or whose `cfg` was formatted. The lost values are the aux rules, ramp assist, ki baseline, iter-tune results and the CT verdict.
- That is the owner-chosen safe direction for aux (an operator-disabled rule cannot come back), but for ki baseline, iter-tune and the CT verdict it silently drops learned data.
- `aux_outputs_cfg.c` still quarantines on `nvs_newer` even though NVS is never written again. Harmless today.

Suggested follow-up: surface "frozen NVS copy present but not adopted" in GET /api/cfgfs or readiness, so the loss is visible.

### LOW-9: `legacy_nvs_erase_keys` treats any probe error as "absent"

Where: `legacy_nvs_erase.h`

`hal_kv_key_exists() != HAL_OK` skips the key, and the verification loop counts only `== HAL_OK` as "still present". A read error therefore reports ESP_OK and the key may survive. The impact is low: the file is authoritative and retired mode never re-adopts NVS. A hal_status other than NOT_FOUND could still be logged.

### Info

- **Wire contract**: `expected_generation`, `expected_rev` and `expected_name` are optional, so older clients are unaffected. `generation` and `slot_rev` are additive response fields. Older firmware ignores the new POST fields (the PcTools comment says so). The changed 409 texts keep their `error` keys.
- **Profile writers**: every profile writer bumps `s_slot_gen` (POST, `profiles_http_save_ex` used by backup import and the LCD, delete, retarget), so the web guard sees them. Only LOW-5 (the LCD itself does not pin) remains.
- **MCP zones writers** all GET, build and POST immediately, so the token is fresh. The bench HP cases are the exception (MED-1). `pid_validation_harness.py` builds from a GET taken just before it POSTs.
- **PcTools profile writers** do not pin `expected_rev`. That is the old behaviour and acceptable.
- **uifx**:
  - `pause_reason` values match the emitters (`pico_reboot_undecided`, `pico_fatal_reboot`, `heat_grant_unconfirmed`).
  - `profile_executor_get_status` memsets its output first.
  - The web text is escaped via `kcEscapeHtml`.
  - The MCP line is printed only for state 1/2.
  - No consumer still matches the old "holds the zones claim" text.
- **Stack**: `char pause_buf[96]` was added in `ui_home_refresh_cb` (`ui_page_home_refresh.c:423`), the LVGL task's deepest frame (4880 B ceiling in 8192 B). It is not measured here; the coordinator's full stack-budget check should confirm the headroom.
- **Comment nit**: `profiles_catalog_http.c:495` says `slot_rev` is "read before the copy below", but the detail GET reads live `s_profiles` with no copy. The read order (rev first) is the safe one, so only the wording is wrong.
