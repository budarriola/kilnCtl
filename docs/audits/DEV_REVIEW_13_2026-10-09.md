## bc334d45: factory reset backup-first and call log

### Coverage of factory-reset paths

All factory-reset senders were checked: every reference in `tools/` and the
firmware entry points. Firmware has two entry points:

- UART `SYSTEM_CMD_FACTORY_RESET` (0x02) on `UART_TASK_ID_SYSTEM`
  (`uart_bridge_system.c` -> `factory_reset_execute()`).
- HTTP `POST /api/factory_reset` (`factory_reset.c`).

PcTools sends the UART command from three places, and all three now back up
first:

- `actions.py` `_factory_reset`. MCP `run_action` also reaches it.
- `mcp_server_ui_test.py` `factory_default_then_load_preset`.
- `gui_danger_zone.py`.

The remaining references are in `selfcheck_actions` and tests. The function
`codec_encode_frame` only builds hex and does not transmit, so it is not a
sender. No PC tool POSTs `/api/factory_reset`; only the browser
`settings_page.html` does, and it is outside PcTools. Nothing under
`tools/PcTools/scripts` or the web-commission `.mjs` drivers sends a factory
reset.

The guard refuses the reset on any export or file-write failure. Only
`skip_backup is True` (exactly True) skips it.

### F1 (MED): wrap test passes without the wrap

`test_registry_entries_are_wrapped_at_import` asserts only
`hasattr(entry.fn, "__wrapped__")`. But `mcp_server_core._tool()` already
applies `functools.wraps`, so every registry entry has `__wrapped__` whether or
not `call_log.install()` ran.

Negtest `registry_not_wrapped` commented out the `_call_log.install(...)` call
in `mcp_server.py`. Result: **MISSED**. The test needs to check something only
the call-log wrapper provides, for example a marker attribute set by
`wrap_direct`, or a tool invocation that produces a log line.

### F2 (LOW): no test that a log failure is harmless

`log_call` wraps its entire body in `try/except Exception: pass`. Negtest
`log_errors_propagate` re-raised inside that handler. Result: **MISSED**; no
test exercises the path.

The behaviour itself is correct. I checked it by hand: with a log dir whose
parent is a file, the wrapped tool still returned its result, and positional
args passed through.

### F3 (LOW): no GUI test

Negtest `gui_no_refuse` made the Danger Zone proceed after a failed backup.
Result: **MISSED**; no test covers the GUI path.

### F4 (LOW): GUI blocking and default host

- `gui_danger_zone.py` calls `factory_reset_guard.backup_before_reset()`
  synchronously on the Tk thread, so the UI freezes for up to the HTTP timeout.
- It passes no host, so the guard uses `ota_http.OTA_AP_DEFAULT_HOST`. That
  value is resolved by `host_resolve` at import time, not taken from the GUI's
  own host setting. The `actions.py` path behaves the same way when `host` is
  omitted.
- By contrast, `factory_default_then_load_preset` resolves the host per call
  via `_ota_resolve_host(host)`: explicit host first, then the STA IP, then the
  default.

A board reachable only at an address the import-time resolver did not pick
fails the backup, so the reset is refused. That is fail-closed, so not unsafe.

### F5 (LOW): same-second overwrite

The backup file is
`logs/backup_export/kilnctl_backup_prereset_<%Y%m%dT%H%M%SZ>.json`. A second
reset within the same second overwrites the first backup, which could be the
only pre-reset copy.

### Call log: arguments, failure isolation, threading

- **Values are never logged.** `log_call` writes the tool name and the kwarg
  **keys** only. `wrap_direct` passes only `kw` keys. Unknown keys are refused
  by `ToolRegistry.invoke` before `entry.fn` runs, so a key cannot carry a
  value through. Negtest `log_values` (log the values) was **CAUGHT**.
- **An unwritable log dir cannot break a call.** See F2.
- **No double logging.** Facade tools (`kiln_call`/`kiln_batch`) are not
  wrapped; only registry `entry.fn` and the KEEP tools (`connect`) are.
- **Threading.** Each line does its own open, append and close. FastMCP runs
  sync tools on its event loop, which serializes them. Background jobs
  (`bench_test_start` and others) call the tool functions directly, so those
  calls are not logged.
- **F7 (LOW):** with O_APPEND on separate Windows handles, lines could in
  theory interleave under true concurrency. This has not been observed.
- **F6 (LOW):** a call that is refused for a gate flag or a bad argument fails
  before `entry.fn` runs, so it leaves no audit line. Arguably, those are the
  calls an audit log most wants to record.
- Tests that invoke tools write into the real `logs/mcp_calls/noport_*.log`.
  That path is gitignored, so this is harmless.

## f1cb3604: backup import topology precheck

`backup_import_zone_topology_precheck` runs in pass 1, after
`profiles_precheck` and before the `dry_run` return. It rejects any zone entry
with `index >= zones_config_get_thermo_count()`, the same condition pass 1b
applies later (~line 1338), so the two cannot disagree on the same input.
Non-finite numbers are already rejected by `backup_json_field_num`.

`thermo_count` could change between pass 1 and pass 2. Pass 2 still re-checks,
so that window can only produce the old 500, never a bad write.

Negtest `topology_precheck_disabled` (precheck always succeeds) was **CAUGHT**
at `test_backup_import.c:5124`: "the refusal is not a partial write (no 500)".

### F8 (LOW): other pass-1b failures remain partial writes

The precheck covers only out-of-range indices. These pass-1b failures still
fire after the kiln_configs and aux phase-1 commits:

- missing or negative pid fields
- duplicate zone index
- too many zone entries
- profile parse errors inside `backup_import_apply_two_pass`

Each still yields a 500 partial write. The commit message claims only the
topology case, so this is not a regression. Moving the full pass-1b parse ahead
of any commit would close the class.

## 3b3b9dce: httpd stack shave

The large JSON buffers moved into `noinline` helpers, and each buffer is a
stack local in its helper, not static, so the handlers stay reentrant. The
helpers are:

- `start_send_gate_refusal` and `start_send_run_failure` in
  `dashboard_exec_http.c`
- `autotune_send_gate_refusal` and `autotune_send_run_failure` in
  `dashboard_autotune_http.c`

The helper frames are not live at the same time as the handler's deeper
callees.

In `kiln_cfg_store.c`, `populate_pico_half_and_hash` moved its two 896 B
`canonical[]` buffers to `persist_scratch_alloc`. Both are freed on every path.
An allocation failure is handled like an encoding failure: the hash is left
unchanged, or the slot is marked not captured. It is never treated as success.

### Measured, not guessed

I ran `check_httpd_task_stack_budget.py --elf` against two builds:

- **`3b3b9dce` build** (author worktree ELF at clean HEAD `3b3b9dce`; it
  contains the new helper symbols): `profile_exec_start_post_handler` 4496 B,
  honest free 1896 B of 8 KB (23.1%, LOW). The handler's own frame is now
  448 B. The next deepest handlers are `autotune_start` 4320,
  `api_readiness_get` 4064, `security_post` 4016 and `ota_esp_status_get`
  3936.
- **Pre-fix build** (`C:\wt\checkbuild_e77db94fc2`): 5248 B (14.0%, CRITICAL).
  It fails against the new ceiling, so the ratchet bites.

### F11 (INFO)

- `CEILING_BYTES` equals the measurement, so any growth fails the check. That
  follows the ratchet convention; it is noted only so nobody mistakes the
  failure for a regression.
- `autotune_send_run_failure` is absent from the ELF because `-fipa-icf`
  folded it into the identical `start_send_run_failure`. That is harmless.
