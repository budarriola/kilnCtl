# Review: KilnFW_recovery end to end, 2026-10-18 (HIGH 0, MED 0, LOW 1, INFO 4)

Scope: `firmware/KilnFW_recovery/main` on origin/dev: entry and boot order (`recovery_main.c`), SoftAP and passphrase (`recovery_wifi.c`, `recovery_passphrase.h`, `recovery_lcd.c`), HTTP upload routes (`recovery_http.c`, `recovery_upload.c`, `recovery_pico.c`), Pico link keepalive (`recovery_keepalive.c`, `recovery_pico_proto.c`), and the exit back to the app. Review only, no board. Recovery routes are unauthenticated by owner decision (2026-10-02); not flagged.

## RE-01 LOW: no restart fence after a route schedules a reboot
`recovery_http.c` `restart_soon()` (used by `/api/ota/esp` success, `/api/recovery/exit`, `wifi_reset`, `sw_reset`) starts a task that calls `esp_restart()` 500 ms later. Nothing marks the image as restarting. The AP allows 4 stations and httpd serves other sockets once the handler returns. So a second client's `POST /api/ota/esp` (or `apply_staged`) in that window passes `recovery_apply_busy()`, claims, and starts erasing/writing `app`. Then the restart lands mid-write. The boot target is already `app` (set and verified by the first request), so the bootloader finds an invalid `app` and falls back. Recovery stays bootable, so this is recoverable, but the first client was told "rebooting into the application" and the image it pushed or verified is gone. Fix: a `s_restart_pending` flag set before `restart_soon()`, checked by every mutating route (409, same as `refuse_while_applying`), and by the install/apply task before it claims.

## RE-02 INFO: RX-12 S6b LINK_DEAD during recovery: no source cause found
Checked against the Pico side:
- Frame: `rpp_build_frame` sends BROADCAST, src ESP(0) to dst SAFETY(2). `link_task_handle_raw_frame` refreshes `s_last_valid_frame_tick` for any cleanly decoded ESP to SAFETY frame, before the command switch (`link_frame_counts_for_liveness`). Host test `test_keepalive` decodes it with the same CommonFW codec.
- Wiring: UART1, TX GPIO5, RX GPIO4, 230400, no TXD inversion, fault GPIO6 driven low. This matches the app's Kconfig defaults and `safety_link.c` (inversion removed on both ends with the ADuM1201).
- Timing: the keepalive starts first in `app_main`, right after the bounded relay hold, which is at most a few hundred ms of retries. It sends every 2 s and stands down only while the Pico relay holds the UART. The window is `RPP_KEEPALIVE_MAX_MS` = 15 min, longer than the 6 min observed, and the Pico hard tier is 120 s.

The evidence instead suggests the ESP was not running recovery `app_main` at all. The board answered ping on its home-Wi-Fi STA address, and recovery never creates a STA netif (RX-12). JTAG `set_otadata_app` was also needed to get back. Both point to a wedged app after the `recovery_boot` request, or a boot that never reached recovery. Next recovery bench run: capture serial for `KilnFW recovery image starting` and `rec_keepalive` lines, and read the Pico's `link_task` valid-frame age during the session. The keepalive never reads Pico replies, so there is no observable that it works on target. A `keepalive_sent` and last-write-error field in `/api/recovery/status` would make this checkable over the AP.

## RE-03 INFO: passphrase generation and handling are sound
12 characters from a 32-symbol alphabet (60 bits), drawn with `bootloader_random_enable()` + `esp_fill_random()` before `esp_wifi_init()`. The raw bytes and the `wifi_config_t` copy are wiped (`secure_zero`). The log line prints the SSID only. The passphrase is held in the LCD's RAM copy and shown only there and in the QR. It is never in NVS (`esp_wifi_set_storage(RAM)`, refused otherwise) and never in any HTTP response. The alphabet still contains look-alike pairs (5/S, 2/Z, 8/B) that the bench glyph reader found ambiguous. Dropping them (for example a 28-symbol set and 13 characters) would keep 60+ bits. This is optional, not a defect.

## RE-04 INFO: upload bounds and concurrency are sound
`/api/ota/esp`: claims `recovery_app_write_claim()` for the whole stream, refuses while the Pico relay is busy, uses `max_len = app partition size`, validates the first chunk before any write, and sets boot only after the full verify. `/api/recovery/pico/upload`: rejects 0 bytes and anything over `RPP_SLOT_SIZE`, needs PSRAM and an internal-RAM floor, reserves `s_busy` under its lock before the malloc, reads with an overall deadline and a no-progress stall cut, checks CRC and vectors before the relay starts, and releases on every failure path. All handlers run on the single httpd task, so the only concurrency is with the relay/apply/install tasks, which are covered by the busy and claim checks (except RE-01's restart window).

## RE-05 INFO: exit path
`/api/recovery/exit` refuses while an apply or Pico transfer runs. It needs a valid and verified `app`, clears boot_guard before it touches otadata, supersedes any pending install request, then sets and reads back the boot partition. Minor: `rpp_pack_begin` mirrors `protocol_version 16`, while CommonFW is at 17. The receiver compares only against its minimum (7), so this is harmless, but the mirror is stale.
