## Findings, ranked

### HIGH-1: OT-E11 polls the recovery image on the application's LAN address, which it can never answer on

`tools/PcTools/src/kilnctrl/bench_test/cases_ota.py:2516-2539`: every tool call in the case
(`recovery_enter`, `recovery_status`, `recovery_push_esp_image`, `recovery_exit`, and the
`_settled_running` read at `:2572`) gets the same `ctx["host"]`. In a bench run that is the
application's LAN address. The recovery image is AP-only and never creates a STA interface
(`docs/RECOVERY_IMAGE_PLAN.md:122`). The bench PC can reach it only after joining its
WPA2 SoftAP, and no PcTools tool joins that AP (CLAUDE.md). So on real hardware:

1. `recovery_enter` succeeds and the board reboots into recovery, off the LAN.
2. `_ote11_wait_recovery` polls `recovery_status(host=<LAN>)` for 60 s. That returns an
   `error: ...` string, not an exception, so the case returns FAIL "recovery image never
   answered".
3. In the `finally`, `recovery_exit(host=<LAN>)` fails the same way. `status_fn()` returns an
   `error:` string, so `_ote11_in_recovery()` gives False. `left_in_recovery` is False and no
   taint is recorded.

The board is left in the recovery image. The run continues as though the board were back,
and nothing names the stranded state. This is the mechanism behind the earlier review's
MEDIUM-2. It is graded HIGH here because it is the normal path on this bench, not an edge
case.

If `host` is set to the AP address instead (with the PC joined to the AP), the push lands,
the application boots onto the LAN, and `_settled_running(ctx, host)` reads the now-silent
AP address and returns None. The case then reports FAIL "RUNNING is None" after a
successful push. The unit tests inject every function (`_recovery_*_fn`), so they exercise
neither path.

Fix: take a separate `recovery_host` (the AP address) and `app_host` (the LAN address).
SKIP when `recovery_host` is missing or does not answer before `recovery_enter`. Pass
`app_host` to `recovery_push_esp_image`/`recovery_exit` (both already accept it) and read
RUNNING on `app_host`. Treat any `status_fn` result that is neither "recovery image" nor a
confirmed application answer as unknown, and taint the run.

### MEDIUM-1: LCD-20 passes vacuously, because the recovery image never blanks the panel

`cases_lcd.py:6022-6043` (`observe_recovery_idle`) waits 70 s inside OT-E11, while the
standalone `KilnFW_recovery` image is running, and PASSes if the panel is still lit. The
plan row (`docs/BENCH_TEST_SYSTEM_PLAN.md:253`) is about `screen_idle`'s recovery flag.
That flag belongs to the application's boot_guard RECOVERY MODE
(`firmware/KilnFW/App/drivers/ui/screen_idle.c:183`, `idle->recovery_mode`), not to the
separate recovery image. The recovery image has no idle or blank logic at all: its backlight
is a plain GPIO driven high (`firmware/KilnFW_recovery/main/recovery_lcd.c:590`). The
observation therefore cannot fail for any `screen_idle` regression, and its PASS proves
nothing about the policy it is named for.

The application's recovery mode is reached by a boot_guard threshold and is a different
state from the one OT-E11 enters. Either retarget LCD-20 at that state or re-specify it as
"the recovery image's LCD stays lit" and drop the `screen_idle` claim. The earlier review
reports no findings for LCD-20, and this finding disagrees with that.

### MEDIUM-2: LCD-20 is NOT_RUN in every standard suite

`_case_lcd20` (`cases_lcd.py:6046`) reports `ctx["_lcd20_result"]`, which only OT-E11 sets.
`SUITES["lcd"]` does not contain OT-E11. `SUITES["ota"]` does not contain LCD-20. Neither
case is in `_NIGHTLY_ORDER` (`registry.py:504-549`), and LCD-20 has no `depends_on`. In every
suite run LCD-20 therefore reports NOT_RUN, and OT-E11's observation is collected and then
discarded. LCD-20 runs only through an explicit `cases="OT-E11,LCD-20"` in that order. If
LCD-20 is meant to run, add it to the `ota` suite after OT-E11 with `depends_on="OT-E11"`,
or report it in OT-E11's own `observed`.

### MEDIUM-3: LCD-15 FAILs spuriously when the bench's only saved network is the connected one

`cases_lcd.py:6638`: `_judge_lcd15` requires an exact match between a saved SSID and a tap
target name (`set(saved_ssids) & set(targets_names)`). The firmware labels the connected
network's row `"<ssid>  (connected)"`
(`firmware/KilnFW/App/drivers/ui/ui_page_network_manage.c:487`), and `kiln_ui.c`'s tap-target
names borrow that label text. On the bench, with one saved network that is also the
connected one, no target equals the bare SSID, so the case FAILs "no saved network shown".
The unit tests use synthetic names and do not cover this. Fix: strip a trailing
`"  (connected)"` before comparing, or match by prefix.

### MEDIUM-4: LCD-18's premise is wrong, so its PASS is coincidental and its FAIL can be spurious

`cases_lcd.py:6714-6760`: the case expects the topbar warning icon to show the ERROR tier
during a safety trip. The home topbar's warning tier is driven only by
`relay_cycles_max_budget_tier()` (`ui_page_home_refresh.c:71-77`). No trip state feeds it
(`ui_topbar.c:361-363` only picks ACCENT_5 or ACCENT_1 from the tier it is given). A PASS
during a trip therefore needs relay wear in the ERROR budget tier, and is otherwise a FAIL
that has nothing to do with the trip. A board whose relays are in the WARN wear tier reads
"warn" during any trip and FAILs. The plan row has the same wrong premise. The case also
does not call `_wake_and_home` before it captures, unlike LCD-07. Re-specify LCD-18 against
the relay-life tier (compare it with `GET /api/relay_cycles`'s tier), or against whatever
the home page actually shows for a trip.

### MEDIUM-5: LCD-11 cannot catch a stale tap that re-arms instead of disarming

`cases_lcd.py:6399-6401`: after the 5 s window lapses, the stale tap is judged only by
`exists() is True`. The firmware's contract
(`ui_page_profile_picker.c`, the "Stale tap" branch of `delete_btn_clicked_cb`) is that a
stale tap disarms and relabels the button "Delete". If a regression made the stale tap
re-arm instead, the profile still exists and `stale_kept` is True. The next tap then
confirms and deletes it, so `deleted` is True and the case PASSes. Meanwhile the third tap
lands on whatever row moved up (see the earlier review's HIGH-1). Check the label after the
stale tap: require "Delete", not "Confirm?". If it reads "Confirm?", FAIL and stop tapping.

### LOW-1: LCD-07 FAILs spuriously in two states

`cases_lcd.py:6592-6625`:

- When `get_exec_status()` raises, the case sets `running = False` (`:6602`). During a firing
  that makes lit pills read as a FAIL. An unreadable executor state should be INCONCLUSIVE.
- The pills are one per physical relay, aux relays included
  (`ui_page_home.c:1044-1079`, refresh at `ui_page_home_refresh.c:995-1008`). An aux relay
  switched ON by hand while idle lights its pill, and the idle "all off" expectation FAILs.
  Exclude pills whose relay is an enabled aux output, or read
  `control_get_aux_outputs` and expect them as reported.

The case writes nothing.

### LOW-2: `_decode_body` turns a corrupt gzip body into a judge FAIL, not INCONCLUSIVE

`cases_web_rw.py:113-125` (`3164aab2`): on `OSError`/`EOFError` from `gzip.decompress` the
helper silently decodes the raw compressed bytes as UTF-8. The judge then sees garbage and
FAILs on content rather than reporting a transport problem. Raise, or return a marker the
caller maps to INCONCLUSIVE. The `Accept-Encoding` header itself does survive the 401
re-login retry (`http_auth.py`'s `_copy_request` copies headers).

### LOW-3: LCD-12 reports a truncated tap-target list as FAIL

`cases_lcd.py:6498-6510`: when `_lcd25_wait_names` comes back truncated, `free` stays None
and the judge FAILs "review offered no free slot". A truncated read is an observation
failure and should be INCONCLUSIVE. (The literal `7` and the provenance-free cleanup on the
same lines are in the earlier review's LOW list.)

### LOW-4: the web-commission profile sweep can run past its stated 2 s bound

**FIXED in dbd1dfa9**: sweep moved to `_web_commission_sweep.mjs`; deadline checked before each icacls/rm (icacls timeout capped to time left), age from newest mtime inside the profile dir; `tests/web_commission_sweep.test.mjs` negtest-verified.

`tools/PcTools/scripts/_web_commission_cdp.mjs:865-882` (`a03093fb`): the deadline is checked
only between directories. Each stale directory now costs up to 5 s of `icacls /T` plus an
`rmSync` with retries, so a backlog of N leftover profiles can stall start-up for about
N x 5 s. The 1 h age test uses the top-level directory's mtime, which a long-running
concurrent driver does not necessarily refresh. Such a driver's live profile could be swept
once it is older than 1 h. Check the deadline before each `icacls`, and age by the newest
entry rather than the top-level mtime.
