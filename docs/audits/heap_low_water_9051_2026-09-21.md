# Internal DRAM low-water mark of 9051 B at 05f1ab1f — source audit

Source- and log-only investigation. No board access (a reflash was in progress on the
bench MCP server at investigation time). Findings are static-analysis inferences from
`firmware/KilnFW/App` and one `.map` file, not a live heap trace.

## Verdict

The dip is consistent with **known, deliberate transient internal-DRAM allocations**
stacking up during a sweep that exercises several handlers back-to-back, not a leak
(uptime is monotonic, no reboot, and the mark went flat afterward). No single allocation
in the code is obviously an 8.5 kB block by itself; the likeliest explanation is several
of the candidates below overlapping in time during the Class C sweep (autotune status
poll + profile live-edit + danger-mode calls, all authenticated, all through the same
httpd worker). This cannot be confirmed to the byte without a live
`heap_caps_get_minimum_free_size(MALLOC_CAP_INTERNAL)` probe bracketing each handler —
named as the settling step in the Recommendation section.

## 2. Ranking by plausible transient size

1. **A — `CFGFS_FILE_BODY_MAX` (8192 B), `diagnostics_http.c:1627`.** Largest single
   internal-DRAM transient identified anywhere in the driver tree. Deliberately internal
   (comment explains PSRAM is unreachable while cache is disabled for a flash write). By
   itself this is close to sufficient to explain the whole ~8.5 kB dip *if* it fired
   during the sweep window — but it is the `POST /api/cfgfs` handler specifically
   (diagnostics page's raw cfg-file editor), not something Class C's named surfaces
   (autotune, profile live-edit, danger mode) call directly. Only relevant if the sweep
   script also touched `/api/cfgfs` or the diagnostics page in the same pass; worth
   checking the sweep's own request log.
2. **B — `verify_write_readback`'s `malloc(len)`, `cfg_fs.c:337`.** This is the strongest
   candidate that *is* on the Class C path: profile live-edit's `decide` (save_as /
   overwrite) and any zones save go through the `cfg` dual-write
   (`docs/CONFIG_FILESYSTEM.md`, CLAUDE.md's cfg-partition note) → `cfg_fs_write_atomic()`
   → this readback allocation, sized to whatever was just written (profile blob or the
   1028 B zones blob). Runs on the flash worker task, internal DRAM, freed immediately
   after the `memcmp`. Several of these in quick succession (a profile write followed by
   a zones write, both plausible in a Class C pass that also drives zone changes) could
   plausibly account for several kB of overlapping transient use even though no single
   call is 8 kB.
3. **G — `READINESS_JSON_CAP` (4096 B), `readiness_http.c:171`.** Not named in the Class C
   surfaces described, but `capability_preflight` (CLAUDE.md) calls readiness-adjacent
   checks before a run; if the sweep's autotune/profile-edit pass included a readiness or
   preflight check, this stacks with B.
4. **D/E — CSV export mallocs.** Two buffers each; only fire on an explicit CSV-download
   request, not on ordinary autotune/profile-edit/danger-mode calls. Lower likelihood
   unless the sweep specifically exercised `/api/autotune.csv` or `/api/firing_history.csv`.
5. **C — cookie malloc.** Fires on *every* authenticated request in the whole sweep (many
   times), but each instance is small (well under the 4096 B cap in practice) and freed
   before the next line runs, so it raises peak concurrency risk only if two httpd worker
   tasks overlap, not size on its own.
6. **F, H — small internal-DRAM scratch structs.** Each is tens of bytes to roughly a
   struct's worth, freed within the same handler; not size-significant individually.

None of the SPIRAM-capped allocations (profile_live_http.c's fork/edit/decide bodies,
zones/status/backup/export JSON buffers) contribute to the internal-DRAM watermark at
all — that large family of buffers was already correctly moved off internal DRAM.

## 3. `.map` / `.dram0.bss` check

`firmware/KilnFW/build/KilnCtrl.map` exists (last written 2026-09-21 00:44, consistent
with the 05f1ab1f build) — **not rebuilt for this audit**, per instructions. It reports:

```
.dram0.bss   0x3fc9fb48   0x17448   (95,304 B total static BSS in internal DRAM)
```

This is the fixed, boot-time static footprint (task stacks, `s_routes` table, and every
other `static`/global in internal DRAM) — it does not itself explain a *dip that recovers*,
since static BSS size doesn't change at runtime. It does confirn the static baseline is
large enough that the ~17.6 kB post-bringup free / 9051 B post-sweep free numbers sit in a
genuinely tight remaining margin, consistent with CLAUDE.md's existing note that the
`s_routes` table alone cost ~19 kB and that a PSRAM-stacked task cannot write NVS. I did
not attempt to diff `.dram0.bss` against an older `.map` from a pre-live-profile-edit
commit — no older `.map` is present in this build directory to diff against, and rebuilding
one was out of scope (instructions: do not rebuild).

## 4. Recommendation

Do not implement any of these; each is reviewable in isolation and each has a real
constraint:

- **B (`cfg_fs.c:337` readback malloc) is the best next target to measure, not to move
  blindly.** It cannot simply move to `MALLOC_CAP_SPIRAM`: it runs on the flash worker
  task during/after a flash write, and PSRAM is documented elsewhere in this codebase
  (`relay_cycles.c`, `flash_worker.h`) as unreachable while the flash cache is disabled —
  the same reasoning `diagnostics_http.c`'s comment gives for keeping (A) internal. The
  safe move, if measurement confirms it matters, is to **shrink the exposure window**:
  the readback buffer only needs to be `len` bytes for the duration of one `fread`+`memcmp`
  — that's already true — so the fix, if one is needed, is likely bounding `len` itself
  (e.g. capping profile/zones blob size tighter) rather than relocating the allocation.
- **A (`CFGFS_FILE_BODY_MAX` = 8192 B) is already the documented, deliberate max** for
  this one handler and is explicitly commented as "generous headroom over any one cfg
  file this codebase writes today" — shrinking it risks breaking a legitimate write:
  needs an audit of actual on-device cfg file sizes before touching, not a blind cut.
- **G (`READINESS_JSON_CAP` = 4096 B)** has its own comment trail (2026-09-08/09) already
  documenting a size increase for a truncation bug — do not shrink it without re-deriving
  the same four-item worst case (`recovery_mode` 152 B, `safety_context` 136 B,
  `safety_commissioned` 130 B, `safety_trip` 97 B) that motivated the last change.
- **Never enlarge httpd buffers** (per CLAUDE.md) — none of these candidates propose that;
  all recommendations above are shrink-or-leave-alone.
- **Settling this precisely needs a live measurement**, not more static reading: bracket
  each of candidates A/B/D/E/G with `heap_caps_get_minimum_free_size(MALLOC_CAP_INTERNAL)`
  calls (temporary, or via an existing diagnostics log point) immediately before/after the
  allocation during a repeat of the Class C sweep, to see which one(s) actually produce
  the drop and whether they overlap in time. Until that is done, the fairest characterization
  is: **the 9051 B low-water mark is consistent with a bounded, documented family of
  transient internal-DRAM allocations (largest identified: 8192 B at diagnostics_http.c:1627,
  most likely on-path: the variable-size readback at cfg_fs.c:337), not a leak and not
  clearly a single smoking gun** — flat since the sweep (no reboot, monotonic uptime)
  supports "transient, correctly freed" over "leak."
