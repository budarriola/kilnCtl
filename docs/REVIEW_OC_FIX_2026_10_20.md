# Review: OC-01..OC-04, OC-07 fix (2026-10-20)

Static review of 84d062552 (fix) and a84a0b506 (ota_page guard) on origin/dev. No code changed, board untouched.

Summary: HIGH 0, MED 0, LOW 4, INFO 4.

| ID | Sev | Where | Problem | Fix |
|----|-----|-------|---------|-----|
| OF-01 | LOW | `update_install_record.c:141-145`, `update_install_http.c:366-369` | The running-image match (mark and status derivation) compares semver only. JTAG dev builds and rebuilt pre-release tags share a semver, so after a rollback whose `rolled_back` write failed, a different VALID build with the same semver is shown as confirming the old install (OC-03 is only half closed). | Match the record's `id` (image sha256) against the running image (e.g. `esp_partition_get_sha256` over `image_length`, computed once at boot), or store and compare the commit hash. |
| OF-02 | LOW | `update_install_record.c:181-183`, `ota_page.html:1144` | A record that names another image (UPD_INST_CONFIRM_NOT_RUNNING) stays OK/unconfirmed for good: status keeps reporting `pending_confirm` ("waiting for the new firmware to confirm itself"), which is false, and the page re-polls every 5 s forever. | Report a distinct state (e.g. `superseded`/`not_running`) in status when the OK record does not match the running image; stop polling on it. |
| OF-03 | LOW | `update_install_record.c:491-494` | The 409 guard says "retry in a minute", but if boot confirm never finishes (mark-valid keeps failing, MED-3 loop) the image stays PENDING_VERIFY for the whole boot and every web install is refused. Recovery still works (reset rolls back; boot_guard reaches recovery), so nothing is bricked, but the message misleads. | Say "the running image is not confirmed; reset the board to roll back or wait for confirm", or include the boot-confirm state in the 409 body. |
| OF-04 | LOW | `main_network_http.c:306-313`, `update_install_http.c:291-293` | The confirm task now lives up to ~70 min (120 x 5 s + 60 x 60 s) and each attempt adds an `update_identity_t` (~200 B: version, 41-B commit, 65-B partitions sha, min_updatable_from) on a 5120-B stack; the high-water log and `stack_margin_task_exit` only run after the loop, so a stack shortfall shows late. On rc -1 from a write that landed but failed read-back, each retry writes the blob again: at most 180 writes, negligible wear but unbounded by "already equal" checks. | Log the high-water mark before the loop too; skip the write when the stored blob already reads back confirmed; consider a static identity buffer. |
| OF-05 | INFO | `ota_http_recovery.c:303-328`, `update_install_http.c:284-295` | No race with a new install: `install_prepare` (which erases the result) and the mark both run under the update claim, and a 409 is returned while PENDING_VERIFY. A prepare between retries leaves no record, so the next mark returns 0 and the loop ends. The loop holds no lock across `vTaskDelay`. | None. |
| OF-06 | INFO | `update_install_http.c:131-140` | The guard keys on PENDING_VERIFY only. A JTAG-flashed slot (UNDEFINED/VALID) and the factory/recovery image are never refused, so the guard cannot block recovery from a bad image. | None. |
| OF-07 | INFO | `ota_page.html:1133-1148` | Re-poll cannot leak: one caller at load, the timer is cleared on entry and only re-armed after a completed fetch, and an auth failure (`!r.ok`) or fetch error stops the chain. It keeps polling in a hidden tab while pending. | Optional: pause on `visibilitychange`. |
| OF-08 | INFO | `recovery_install.c` | Recovery interop unchanged: the recovery image calls none of the changed functions (`confirm_result`, `prepare`, new ops field), and the record/result wire format is unchanged. OC-06 (recovery rebuild for detail 36) still stands. | None. |
