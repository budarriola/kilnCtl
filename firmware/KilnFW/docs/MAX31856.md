# MAX31856 — Notes, register formats, and driver usage

Notes for the `MAX31856` driver (SPI cold-junction-compensated thermocouple-to-digital
converter with on-chip linearization). Three of them, on the thermocouple
daughterboard.

## What the part is

The MAX31856 does the whole thermocouple front end in one chip: a low-noise
differential input for the thermocouple, an integrated cold-junction sensor, a
50/60 Hz notch filter, and — the reason it is worth its price over a bare ADC —
the **linearization**. It reports degrees Celsius directly (19-bit, 0.0078125 °C
per code), not a millivolt reading someone has to push through a NIST
polynomial. It also detects an open thermocouple and an over/under-voltage input
by itself, which for a kiln is the difference between "the element stayed on
because the reading froze" and "the controller knew the sensor fell off".

Eight thermocouple types are supported (B/E/J/K/N/R/S/T) plus two raw voltage
modes; this kiln ships **type K**.

## Wiring

Everything below is from `docs/HARDWARE.md`, which is the authority.

The three parts (U2/U3/U4 on the daughterboard) hang off the **shared** SPI bus
through J6 — one bus, one clock, one MOSI/MISO pair, three chip selects. The
ILI9488 display is a fourth device on that same bus at a different mode and a
much higher clock, which is why every device gets its own
`spi_device_interface_config_t` and why all traffic is funnelled through one
`spi_owner_t` worker task.

| Signal | Channel 0 | Channel 1 | Channel 2 | Notes |
|--------|-----------|-----------|-----------|-------|
| `~CS`   | GPIO14 | GPIO17 | GPIO18 | plain GPIO, bit-banged by `spi_owner` |
| `~FAULT`| GPIO38 | GPIO47 | GPIO48 | active low, input + internal pull-up |
| `~DRDY` | SX1509 IO8 | SX1509 IO9 | SX1509 IO10 | **not** an ESP32 GPIO |
| SCLK / MOSI / MISO | GPIO12 / GPIO11 / GPIO13 | shared | shared | |

Clock comes from `THERMO_SPI_CLOCK_HZ` (`App/drivers/hw/settings.h`, Kconfig-backed).
It is **capped at 4 MHz**, not merely defaulted there: the part's own `fSCL` limit
is 5 MHz, but the cap is an owner decision (2026-10-06): 4 MHz is ample for the
MAX31856 conversion rates and faster SPI is not needed. Enforced by a `range` on
`KILNCTL_THERMO_SPI_CLOCK_HZ` and a `_Static_assert` in `MAX31856.c`. This does
not affect `DISPLAY_SPI_CLOCK_HZ`, a separate symbol for a separate device on the
same bus. **SPI mode 1.** The
datasheet's Table 5 note is that the part sniffs SCLK polarity when `~CS` falls
and adapts, but "CPHA bit polarity must be set to 1" — so mode 1 or mode 3, and
this board's documentation says mode 1.

### The ~DRDY problem

`~DRDY` goes low when a new conversion result is available and returns high when
the temperature registers are read. On this board it lands on the **SX1509 I/O
expander**, not on a GPIO, so this driver cannot see it without owning an I2C
device that belongs to another driver. Two consequences:

- The driver exposes a hook, `MAX31856_set_drdy_provider()`, that whoever owns
  the expander can install. With it, `MAX31856Reading::stale` is the hardware's
  own answer.
- Without it, `stale` falls back to elapsed time: it is set when not enough time
  has passed since the last read for a new conversion to exist. That catches
  polling faster than the part converts. It **cannot** detect a part that has
  silently stopped converting — that is the documented limit of the fallback.

The driver samples `~DRDY` (via the hook) *before* its register burst, because
reading `CJTH`/`CJTL` is exactly what releases `~DRDY` high again.

## Registers and conversions

Sixteen 8-bit registers. **Reads use address `0Xh`, writes use `8Xh`** — the
write address is the read address + 0x80 (`MAX31856_WRITE_ADDR()`). The address
auto-increments for as long as `~CS` stays low, so a burst is one transaction.

| Addr | Name | What matters |
|------|------|--------------|
| 00h | `CR0` | CMODE (auto convert), 1SHOT, OCFAULT[1:0], CJ disable, FAULT mode, FAULTCLR, 50/60 Hz |
| 01h | `CR1` | AVGSEL[2:0] (1/2/4/8/16 samples), TC TYPE[3:0] |
| 02h | `MASK` | which faults may drive the `~FAULT` pin; **1 = masked**, default FFh |
| 03h/04h | `CJHF`/`CJLF` | cold-junction thresholds, int8, **1 °C/LSB** |
| 05h–08h | `LTHFTH/L`, `LTLFTH/L` | thermocouple thresholds, int16, **0.0625 °C/LSB** |
| 09h | `CJTO` | cold-junction offset, int8, 0.0625 °C/LSB, range ±8 °C |
| 0Ah/0Bh | `CJTH`/`CJTL` | cold-junction temperature |
| 0Ch–0Eh | `LTCBH/M/L` | linearized thermocouple temperature, 19 bits |
| 0Fh | `SR` | fault status (read-only) |

### The fixed-point formats, exactly

These are the four conversions worth getting right; all of them live in
`MAX31856.c` next to a comment citing the datasheet's bit-weight table.

- **Thermocouple temperature** (`LTCBH:LTCBM:LTCBL`) — sign + 2^10…2^-7 in the
  top 19 bits of a 24-bit word; `LTCBL[4:0]` are don't-care and are *not*
  guaranteed zero. Mask off the low 5 bits, sign-extend bit 23, then
  `degC = raw / 4096.0` (identical to `code19 × 0.0078125`, but without an
  arithmetic shift of a negative value).
- **Cold-junction temperature** (`CJTH:CJTL`) — sign + 2^6…2^-6, low two bits of
  `CJTL` hard-wired to 0. Treat the pair as a plain `int16` and
  `degC = raw / 256.0`. Clamped by the part to −64…+128 °C.
- **Thermocouple thresholds** (`LTHFTH:LTHFTL`, `LTLFTH:LTLFTL`) — `int16` at
  0.0625 °C/LSB. e.g. 1300.0 °C → 20800 → `0x51 0x40`.
- **Cold-junction offset** (`CJTO`) — `int8` at 0.0625 °C/LSB, so the register
  simply cannot express anything outside −8.0…+7.9375 °C. The driver clamps and
  logs a warning rather than letting two's complement wrap a large offset into a
  plausible one of the wrong sign.

Note the asymmetry that is easy to get wrong: **CJ thresholds are 1 °C/LSB,
thermocouple thresholds are 0.0625 °C/LSB.** That is why the wire protocol
carries the CJ ones as plain `int8` degrees and the TC ones as floats.

### Conversion timing

`tCONV` is 143 ms typ / 155 ms max at 60 Hz rejection, 169/185 at 50 Hz, plus
`(samples − 1) × 33.33 ms` (60 Hz) or `× 40 ms` (50 Hz) for averaging. In
automatic mode conversions repeat every ~100 ms nominal and the per-sample adder
halves. `MAX31856_conversion_time_ms()` reports this; internally the driver uses
the **max** column, since the only thing the number is used for is deciding when
a result can possibly exist, and being early there would mean calling a stale
reading fresh.

### The 50/60 Hz bit is not writable at any time

The datasheet: *"Change the notch frequency only while in the 'Normally Off'
mode – not in the Automatic Conversion mode."* The same page says the averaging
setting "should not be changed while conversions are taking place". Rather than
push that onto callers, `MAX31856_configure()` always does the same three
writes: `CR0` with `CMODE = 0` (carrying the new filter bit), then `CR1`, then
`CR0` again with the requested `CMODE`. Stop, write, restore.

### Faults

`SR` bits (same numbering as `THERMO_FAULT_*` in `uart_task_ids.h`): bit0 OPEN,
bit1 OVUV, bit2 TCLOW, bit3 TCHIGH, bit4 CJLOW, bit5 CJHIGH, bit6 TC out of
range, bit7 CJ out of range.

- The driver uses **comparator** fault mode (`CR0.FAULT = 0`), where the bits
  track the condition and clear themselves with 2 °C of hysteresis. `FAULTCLR`
  "has no effect in comparator mode" — the `CLEAR_FAULTS` subcommand still
  writes the bit, it just cannot do anything unless interrupt mode was selected.
- `MASK` powers up as FFh, i.e. **every fault masked off the `~FAULT` pin**,
  which would leave the three `~FAULT` GPIOs permanently idle.
  `MAX31856_start_all()` writes `0xFC`: open-circuit and OV/UV are allowed
  through, the four threshold faults stay masked (they are limits the operator
  set, better handled by reading `SR` than by a pin edge). The out-of-range bits
  never drive `~FAULT` at all — that is the part's behaviour, not a choice.
- OPEN / OVUV / TC-range / CJ-range are logged at **WARN** with the channel
  number, once per change of `SR` rather than once per read, so an unplugged
  thermocouple produces one line and not one per auto-report tick.

### Failure honesty

Every `MAX31856_read()` fills its output struct even when the SPI transfer
fails: both temperatures come back **NaN** with `spi_failed` set. There is no
path in this driver that returns a cached, zeroed, or last-known value dressed
up as a measurement.

## Driver APIs

Two structs: one `MAX31856BusClass` owns the SPI bus, the `spi_owner_t` worker
task and the channel registry; three `MAX31856Class` instances each own a
`spi_device_handle_t`, a `~CS`, a `~FAULT`, register shadows and a mutex. All
caller-provided (statics in `app_main`) — nothing is allocated after init.

Bring-up:

- `MAX31856_start_all(bus, channels)` — one-call bootstrap for `app_main`, the
  same shape as `SX1509_start` / `ILI9488_start`: bus init, three channels at the
  `THERMO_CSn`/`THERMO_FAULTn` pins, default config, fault mask, and a `CR1`
  read-back per channel so an absent part is an error line at boot rather than a
  mystery later. A failed channel is deinitialized and the others still work.
- `MAX31856_bus_init(bus, host, sclk, mosi, miso)` / `MAX31856_bus_deinit(bus)` —
  if another driver already initialized the host (the display), the bus is
  shared and only its original owner frees it.
- `MAX31856_init(ch, bus, channel, cs_gpio, fault_gpio)` / `MAX31856_deinit(ch)`
- `MAX31856_bus_channel(bus, channel)` — index → instance, `NULL` if it never
  came up
- `MAX31856_set_drdy_provider(bus, fn, ctx)`

Configuration:

- `MAX31856_config_default(cfg)` — type K, 1 sample, 60 Hz, OC detect mode 1,
  comparator faults, auto-convert per Kconfig
- `MAX31856_configure(ch, cfg)` — full `CR0`/`CR1` rewrite with the stop/write/
  restore dance above
- `MAX31856_config_channel(ch, tc_type, avg_mode, filter_50hz, auto_convert)` —
  exactly the four fields `CONFIG_CHANNEL` carries
- `MAX31856_get_config(ch, out_cfg)`, `MAX31856_set_conversion_mode(ch, auto)`
- `MAX31856_set_thresholds(ch, tc_high_c, tc_low_c, cj_high_c, cj_low_c)`
- `MAX31856_set_cj_offset(ch, offset_c)`, `MAX31856_set_fault_mask(ch, mask)`

Measurement:

- `MAX31856_trigger_one_shot(ch)` — the conversion starts when `~CS` rises at the
  end of the transaction; the result is not returned here
- `MAX31856_read(ch, &reading)` — one burst of `CJTH…SR` (0x0A–0x0F, six
  registers, one transaction) giving CJ temp, TC temp and `SR` from the *same*
  conversion
- `MAX31856_read_all(bus, out, max, &count)`
- `MAX31856_read_faults(ch, &sr, &mask)`, `MAX31856_clear_faults(ch)`
- `MAX31856_fault_pin_asserted(ch)` — GPIO level only, no SPI
- `MAX31856_conversion_time_ms(ch, one_shot)`

Raw access (the debug subcommands):

- `MAX31856_read_reg(ch, reg, buf, len)` — burst, 1…16
- `MAX31856_write_reg(ch, reg, value)` — updates the CR0/CR1/MASK shadow too, so
  a debug poke cannot desynchronize the driver from the part

Thread safety: one mutex per channel guards the shadows and any multi-transfer
sequence; the shared `spi_owner_t` serializes the wire itself. Concurrent
callers on different channels never block each other except in the SPI queue.

## UART subcommands (task_id 1, THERMO)

Full definitions in `App/drivers/common/uart_task_ids.h`; the bridge in
`uart_bridge.c` maps them onto the C API above. Payload bytes only (the framing,
CRC and header are the protocol layer's — see `docs/UART_PROTOCOL.md`).

| Cmd | Payload | Example |
|-----|---------|---------|
| `0x01` CONFIG_CHANNEL | ch, tc_type, avg, filter, conv_mode | `01 00 03 00 00 01` → ch0, type K, 1 sample, 60 Hz, automatic |
| `0x02` SET_THRESHOLDS | ch, f32 tc_high, f32 tc_low, i8 cj_high, i8 cj_low | `02 00 00 80 A2 44 00 00 00 00 3C F6` → ch0, TC 1300.0/0.0 °C, CJ +60/−10 °C |
| `0x03` SET_CJ_OFFSET | ch, f32 offset | `03 00 00 00 C0 BF` → ch0, −1.5 °C (`CJTO` = 0xE8) |
| `0x04` ONE_SHOT | ch | `04 00` |
| `0x05` READ | ch or 0xFF | `05 FF` → all three |
| `0x06` READ_FAULTS | ch or 0xFF | `06 00` |
| `0x07` CLEAR_FAULTS | ch | `07 00` (no-op in comparator mode — see above) |
| `0x08` SET_AUTO_REPORT | ch mask, u16 period_ms | `08 07 E8 03` → all three channels every 1000 ms |
| `0x09` READ_REG | ch, reg, len | `09 00 00 02` → ch0, `CR0`+`CR1` |
| `0x0A` WRITE_REG | ch, reg, value | `0A 00 01 33` → ch0, `CR1` = 8 samples, type K |

Responses:

- **READ / auto-report** — `05`, count, then 12 bytes per channel: channel,
  f32 TC °C, f32 CJ °C, `SR`, flags (bit0 `~FAULT` low, bit1 SPI read failed,
  bit2 stale), reserved.
  `05 01 00 00 00 C0 41 00 00 B4 41 00 00 00` → ch0, 24.0 °C, CJ 22.5 °C, no
  faults, fresh. A channel whose read failed still appears, with bit1 set and
  both temperatures NaN (`00 00 C0 7F`).
- **READ_FAULTS** — `06`, count, then 3 bytes per channel: channel, `SR`, `MASK`.
  `06 01 00 01 FC` → ch0, open-circuit fault, default mask.
- **READ_REG** — `09`, channel, reg, len, then the bytes.
  `09 00 00 02 80 03` → `CR0` = 0x80 (automatic), `CR1` = 0x03 (type K, 1 sample).
