# SX1509 — Notes, board pin map, and driver usage

Notes for the `SX1509` driver (Semtech SX1509B, 16-channel level-shifting I2C
GPIO expander with LED driver and keypad engine) and for `kiln_io`, the board
layer above it. The expander is **U5** on the kilnCtl main board and it owns
everything slow: the four relay drives, seven general-purpose digital I/Os, the
three thermocouple `~DRDY` lines and the display's D/C and `~RESET`.

It replaces the PCF8575 that the unit-test fixture used. If you know that
driver, the two differences that matter most are that this part has *real*
direction/pull-up/interrupt registers instead of quasi-bidirectional pins, and
that its 16-bit quantities are **big-endian on the wire** where the PCF8575's
were little-endian.

## Wiring

I2C on SDA GPIO8 / SCL GPIO9 — the SX1509 is the only device on the main
board's bus, though SDA/SCL are also carried out to J2 (display) and J6
(thermocouple board) in case a module ever wants to hang something there.

`SX1509_init` does **not** create the bus: ESP-IDF allows one
`i2c_master_bus_handle_t` per physical bus, so the caller passes the existing
handle in. The driver attaches as a device with `i2c_master_bus_add_device()`
and creates its own `i2c_owner_t` wrapping that same handle, so its transfers
get their own FIFO-ordered queue.

Two GPIOs beyond the bus, both configurable in menuconfig:

| Line | GPIO | Notes |
|------|------|-------|
| `~INT`   | 7  | Active low, **open-drain**, no external pull-up — the driver enables the ESP32's internal one. |
| `~RESET` | 10 | Active low. Driven high before the pin becomes an output so reset never glitches at boot. |

The driver configures `~INT` as a pulled-up input and installs **no ISR**.
Which task wants to hear about an edge, and by what mechanism, is not the
driver's business — `kiln_io_irq_gpio()` / `SX1509_get_irq_gpio()` hand out the
number and the caller installs whatever it likes.

## Addressing (all four supported)

`ADDR1`/`ADDR0` select one of four addresses. They are **not contiguous** —
0x3E/0x3F and 0x70/0x71 are two separate pairs — so `SX1509_scan` walks a table
rather than a range.

| ADDR[1:0] | Address |
|-----------|---------|
| 00 | **0x3E** ← both strapped to GND on this board |
| 01 | 0x3F |
| 10 | 0x70 |
| 11 | 0x71 |

0x3E is the Kconfig default (`KILNCTL_SX1509_I2C_ADDR`). All four are
selectable at runtime: `SX1509_set_address()` swaps the I2C device handle
without a reboot — probing the target first and refusing with
`ESP_ERR_NOT_FOUND` if nothing answers there, rather than pointing at a part
that isn't installed and then burning a bus reset plus a retry on every
transfer. Both are reachable from the PC (`SX_SCAN`, and the address selector
in the GUI).

## This board's pin map

Traced from `hardware/mainBoard/kiln.kicad_sch`; `docs/HARDWARE.md` is the authority.
The pin numbers themselves live in `App/drivers/settings.h`
(`SX1509_RELAY1_PIN` and friends) and `kiln_io.c` derives every mask from them.

| Pin | Net | Function |
|-----|-----|----------|
| IO0  | `Relay1` | Q3 → **K3** → J8 |
| IO1  | `Relay2` | Q1 → **K1** → J3 |
| IO2  | `Relay3` | Q2 → **K2** → J4 |
| IO3  | `Relay4` | Q5 → **K5** → J11 |
| IO4  | `IO_1` | Opto-isolated **input** from J24 (U13), 2.2k pull-up on board |
| IO5  | `IO_2` | Drives the opto-isolated **output** to J25 (U14) via 390R |
| IO6  | `IO_3` | J20 pin 1 |
| IO7  | `IO_4` | J20 pin 2 |
| IO8  | `thermoDrdy_0` | MAX31856 ch0 `~DRDY`, active low |
| IO9  | `thermoDrdy_1` | ch1 `~DRDY` |
| IO10 | `thermoDrdy_2` | ch2 `~DRDY` |
| IO11 | `IO_5` | J21 pin 1 |
| IO12 | `IO_6` | J21 pin 2 |
| IO13 | `IO_7` | J23 pin 1 |
| IO14 | `LCD_IORQ` | ILI9488 data/command select |
| IO15 | `LCD_Reset` | ILI9488 `~RESET`, active low |

### Relay numbering is not K numbering

`Relay1..Relay4` are the *schematic's* net names and the expander's bit order.
They do not line up with the K designators:

```
Relay1 = IO0 -> Q3 -> K3 -> J8
Relay2 = IO1 -> Q1 -> K1 -> J3
Relay3 = IO2 -> Q2 -> K2 -> J4
Relay4 = IO3 -> Q5 -> K5 -> J11
```

The firmware exposes `Relay1..4` on the API and wire protocol, matching the
schematic and terminal-block labels above exactly. The GUI (web and LCD) was
moved to 0-based display (`Relay0..3`) on 2026-08-27 to match the
thermocouple/zone/CT numbering used everywhere else on screen; only the
printed label is shifted, the wire number underneath is unchanged. Reading a
terminal-block label is the one place the 1-based table above is needed. K4
is on the safety domain and belongs to the RP2040, not to this firmware.

Relay coils are 12 V (EE2-12NUH) switched low-side by a BSS138, so **an
expander pin driven high energizes the relay**. That is why boot order matters
(below).

## Register notes that actually matter

### 16-bit registers are big-endian

Every 16-bit quantity is a *pair* of 8-bit registers, and **bank B (I/O[15:8])
sits at the LOWER address**: `RegDataB` = 0x10, `RegDataA` = 0x11; `RegDirB` =
0x0E, `RegDirA` = 0x0F. With the part's address auto-increment on (`RegMisc`
bit 1 = 0, the power-on default — this driver relies on it and never turns it
off), a two-byte burst starting at the B address carries the **high byte
first**.

So `SX1509_write_reg16(e, SX1509_REG_DATA_B, 0x1234)` puts `0x12` then `0x34`
on the wire. That is the reverse of the PCF8575's two port bytes, and the
reverse of the little-endian `u16` the UART protocol carries — the conversion
happens once, in `SX1509_write_reg16`/`SX1509_read_reg16`. Everywhere above
that layer a `uint16_t` is just "bit N = pin N".

The same rule, twice as wide, applies to the four sense registers (below).

### `RegDir`: 1 = input

The opposite of what most people guess, and the reset value is `0xFFFF` — every
pin an input. The driver keeps the part's polarity rather than inverting it, so
a register dump, a wire payload and a C variable all mean the same thing.
`SX1509_set_dir` takes the mask in that polarity, and so does the wire's
`SX_SET_DIR`.

### Interrupts: mask polarity, sense encoding, and clearing

- `RegInterruptMask` bit = **1 disables** that pin's interrupt (reset value
  `0xFFFF`, everything off).
- Sense is **2 bits per pin**, spread over four consecutive registers that run
  from the *highest* pins down: 0x14 = I/O[15:12], 0x15 = I/O[11:8], 0x16 =
  I/O[7:4], 0x17 = I/O[3:0]. `SX1509_set_interrupt` takes them flattened into
  one `uint32_t` with pin N at bits `[2N+1:2N]` — which is exactly a 32-bit
  big-endian write of that field. Values: `0` none, `1` rising, `2` falling,
  `3` both; use `SX1509_SENSE_FOR_PIN(pin, mode)`.
- A pin with sense `0` never fires regardless of the mask.
- `~INT` stays low until **every** bit of `RegInterruptSource` is cleared.
  Clearing is write-1-to-clear, and the driver writes back exactly the bits it
  read, so an edge that arrives in between keeps its bit instead of being
  erased.
- The part can auto-clear the interrupt source whenever `RegData` is read
  (`RegMisc` bit 0). **This driver turns that off** and re-applies the setting
  after every reset: with it on, ordinary polling of the port would silently
  consume the very edges the poller exists to notice. `kiln_io_read` therefore
  clears the source explicitly, right after the data read, so a polling reader
  still can't leave `~INT` stuck low.

### The oscillator is off, and three features quietly depend on it

`RegClock[6:5]` = OFF at reset. While it is off the **debouncer**, the keypad
engine and **every LED driver** are inert — no error, just nothing happening.
This is the single most common "I enabled the LED driver and it did nothing".

The driver switches the internal 2 MHz oscillator on **lazily**, the first time
`SX1509_led_driver` or `SX1509_set_debounce` actually needs it, and additionally
programs `RegMisc[6:4]` (the shared LED clock `ClkX`) for the LED case. It is
not done in init because this board's expander otherwise has no use for a clock,
and running a 2 MHz oscillator forever to drive nothing is just quiescent
current. `kiln_io_init` deliberately leaves debouncing **off** for the same
reason — an opto input and a few terminal blocks that the firmware samples every
few tens of milliseconds do not need hardware debouncing.

The LED driver is a current **sink**: the pin goes to its `RegIOnX` intensity
when `RegData[pin]` is driven **LOW**. Light it with
`SX1509_write_pin(e, pin, false)`. No LED is populated on any expander pin on
this board — the feature exists for the terminal blocks and for bench use.

### Reset

- **Software**: write `0x12` then `0x34` to `RegReset` (0x7D), *consecutively
  and as two separate transfers* — a two-byte burst would land `0x34` in
  `RegTest1` thanks to auto-increment. Datasheet-equivalent to a POR.
- **Hard**: pulse `~RESET` low. The datasheet's minimum is 200 ns; the driver
  holds it 10 µs and then waits out the reset recovery. This is the only reset
  that works on a part whose I2C state machine has wedged, which is exactly when
  you want one. It behaves as a POR only because `RegMisc` bit 2 is left at 0
  (with it set, `~RESET` resets just the PWM/blink counters) — the driver never
  sets that bit.

Either way every shadow goes back to the power-on values and the `RegMisc` bit
above is re-applied.

## Write verification — and where it is honestly impossible

Every write retries up to `I2C_WRITE_RETRY_ATTEMPTS` (5, `settings.h`) on a
transport error, on top of the single bus-reset-and-retry `i2c_owner` already
does per transaction. Where a read-back means something, the driver also
verifies and counts a mismatch as a failed attempt, returning
`ESP_ERR_INVALID_RESPONSE` if it never agrees.

**Verified by exact compare** — plain read/write configuration registers,
nothing outside the chip can influence what they read back: `RegDir`,
`RegPullUp`, `RegPullDown`, `RegOpenDrain`, `RegInterruptMask`, `RegSense`,
`RegDebounceConfig`/`RegDebounceEnable`, `RegLEDDriverEnable`, `RegIOnX`,
`RegClock`, `RegMisc`, `RegInputDisable`.

**Verified over a subset** — `RegData`. A read of it returns *pin* states, so
only bits that are (a) configured as outputs, (b) not open-drain and (c) not
driven by the LED driver are checked. An input pin reads the outside world; an
open-drain pin "driven high" reads whatever is pulling the net; an LED pin reads
a sample of a PWM waveform. None of those disagreeing is a fault, so none is
treated as one. With no verifiable bits the ACK alone is the check.

**Not verifiable, and not faked**:

- `RegInterruptSource` / `RegEventStatus` — write-1-to-clear. Re-reading after a
  clear legitimately shows any edge that happened since, so there is no compare
  to make. Transport failures are reported; "did it really clear" is not
  claimed.
- `RegReset` — reads nothing useful by construction.
- `SX1509_write_reg` (the raw escape hatch behind `SX_WRITE_REG`) never
  verifies: it is generic, and only the caller knows which of the above
  categories the register it just wrote falls into. It does keep the driver's
  shadows in step, so poking a register from the PC cannot desynchronize the
  driver.

## Boot order (why relays don't click at power-up)

`RegData`'s power-on value is all ones and a high pin energizes a relay. So
`kiln_io_init` does, in this order:

1. software reset — all 16 pins become inputs, dropping any relay a warm
   restart left energized, and re-establishing the `RegMisc` bit;
2. write `RegData` with the safe levels (relays 0, IO_2's opto 0, `LCD_Reset`
   **high** = not held in reset, `LCD_IORQ` high). Every pin is still an input,
   so this moves nothing — it only loads the output latches;
3. pull-ups on the bare terminal-block inputs and on the three `~DRDY` lines
   (an absent thermocouple board then reads "not ready" instead of floating);
   pull-downs and open-drain explicitly zeroed;
4. interrupts: both edges on the opto input and the terminal blocks, **falling
   only** on `~DRDY` (the rising edge is just the part rearming);
5. `RegDir` **last** — the moment the outputs start driving, with the values
   from step 2.

Doing it the obvious way round (direction first, then levels) would energize all
four coils for as long as the next I2C transfer takes. On a kiln that is every
element on for a few hundred microseconds at every boot.

## Display D/C is on the critical path

Every command/data transition on the ILI9488 costs an I2C transfer, because
`LCD_IORQ` is an expander pin. `kiln_io_lcd_dc` is built accordingly:

- it is a **no-op** when the line is already where it needs to be (the display
  driver batches each command's whole payload into one SPI transaction, so runs
  of data don't touch the bus at all);
- otherwise it is **one two-byte write of `RegDataB` alone**, computed from the
  driver's data shadow — no read-modify-write round trip. Both display lines
  live in bank B, so this path is physically incapable of disturbing a relay;
- and it skips read-back verification. Doubling the traffic on the one call that
  runs per display command would be paid forever, and the failure it would catch
  shows up immediately anyway — as a display drawing garbage and as errors from
  every other expander access.

`kiln_io_lcd_reset` runs twice per panel reset, not per command, so it takes the
verified masked-write path instead.

## C API

### `SX1509.h` — the chip

- `SX1509_start(e, bus)` — one-call bootstrap for `app_main`: probe at the
  Kconfig address, `SX1509_init` with the Kconfig `~INT`/`~RESET` GPIOs, reset,
  and one `RegDir` read-back so an absent part is an error line at boot rather
  than a mystery on the first GUI command.
- `SX1509_init(e, bus, addr, irq_gpio, reset_gpio)` / `SX1509_deinit(e)` — init
  issues no register traffic at all; the part comes out of reset safe and
  configuring the board is `kiln_io_init`'s job.
- `SX1509_set_address(e, addr)` / `SX1509_scan(bus, out, max, count)`
- `SX1509_write_reg` / `read_reg` / `read_regs` — raw, unverified, shadow-safe.
- `SX1509_write_reg16` / `read_reg16` — `reg` is the **bank B** address of the
  pair; big-endian on the wire (above).
- `SX1509_set_dir` (1 = input) / `set_pullup` / `set_pulldown` /
  `set_open_drain`
- `SX1509_set_debounce(e, enable_mask, config)` — `config` 0–7 = 0.5 ms ≪ n at
  2 MHz; enabling any of it starts the oscillator.
- `SX1509_set_interrupt(e, mask, sense)` — mask 1 = *disabled*; sense is the
  flattened 32-bit field.
- `SX1509_get_interrupt_source(e, &mask, clear)`
- `SX1509_write_port` / `write_masked(e, mask, value)` (atomic RMW against the
  shadow, no device read) / `read_port` / `write_pin` / `read_pin`
- `SX1509_led_driver(e, pin, enable, intensity)` — lazily starts the oscillator
  and `ClkX`, does the datasheet's pin housekeeping, writes `RegIOnX`.
- `SX1509_reset(e, hard)`
- `SX1509_get_shadow(e)` (last `RegData` *written*) / `SX1509_get_dir_shadow(e)`
  / `SX1509_get_irq_gpio(e)` / `SX1509_irq_asserted(e)`

### `kiln_io.h` — the board

- `kiln_io_init(io, exp)` — the boot sequence above.
- `kiln_io_set_relay(io, relay /*1-4*/, on)`
- `kiln_io_set_relay_mask(io, mask, value)` — one atomic write, so several
  relays switch on the same transfer.
- `kiln_io_all_relays_off(io)` — the link-loss / fault fallback; no reads, no
  loop, nothing that can half-succeed.
- `kiln_io_set_io(io, index /*1-7*/, level)` /
  `kiln_io_set_io_dir(io, index, input, pullup)`
- `kiln_io_read(io, &state)` → `kiln_io_state_t { data, dir, relay_shadow,
  io_levels, drdy_bits, flags }`, laid out to match the wire response field for
  field.
- `kiln_io_get_drdy(io, channel /*0-2*/, &asserted)` — asserted = pin LOW.
- `kiln_io_lcd_dc(io, data)` / `kiln_io_lcd_reset(io, asserted)`
- `kiln_io_irq_gpio(io)` / `kiln_io_irq_asserted(io)` /
  `kiln_io_get_relay_shadow(io)`

The relay shadow is deliberately **not** updated when a write fails: the honest
report is "I could not put them where you asked", not "they are where you
asked".

## UART subcommands

Task `UART_TASK_ID_IO` (2). Payloads below are the DATA frame's payload bytes,
`byte0` being the subcommand. See `docs/UART_PROTOCOL.md` for the envelope and
`App/drivers/uart_task_ids.h` for the authoritative definitions.

| Sub | Name | Payload |
|-----|------|---------|
| 0x01 | `SET_RELAY` | `byte1` relay 1–4, `byte2` on 0/1 |
| 0x02 | `SET_RELAY_MASK` | `byte1` mask (bits 0–3), `byte2` value (bits 0–3) |
| 0x03 | `SET_IO` | `byte1` io 1–7, `byte2` level 0/1 |
| 0x04 | `SET_IO_DIR` | `byte1` io 1–7, `byte2` dir (0 = out, 1 = in), `byte3` pullup 0/1 |
| 0x05 | `READ` | — (query) |
| 0x06 | `SET_AUTO_REPORT` | `bytes1..2` period_ms u16 LE (0 = off) |
| 0x07 | `ALL_RELAYS_OFF` | — |
| 0x10 | `SX_WRITE_REG` | `byte1` reg, `byte2` value |
| 0x11 | `SX_READ_REG` | `byte1` reg, `byte2` len 1–16 (query) |
| 0x12 | `SX_SET_DIR` | `bytes1..2` u16 **LE**, 1 = input |
| 0x13 | `SX_SET_PULLUP` | `bytes1..2` u16 LE |
| 0x14 | `SX_SET_OPENDRAIN` | `bytes1..2` u16 LE |
| 0x15 | `SX_SET_DEBOUNCE` | `bytes1..2` enable mask u16 LE, `byte3` config 0–7 |
| 0x16 | `SX_SET_INT_MASK` | `bytes1..2` mask u16 LE, `bytes3..4` sense u16 LE |
| 0x17 | `SX_LED_DRIVER` | `byte1` pin 0–15, `byte2` enable 0/1, `byte3` intensity |
| 0x18 | `SX_RESET` | `byte1` hard (0 = `RegReset`, 1 = pulse `~RESET`) |
| 0x19 | `SX_SCAN` | — (query) |

Note the direction of travel: **u16 fields on the wire are little-endian**, and
the driver flips them to the part's big-endian register order. Bit N is pin N in
both.

### Examples

Energize Relay1 (K3 / J8):

```
01 01 01
```

Turn Relay2 and Relay4 on and Relay3 off in one register write (mask
`0b1110` = 0x0E, value `0b1010` = 0x0A):

```
02 0E 0A
```

Drop everything:

```
07
```

Make IO_5 an input with the internal pull-up on:

```
04 05 01 01
```

Read the board (query — the response comes back as a separate DATA frame):

```
05
```

Response payload, e.g. relays 1 and 2 on, channel 0 signalling data-ready,
`~INT` asserted:

```
05  0F FC  D0 3F  03  00  01  01
│   └─┬──┘ └─┬──┘  │   │   │   └ flags: bit0 ~INT low
│     │      │     │   │   └──── drdy: bit0 = ch0 asserted
│     │      │     │   └──────── io levels, bits0-6 = IO_1..IO_7
│     │      │     └──────────── relay shadow, bits0-3 = Relay1..4
│     │      └────────────────── RegDir  u16 LE (0x3FD0: inputs)
│     └───────────────────────── RegData u16 LE (raw pin states)
└─────────────────────────────── echo of IO_CMD_READ
```

Raw register poke — set `RegDirA` (0x0F) so I/O[7:0] are all outputs:

```
10 0F 00
```

Read the four sense registers (0x14–0x17) in one go:

```
11 14 04
```

Software-reset the part:

```
18 00
```

Scan for the expander:

```
19
```

→ `19 01 3E` (one device, at 0x3E).
