# ILI9488 — Notes, wiring, and driver usage

Notes for the `ILI9488Class` driver: a 3.5", 480x320 TFT on the kilnCtl main
board's **J2**, driven over the board's shared SPI bus. It replaces the
SSD1306 OLED the unit-test fixture used, and almost nothing carries over —
this panel has no framebuffer in the MCU, no `display()` flush step, and its
two control lines are not GPIOs.

**Source file note (`DISPLAY_ST7796_PLAN.md` Sec.6/12, Phase 3, 2026-09-01):**
the driver file itself was renamed `ILI9488.c/.h` → `App/drivers/panel_spi.c/.h`
and parameterised by a `const panel_desc_t *` (`panel_codec.h`) so the same
driver can run either this panel or an ST7796S (`st7796_panel.c/.h`) — chosen
by `KILNCTL_DISPLAY_PANEL` at build time today, with auto-detection logic
landed but inert (`panel_detect.c/.h` — see `DISPLAY_ST7796_PLAN.md` §14/Phase
4). The public API kept its `ILI9488_`/`ILI9488Class` names on purpose —
`screen_idle.c` and others call them directly and renaming would touch files
outside that phase's scope — so everything below describing that API is still
accurate for **either panel**; only the header/geometry-table/COLMOD/init-
sequence details in "RGB666 over SPI" are ILI9488-specific. The ST7796S
accepts RGB565 natively (no 666 widening, no third-per-pixel byte cost) and
has never run on real hardware — see the STOP block and §4 of
`DISPLAY_ST7796_PLAN.md` before wiring one up.

## What the panel is

The module is a **BIGTREETECH TFT35 SPI V2.1**: 3.5", 480x320, ILI9488
controller, 3.3 V logic on a 5 V supply, with the backlight apparently
hardwired on (there is no control pin on the connector). It also carries a
touch controller, which this firmware does **not** drive — BIGTREETECH's own
documentation and hardware repository say that part is an **NS2009** (I2C),
not the XPT2046 (SPI) that third-party listings often claim. Either way, the
firmware drives the display only.

The controller's frame memory is 320 columns x 480 rows in its native
orientation, regardless of rotation; `MADCTL` (0x36) only changes the scan
order, never the memory size. `KILNCTL_DISPLAY_ROTATION` defaults to 1, i.e.
landscape 480x320.

## Wiring

J2 is a 10-pin JST XH. Pins 5–10 are unambiguous:

| J2 | Main-board net | Goes to |
|----|----------------|---------|
| 5  | `CS3`   | ESP32-S3 **GPIO21** — the panel's `~CS`, a real GPIO |
| 6  | `CLK`   | Shared SPI clock, GPIO12 |
| 7  | `MOSI`  | Shared SPI, GPIO11 |
| 8  | `MISO`  | Shared SPI, GPIO13 |
| 9  | GND     | |
| 10 | 5V      | |

Pins 1–4 are the problem.

### The D/C-vs-reset ambiguity

The main board names J2 pin 1 `LCD_IORQ` and pin 4 `LCD_Reset`, and routes
both to the **SX1509 expander** (IO14 and IO15 respectively) — not to GPIOs.
Every published pinout for this module, however, says pin 1 is the *touch
controller's interrupt* and pin 4 is **RS** (register select = data/command),
with no panel reset brought out on the connector at all. Those sources are
single-origin and carry a "V2.2" silkscreen, so neither reading is proven.
**Check both against the physical connector before powering the panel.**

The firmware therefore does not pick a winner in code. `settings.h` has:

| `KILNCTL_DISPLAY_SWAP_DC_RESET` | `SX1509_LCD_DC_PIN` | `SX1509_LCD_RESET_PIN` |
|---|---|---|
| **n** (default) — the module's pinout | IO15 (`LCD_Reset` net, J2 pin 4 = module RS) | IO14 |
| y — the schematic's naming | IO14 (`LCD_IORQ`, J2 pin 1) | IO15 |

The default follows the module, on the reasoning that a display with no D/C
cannot work at all, while a display with no reset merely loses a recovery
lever. **If the panel shows nothing but `READ_ID` comes back correctly, this
is the first thing to flip.** Nothing else in the firmware assumes an order —
the driver reads whichever pin is configured, through
`kiln_io_lcd_dc()` / `kiln_io_lcd_reset()`.

`ILI9488_reset(disp, true)` (hard reset) is allowed to fail: if the connector
really has no reset line, the pulse goes to the touch IRQ and does nothing.
The driver logs that and falls back to `SWRESET`.

**Bench-wiring bypass.** `KILNCTL_DISPLAY_DC_RESET_DIRECT_GPIO` (off by
default) skips the expander for D/C and/or `~RESET` entirely and drives them
from two bare ESP32 GPIOs instead (`KILNCTL_DISPLAY_DC_GPIO` /
`KILNCTL_DISPLAY_RESET_GPIO`, `settings.h`'s `DISPLAY_DC_GPIO`/
`DISPLAY_RESET_GPIO`). Useful when the SX1509 isn't populated/working yet but
the panel's other lines (SPI, `~CS`, power) are wired normally — with this
on, `app_main`'s `io_ready` gate no longer blocks display bring-up on the
expander being up. `ILI9488_init` takes `dc_gpio`/`reset_gpio` params for
this (`-1` = expander, as above; `>= 0` = that GPIO directly) — see
`ILI9488.h`.

One more, for the next board revision rather than for firmware: the main
board puts SDA on J2 pin 2 and SCL on pin 3, the module pinout has them the
other way round. That only affects the touch controller, which nothing here
drives.

### D/C on I2C is the thing that shapes the driver

A GPIO toggle is nanoseconds; an expander toggle is a full I2C transaction —
roughly 90 µs at 400 kHz, through another driver's queue on top. So on this
board **D/C transitions, not bytes, are the expensive unit**, and the driver
is built around minimizing them:

- Every command is exactly **one** D/C toggle: low, send the opcode, high,
  send that command's *entire* payload in one `spi_owner_transfer()`.
- Fills, glyphs and blits leave D/C parked in "data" for their whole duration
  and push the pixel stream in chunks. A 480x320 clear costs 2 D/C toggles
  and ~320 SPI transfers, not 460,800 I2C round trips.
- `dc_is_data`/`dc_valid` shadow the line so back-to-back data pushes skip the
  I2C write entirely. `dc_valid` starts false, so the driver never assumes a
  level it did not itself write (the expander may have been reset underneath
  it).

Splitting a pixel stream across transfers is legal by the datasheet: §4.3
"Data Transfer Pause" says the controller resumes where it paused if CSX is
released after a *whole byte* of frame-memory or parameter data.
`spi_owner_transfer()` raises CS between transfers and every transfer here
ends on a byte boundary — which is also what makes the streaming blit legal
across separate UART frames.

## RGB666 over SPI — the format is not negotiable

The API speaks **RGB565 `uint16_t`**, which is what the UART protocol carries
and what callers want. The panel cannot accept it.

The command table (§5.2.34, COLMOD 3Ah) lists DBI[2:0] = 101 as "16
bits/pixel", and §4.7.2 even names 65K colour as available on the 4-line
serial bus. But the serial data-format section that actually *defines the bit
layout* only ever defines two: 3 bit/pixel (§4.7.2.1) and 18 bit/pixel
(§4.7.2.2). There is no figure anywhere in the document for 16 bit/pixel over
3- or 4-line SPI — every 16 bpp data-format figure belongs to a parallel MCU
bus or to DPI/DSI. This matches the universally-reported behaviour: set
COLMOD to 0x55 over SPI and the panel produces garbage.

So the driver runs **COLMOD = 0x66** (DBI 110, 18 bits/pixel) and sends three
bytes per pixel. The widening happens in exactly one place,
`ili9488_rgb565_to_rgb666()`. It costs 50% more bytes on the wire than RGB565
would; there is no alternative on this interface.

Two consequences worth stating:

- **There is no framebuffer, and there cannot be one in internal RAM.**
  480 x 320 x 3 = 460,800 bytes, more than the ESP32-S3's 512 KB of internal
  SRAM once Wi-Fi has taken its share. Every draw call goes straight to the
  panel's own frame memory, which is why — unlike the SSD1306 driver — there is
  no `ILI9488_display()` flush. By the time a draw call returns, the pixels are
  on the glass. The cost is that nothing can be read back or composited: drawing
  is write-only and order-dependent.

  **The module does have PSRAM that would hold one** (2 MB or 8 MB depending on
  the variant — see `PROJECT_STATUS.md`), and it is deliberately left disabled.
  A PSRAM framebuffer would mean rendering into PSRAM and then shipping the same
  pixels over SPI to the panel's own GRAM — two copies of the work — to buy
  read-back, compositing and flicker-free partial redraw. Nothing here asks for
  those yet. **This is the one named trigger that would flip the PSRAM
  decision**; the reasoning, and what enabling it would cost, is in
  `TODO.md` section 9.1a.
- **The bus must have DMA.** The driver's reusable scratch buffer is one full
  landscape row, `ILI9488_SCRATCH_BYTES` = 480 x 3 = 1440 bytes, allocated
  once with `MALLOC_CAP_DMA`. A `SPI_DMA_DISABLED` bus caps a transfer at 64
  bytes. `app_main` therefore calls `spi_bus_initialize()` itself with
  `max_transfer_sz = ILI9488_SCRATCH_BYTES` and `SPI_DMA_CH_AUTO` *before*
  either driver starts, because only the first `spi_bus_initialize()` on a
  host takes effect and `MAX31856_bus_init` would otherwise configure it
  DMA-disabled with `max_transfer_sz` 17. If some other bus owner cannot make
  that promise, lower `disp->chunk_bytes` after `ILI9488_init()`; correctness
  is unaffected, only throughput.

Colour filter order is an **assumption**: the driver sets `MADCTL` BGR, which
is what essentially every ILI9488 breakout uses. The datasheet cannot settle
it — filter order is a property of the glass, not the controller. If red and
blue come out swapped on the bench, clear `ILI9488_MADCTL_COLOR_ORDER`;
nothing else changes.

Reads are clocked separately. The datasheet's serial clock cycle minimum is
50 ns for a write but 150 ns for a read (§17.4.3) — 20 MHz vs 6.67 MHz — so
the driver keeps a *second* `spi_device_handle_t` on the same CS at
`ILI9488_READ_CLOCK_HZ` (4 MHz), used only by `ILI9488_read_id()`.

## C API

`ILI9488Class` borrows everything it does not own: the `spi_owner_t`, the
`kiln_io_t` and the SPI bus all belong to `app_main`, and `deinit` frees none
of them.

Bring-up:

- `ILI9488_start(disp, owner, host, io)` — the one-line `app_main` call.
  `ILI9488_init` with the Kconfig CS/clock/geometry/rotation, plus a boot
  banner so the panel proves it is alive before anything connects over UART.
  Logs and returns the error rather than aborting: a dead panel is not worth
  failing boot over.
- `ILI9488_init(disp, owner, host, io, cs_gpio, dc_gpio, reset_gpio, panel_w, panel_h, rotation, clock_hz)`
  — adds two devices on `host` (fast write, slow read), hardware-resets if it
  can, runs the vendor power/gamma sequence, sets COLMOD = RGB666 and MADCTL,
  sleeps out, turns the display on and clears to black. `dc_gpio`/`reset_gpio`
  are `-1` for "use the expander" (the normal wiring) or a real GPIO number for
  the bench-wiring bypass above. `io` is **mandatory** whenever `dc_gpio < 0`:
  with D/C on the expander, no expander means no way to send even one command.
  `panel_width`/`panel_height` are the **native** 320x480; rotated dimensions
  are derived.
- `ILI9488_deinit(disp)`

Panel state:

- `ILI9488_reset(disp, hard)` — `hard` pulses `~RESET` through the expander,
  otherwise `SWRESET`. Either way the panel returns to power-on defaults, so
  this re-runs the whole init sequence; skipping that would leave COLMOD at
  the power-on 0x06 and every subsequent pixel misinterpreted.
- `ILI9488_set_power(disp, on)` — display off + sleep in when false
- `ILI9488_set_rotation(disp, 0..3)` — updates `width`/`height`
- `ILI9488_set_invert(disp, invert)`
- `ILI9488_get_dimensions(disp, &w, &h)` — as currently rotated

Drawing. Colours are RGB565; coordinates are in the current rotation and are
**bounds-checked, never clipped** — an out-of-range rectangle returns
`ESP_ERR_INVALID_ARG` rather than drawing part of itself, because a silently
truncated frame is much harder to notice than an error return.

- `ILI9488_clear(disp, color)`
- `ILI9488_fill_rect(disp, x, y, w, h, color)`
- `ILI9488_draw_rect(disp, x, y, w, h, color)` — 1 px outline
- `ILI9488_draw_line(disp, x0, y0, x1, y1, color)`
- `ILI9488_draw_pixel(disp, x, y, color)`

Text, using the same 5x7 ASCII font as the old SSD1306 driver (6x8 cell),
integer-scaled 1..8. Wraps at the right edge to the next text line and from
the bottom back to y = 0 — there is no scrolling, which would require reading
the panel back, and this wiring cannot do that at any useful speed.

- `ILI9488_set_text_cursor(disp, x, y)` — pixels, glyph top-left
- `ILI9488_set_text_style(disp, fg, bg, size, opaque_background)`
- `ILI9488_write_char/_write_str/_write(disp, data, len)/_printf/_vprintf`

Streaming blit. `BEGIN` opens a pixel window and leaves it open across as many
`DATA` calls (i.e. as many UART frames) as it takes to fill it; `END` closes
it. Between calls the panel's address counter is live and D/C is parked in
"data", so **no other drawing may happen** — any other draw call while a blit
is open aborts the blit and returns `ESP_ERR_INVALID_STATE`. An odd length (a
split pixel) or more pixels than the window holds also aborts it, because a
desynchronized stream would smear the rest of the image.

- `ILI9488_blit_begin/_blit_data/_blit_end/_blit_abort/_blit_active`

Diagnostics:

- `ILI9488_read_id(disp, out_id[3])` — RDDID (0x04), 24 bits of
  manufacturer/version/driver ID on the slow read device. Returns
  `ESP_ERR_NOT_FOUND` if the panel answers all-zero or all-ones, which is what
  an unwired or high-impedance MISO looks like — worth distinguishing from a
  bus error.

Thread safety: one mutex guards anything spanning more than one transfer. A
window set followed by a pixel write is two-to-four transfers with the panel's
address counter live in between; a second caller landing in that gap would
write its pixels into the first caller's window. The shared `spi_owner_t`
serializes the wire itself, which is what keeps a 1440-byte pixel push from
being interleaved into the middle of a MAX31856 register burst at a different
clock and mode.

## UART subcommands (task_id 4, DISPLAY)

Payloads below are the DATA frame's payload bytes, `byte0` being the
subcommand. All multi-byte fields are **u16 little-endian**, including
colours. See `docs/UART_PROTOCOL.md` for the envelope and
`App/drivers/uart_task_ids.h` for the authoritative definitions.

| Sub | Name | Payload |
|-----|------|---------|
| 0x01 | `RESET` | `byte1` hard (0 = `SWRESET`, 1 = pulse `~RESET` via the expander) |
| 0x02 | `SET_POWER` | `byte1` on 0/1 (display off + sleep-in when 0) |
| 0x03 | `SET_ROTATION` | `byte1` 0–3 (0/2 portrait 320x480, 1/3 landscape 480x320) |
| 0x04 | `SET_INVERT` | `byte1` invert 0/1 |
| 0x05 | `CLEAR` | `bytes1..2` colour |
| 0x06 | `FILL_RECT` | `1..2` x, `3..4` y, `5..6` w, `7..8` h, `9..10` colour |
| 0x07 | `DRAW_RECT` | same as FILL_RECT — 1 px outline |
| 0x08 | `DRAW_LINE` | `1..2` x0, `3..4` y0, `5..6` x1, `7..8` y1, `9..10` colour |
| 0x09 | `SET_TEXT_CURSOR` | `1..2` x, `3..4` y |
| 0x0A | `SET_TEXT_STYLE` | `1..2` fg, `3..4` bg, `byte5` size 1–8, `byte6` opaque bg 0/1 |
| 0x0B | `PRINT` | `bytes1..(length-1)` ASCII, **not** null-terminated |
| 0x0C | `BLIT_BEGIN` | `1..2` x, `3..4` y, `5..6` w, `7..8` h |
| 0x0D | `BLIT_DATA` | `bytes1..(length-1)` RGB565 pixels, u16 LE, row-major |
| 0x0E | `BLIT_END` | — |
| 0x0F | `READ_ID` | — (query) |

`READ_ID` response payload:

```
byte0     = 0x0F
byte1     = ok (0/1) -- 0 if the read failed or the panel answered all-zero
bytes2..4 = the three RDDID bytes
bytes5..6 = width  u16 LE, as currently rotated
bytes7..8 = height u16 LE
```

A panel that will not answer still produces a valid reply with `ok = 0`, so
this query never times out on the PC side.

### Examples

Clear to black, then white 3x text at (8, 8):

```
05 00 00
0A FF FF 00 00 03 01
09 08 00 08 00
0B 6B 69 6C 6E 43 74 6C            ("kilnCtl")
```

Fill a 100x40 red box at (20, 60) — RGB565 red is 0xF800:

```
06 14 00 3C 00 64 00 28 00 00 F8
```

Ask the panel who it is:

```
0F
```

A typical answer, 480x320 landscape:

```
0F 01 54 80 66 E0 01 40 01
```

Stream a 4x2 image into (0, 0) across two frames:

```
0C 00 00 00 00 04 00 02 00        BLIT_BEGIN 4x2
0D <8 bytes: 4 pixels, u16 LE>    first row
0D <8 bytes: 4 pixels, u16 LE>    second row
0E                                 BLIT_END
```

Anything other than `BLIT_DATA`/`BLIT_END` while a blit is open is an error
and aborts the blit.
