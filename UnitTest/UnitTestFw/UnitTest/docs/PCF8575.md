# PCF8575 — Notes, addressing, and driver usage

Notes for the `PCF8575` driver (I2C 16-bit quasi-bidirectional I/O expander).

## Wiring

I2C — **shares the DAC's already-created I2C0 bus**, same arrangement as the
SSD1306 (ESP-IDF allows only one `i2c_master_bus_handle_t` per physical bus,
and the DAC claims I2C0 first at boot). `PCF8575_init` attaches as another
device on that existing bus via `i2c_master_bus_add_device()` and creates its
own `i2c_owner_t` wrapping the same bus handle, so its transfers get their own
FIFO-ordered queue independent of the DAC's and the OLED's.

No extra GPIOs: SDA/SCL are the same two pins already reported by
`INFO_CMD_GET_PIN_CONFIG`. The part's `INT` output is not used by this
firmware — reads are polled.

## Addressing (all eight supported)

The three address pins A2/A1/A0 select one of **0x20–0x27**. On this board all
three are pulled down, so the part answers at **0x20**, which is the Kconfig
default (`KILNCTL_PCF8575_I2C_ADDR`, see `docs/HARDWARE.md`).

All eight are supported at runtime as well as at build time:

- `PCF8575_set_address(exp, addr)` re-targets a live driver instance without a
  reboot — it swaps the I2C device handle for one at the new address, keeping
  the same bus and owner task, and resets the output shadow to the power-on
  state (a different chip's outputs have nothing to do with the old one's).
- `PCF8575_scan(bus, ...)` probes all eight and reports which ACK.

Both are reachable from the PC: UART subcommands `SET_ADDRESS` / `SCAN` (see
`docs/UART_PROTOCOL.md`), the GUI's address combobox + **Scan 0x20-0x27**
button, and the `expander_set_address` / `expander_scan` MCP tools.

## Pin semantics (the usual gotcha with this part)

The pins are **quasi-bidirectional** — there is no direction register:

- Writing a **1** turns the strong pull-down off and leaves only a weak
  (~100 µA) current source pulling the pin high. That *is* the "input" state,
  and it is the power-on state of all 16 pins.
- Writing a **0** drives the pin hard low.
- Therefore a pin this device is currently driving low **always reads back 0**,
  no matter what is wired to it. Write a pin high before trying to read it.

There is also no readable output register: a read returns *pin* states. So the
driver keeps a **shadow** of the last value written, and every single-pin or
mask operation (`PCF8575_write_pin`, `set/clear/toggle_mask`) is a
read-modify-write against that shadow rather than against a read-back — which
is why a read-back reports both `pins` and `shadow`, and why the GUI re-syncs
its checkboxes from `shadow`, not from `pins`.

## Write verification

Every `PCF8575_write_port` (and so every pin/mask helper, which all funnel
through it) reads the port back and checks the result before returning. Only
the bits written as **0** are checked: those turn on the strong pull-down, so
they must read back 0. Bits written as 1 are the input state and legitimately
read whatever is wired to them, so they are excluded from the comparison.

A NACK, a failed read-back, or a mismatch is logged (`ESP_LOGW`, forwarded to
the PC over the UART log bridge) and the whole write is retried, up to
`I2C_WRITE_RETRY_ATTEMPTS` (5, see `App/drivers/settings.h`) times. If it still
doesn't verify, the last error is returned — `ESP_ERR_INVALID_RESPONSE` when
the part ACKed but the pins didn't follow, which is what a shorted output or a
second driver on the same net looks like. The shadow tracks the last value
written even when verification fails, since that is still what the driver drove.

`PCF8575_init` deliberately does **not** write the port: the pins come out of
power-on reset all-high (which the shadow already reflects), and whatever is
wired to them shouldn't be yanked low just because the firmware restarted.

## Driver APIs

- `PCF8575_start(exp, bus)` — one-call bootstrap used by `app_main`:
  `PCF8575_init` at the Kconfig address plus one read-back, so a part that's
  configured but not actually present shows up as an error line at boot
  rather than only failing on the first command from the GUI. Logs and
  returns the error rather than aborting — the expander isn't critical enough
  to fail boot over.
- `PCF8575_init(exp, bus, addr)` / `PCF8575_deinit(exp)`
- `PCF8575_set_address(exp, addr)` / `PCF8575_scan(bus, out, max, count)`
- `PCF8575_write_port(exp, value)` / `PCF8575_read_port(exp, &value)`
- `PCF8575_write_pin(exp, pin, level)` / `PCF8575_read_pin(exp, pin, &level)`
- `PCF8575_set_mask` / `PCF8575_clear_mask` / `PCF8575_toggle_mask`
- `PCF8575_get_shadow(exp)` — last value *written*, not a device read

Bit N of a port value is pin N: bits 0–7 are `P00`–`P07`, bits 8–15 are
`P10`–`P17` (the port value goes on the wire low byte first, matching the
part's own two-byte format).
